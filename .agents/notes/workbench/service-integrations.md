# 服务集成与 CPA 账号管理复用

## CPA 官方插件

旧 `release/10-30-before-plugins-20261030-145752` 宿主仅授权 Blueprint，其 `1.0.0-local.1` CPA 包使用 `cpa-local`，不能与正式宿主混用。应使用 `release/10-30` 的宿主和 `official.cpa-1.0.0.jxp`。2026-10-30 复验命令 `node release/10-30/verification/check-cpa-packaged.mjs` 直接读取打包宿主的公钥与 native 白名单，签名、完整性、兼容性、实际导入／启用及重启恢复通过；开发模式关闭，仅替换文件选择器，使用隔离 profile，未验收 CPA 完整业务。结果保存在同目录 `cpa-packaged-verification.json`。

CPA 已迁入独立 `plugins/cpa/`，ID 为 `official.cpa`，通过签名包安装、权限审阅和启用。主程序移除内置 CPA 注册、专用 IPC、固定服务集成设置以及安装器／托管代码；仅保留旧配置和登录分区的固定迁移映射。2026-10-30 本地交付使用现有 `janusx-blueprint-20261026` 发布签名，生产 trust 增加 `official.cpa` native 白名单；`release/10-30/official.cpa-1.0.0.jxp` 与同目录重新构建的宿主配套，可手动导入，无需开发模式。未上传 Release 或上线发现目录。隔离开发入口继续可用。下文原内置实现的回归记录为历史证据；插件验证单独记录。

目标为：插件中心管理安装、授权、启停、更新和卸载；安装启用后在工具箱提供应用级 CPA 入口，连接配置与运行状态进入插件设置。未安装不显示 CPA 专属工具/设置入口，不包含 CPA 专属页面、安装器和运行策略；宿主保留通用浏览器、加密存储、代理及受监督进程能力。CPA 的自有前后端组件继续按需获取，插件安装和组件准备是两层状态，不能将安装插件等同于已有可运行服务。

保留本地托管和连接已有实例两种模式。保留原有按需启动：保存已开启的本地配置、打开管理页或显式启动时运行，应用冷启动和单独启用插件不主动启动 CPA；新安装默认尚未开启，不下载组件。关闭管理页只释放网页，显式停止、禁用／重载／卸载插件或退出 JanusX 停止自有实例，外部进程不接管、不终止。单次停止保留配置，重开管理页可以再次启动；关闭本地启用开关才持久禁用托管。不安装独立系统服务。Docker 的相同页面／后台分离原则见[Docker 官方插件](./docker-management-entry.md)。

### 迁移步骤与约束

1. 盘点 `extensions/cpa.tsx`、`components/cpa/`、`main/cpa/`、专属 IPC、设置和打包接线，区分 CPA 领域业务与应留宿主的通用能力。建议独立目录 `plugins/cpa/` 和可签名官方包；公开插件 ID 不使用 SDK 保留的 `janusx.*`，旧视图身份通过受控迁移处理。
2. 先验证原版管理页的承载：现有隔离插件页面离线，不能直接将 localhost/远程 CPA 管理页作为插件页面加载。使用独立、无宿主桥的受控浏览器 surface，并明确地址、持久分区、弹窗、OAuth 预检及外开能力；不整体放宽普通插件网络。native 后台迁移仍需官方签名、白名单和 OS 权限授权。
3. 将配置、组件下载更新、托管和日志策略迁入插件，宿主提供必要的通用加密/代理/网页/进程接口。现有网络与凭据契约不足以直接替换本地管理访问、可复制管理密钥、组件下载及代理，先试验缺口再收口，不能导入原宿主私有 IPC 作为插件捷径。
4. 迁移旧 `cpaSettings`、已下载组件、管理密钥、账号目录和网页登录分区。迁移前停止旧托管实例，保留加密和数据校验，保证端口单一所有者；失败保留原始数据，避免同时运行两套服务。停用/卸载保留账号和配置，删除数据另行显式处理。
5. 独立签名包安装/升级/停用/卸载以及真实托管、已有实例、代理、OAuth、登录和关闭页面后持续请求回归通过后，再移除内置 CPA 业务和固定设置页，核对主包边界。生产发布按届时授权执行。

实现采用应用级 native 激活持有进程与代理，页面 `releaseContext` 不停止后台。保存／更新为后台作业并查询进度，避免组件下载超过页面请求时限；停止和退出会失效排队作业，防止晚到启动。第一次激活将旧 `cpaSettings`、组件、配置、账号和加密密钥复制至 `janusx/plugins/data/official.cpa/native/components`，先完成临时目录后改名启用；拒绝符号链接，失败不启用部分副本，原目录不删不改。显式删除插件数据后不重新导入旧数据。

通用 `desktop.native` 必须与 `runtime.native` 同时声明，仅已验证、白名单签名且获 native 授权的服务可调用。宿主提供加密、复制、受限日志打开、当前代理与独立联网 guest；普通插件页面保持离线。guest 无 preload／SDK／Node，按所属页面校验身份并裁剪到页面分配区域；页面被遮挡时一起隐藏，关闭／崩溃／停用时销毁。固定 origin 登录分区沿用旧名称，账户登录不注入、不回传给插件页面。OAuth 路由、供应商链接与端口由 CPA 插件声明，宿主只执行通用预检与跳转隔离。

本地使用 `npm run dev:cpa`，在隔离 profile 的插件中心启用；`-- --prepare-only` 只构建签名包，已生成 `1.0.0-local.2`。`npm run plugins:cpa:check` 通过仓库外公开 SDK 打包安装、严格类型检查、独立构建及包资源检查；`artifacts/plugins/cpa/external-build.json` 保存构建依赖证据。CPA、native 服务、插件运行器、SDK、工具、窗口、视图、目录与分发相关 15 个测试文件共 245 项单测通过。

`npx playwright test --config playwright.cpa.config.ts --workers=1` 两项桌面用例通过，覆盖签名包可选启用、无项目使用、跨项目身份、独立设置保存后替换管理 guest、外部登录隔离与保留，以及 Windows 实际 CPA 8.0.31／管理页 1.26.5 的校验迁移、密钥复制、登录、关页继续服务、禁用和退出停止。实际运行使用 `JANUSX_E2E_CPA_COMPONENTS` 指向已核验的固定程序目录，只读取二进制和页面，不导入源 profile 的账号／密钥；也支持固定 ZIP 与 HTML 输入。单独启用插件不启动托管实例。截图与 trace 由 Playwright 写入 `test-results/`。

严格 unused 类型检查、应用构建、包边界、打包排除、i18n 和主题检查通过。ESLint 无错误，保留 51 项既有告警；Notes 校验保留已显式标记的跨仓引用诊断。展示脚本 `scripts/showcase/capture-cpa.mjs` 已改用隔离签名插件与公开页面，语法检查通过，本轮未执行完整展示录制。未重新打包安装器、未发布生产插件目录，其他平台真实进程及供应商 OAuth／额度查询未验证。Docker 尚未实施。

## Intent

JanusX 通过可信扩展接入 CLIProxyAPI（CPA）的既有管理页，Figma 仍为后续候选。通用扩展基础与内置工具迁移已交付 S1、S2；S3 提供应用全局的 CPA 连接设置和中部页面。服务集成增强工具连接、配置和工作台入口，保留原 CLI 的会话管理、交互和执行逻辑。

CPA 复用既有管理前端，支持 JanusX 托管本地实例和连接已有实例。已有实例模式只保存地址，不读取或注入管理密钥；本地模式首次启用下载官方组件，支持用户设置管理密钥或自动生成，加密保存后在原版页面登录，也可显式复制当前密钥。账号授权、刷新令牌和额度查询由 CPA 管理；不自动复制 CLI 登录或修改 JanusX 模型凭据。未来如需原生额度摘要或模型 API 配置，再单独确定接口和供应商覆盖。

CPA 只覆盖接入该实例的账号与调用。CLI 直接使用自己的登录时，不能假定 CPA 已观察到其身份、请求或额度。只有出现不经 CPA 的账号需求，或工作台确实需要跨实例、跨服务摘要时，再评估只读账号视图。

Figma 作为独立服务集成候选：工作台承担连接状态、设计文件关联和打开入口；Agent 读取设计或执行操作需另行核对所选 API/MCP 能力及各 CLI 的接入方式。CPA 的模型网关与账号管理不替代 Figma 授权。

先以内部集成接口验证实际需求，再评估第三方插件开放。不同集成按实际能力声明配置、状态查询、操作入口及工具接入，不要求全部实现 Harness 会话协议。此探索关联既有 [插件架构提案](./requirements/plugin-architecture-forms.md) 与 [插件导入和调试提案](./requirements/plugin-import-debug.md)，不改写其未完成验收或授权边界。

交付顺序及测试证据归[插件平台分阶段计划](../planning/plugin-platform-roadmap.md)。文件树、Git、会话管理继续由内置定义与原宿主服务提供；CPA 使用相同视图贡献协议。当前生命周期由可信代码控制，尚无插件管理页与跨启动停用偏好；第三方导入与市场归后续阶段。

### Proposed surfaces

设置中的“服务集成”位于“应用设置”分组，与终端管理并列，选择本地托管或已有实例。托管提供启用、端口、自动更新、运行状态、启停／重启、立即更新、复制管理密钥和日志入口；已有实例保留地址与“保存并打开 CPA”。后续“插件”页再负责安装、启用、更新和卸载；服务连接和插件安装状态分别维护。

CPA 设置沿用设置中心的表单样式与主题下拉组件，按连接配置、管理密钥、更新及运行状态以细分隔线分组。宽面板左侧为标签和说明、右侧为控件；小于 560px 的面板将输入行改为单列。启用和自动更新使用现有滑动开关，密钥输入内提供带提示的显示／隐藏及随机生成图标，复制已保存密钥与编辑草稿分开。更新操作位于更新组，运行组按状态显示启动或停止，并保留重启和日志；底部固定保存及保存打开按钮，编辑字段后清除旧的成功提示和表单错误。设置页、CPA 连接弹窗与首次启用页共用该布局，独立弹窗也有主题控件令牌的默认值。

用户已确认中部工作区和右侧工作区均开放为通用插件贡献入口。中部用于需要较大空间和持续操作的页面，右侧用于紧凑工具及当前项目、文件或选区的辅助信息，轻量状态入口用于状态摘要及打开完整页面。插件可以仅提供其中一种视图，也可以同时提供两种，不要求所有插件都有界面。各界面沿用现有设置与工作台的主题令牌、字号、留白和细分隔线，保持简洁，不为每项服务另设一套卡片与视觉语言。

目标插件清单声明视图身份、标题、图标、页面入口、承载位置及应用级或项目级作用域，宿主按声明自动注册入口；接入已支持的能力不需要逐插件修改主程序。S1 已支持可信代码定义的视图注册、宿主入口、打开与关闭、内存快照恢复、停用清理和局部错误处理。插件作者维护页面内容及业务状态；第三方清单字段、独立 SDK、权限和受限通信仍待后续阶段实现，不能从可信扩展接口推导为已向第三方开放。

插件包自带页面与外部服务网页分别采用受限的承载及权限规则，共用视图注册机制；外部网页不因此获得 JanusX 插件桥或被作为远程插件代码加载。同一插件同时提供中部与右侧视图时，可通过宿主提供的受限接口共享业务状态；自动搬移视图、跨容器拖拽及双视图并行保活不由本次方向确认自动承诺。

CPA 是官方集成，待市场建立后可作为推荐项。主要用途为查看管理前端提供的额度及重置次数、时间等信息，转 API 按需使用。`janusx.cpa` 贡献应用级中部视图 `extension:janusx.cpa/management`，通过右上角工具箱菜单的 CPA 项打开，设置中的保存打开仍保留；中部终端新增列表不再显示 CPA。CPA 呈现在[全局工具区](./global-tool-layout.md)，切换项目不卸载页面或转移标签，原生网页会话复用。S3 后补充本地组件托管，仍无原生右侧额度摘要。

工作区扩展可声明 `launcher: 'tool-menu'`，宿主据此将入口放入顶栏工具箱，默认仍为中部新增菜单；该字段不改变页面的中部承载位置。顶栏按注册状态及作用域生成入口，打开后显示“已打开”，再次点击定位同一页面并展开工具区，未选项目或尚无终端时仍可打开应用级 CPA。打开走全局工具的回到工作区正面逻辑；展开工具箱时暂时隐藏原生网页，关闭菜单后恢复，避免网页遮住菜单。2026-10-17 起让位状态以冻结帧呈现（见[原生网页承载](../desktop/browser-surface.md)），不再露出空场黑块；同一规则补到中部"新建终端"菜单——它的浮层原先压在 CPA 原生页之下被遮挡，现按对话框/工具箱同一套遮挡租约在菜单挂载期间让位。禁用或注销扩展后入口随注册快照移除。

中部标签栏的关闭由宿主统一使用 `HoldToConfirm`：终端、浏览器、Markdown、CPA 及所有工作区扩展均需连续按住一秒，支持鼠标与 Enter／空格键并显示进度。短按、提前松开、移出控件或失去焦点取消本次确认，不开始标签拖拽；关闭控件可通过键盘聚焦。入口来自工具箱或中部新增菜单均遵循同一规则，后续导入的工作区视图沿用宿主控件，无需插件逐个实现。浏览器仍释放对应网页，Markdown 只关闭呈现，扩展不因此停用，托管 CPA 服务及账号保留。禁用、注销或应用退出的生命周期清理不要求用户长按。

统一关闭验证：`npx vitest run tests/unit/hold-to-confirm.test.ts tests/unit/extensions.test.ts tests/unit/global-tool-entry.test.ts` 通过 38 项；`npx playwright test tests/e2e/extensions.spec.ts tests/e2e/pane-tab-drag.spec.ts --project=island --workers=1` 通过 27 项。桌面 `desktop-cpa.spec.ts` 的 Browser／Markdown 关闭重开与 `desktop-smoke.spec.ts` 的原生浏览器释放通过；CPA 登录保留用例最终以 `--grep 'CPA native page' --repeat-each=2` 连续两次通过，验证短按保留原生网页、长按释放、跨项目及重启登录复用。桌面 CPA 关闭测试持续按住直至标签移除再松手，避免固定松手时间与原生事件调度竞争。严格类型检查、局部 ESLint、应用构建及 Notes 检查通过。日志和桌面截图位于 `artifacts/tool-close*`；本轮未重跑真实托管 OAuth／供应商查询，未打包 exe。

入口迁移验证：`npx vitest run tests/unit/extensions.test.ts tests/unit/global-tool-entry.test.ts` 通过 34 项，严格类型检查、局部 ESLint 与 `npm run build:app` 通过。`npx playwright test tests/e2e/desktop-cpa.spec.ts --project=desktop --workers=1 --grep 'CPA native page' --output=artifacts/cpa-launcher/desktop` 通过 1 项桌面用例，覆盖无项目时打开、已打开禁用、工具箱遮挡及恢复、中部新增菜单移除入口、关闭后恢复入口，以及跨项目与重启登录保留；日志和菜单截图位于 `artifacts/cpa-launcher*`。未打包 exe。

### CPA connection and session

默认地址为 `http://127.0.0.1:8317/management.html`，已有实例可配置自定义路径。仅接受 HTTP／HTTPS，拒绝地址中的用户名、密码和查询参数；无协议的回环地址按 HTTP，其余按 HTTPS，根路径自动补管理页。全局 `cpaSettings` 保存模式、启用、端口、自动更新和页面地址，密钥不进入该 JSON。缺少设置时为尚未启用的本地托管，旧版只有地址的配置恢复为已有实例模式，损坏设置回退默认值以便修复。

CPA 使用专用简洁外壳：中部 Tab 已标识 CPA，不再重复显示“CPA 账号管理”；唯一顶栏右侧提供“复制管理密钥、在浏览器打开、连接设置”图标及悬停提示，复制仅在已启用本地托管时出现，成功后短暂显示勾选反馈。隐藏通用浏览器标签、前进／后退和地址栏，页面直接填充顶栏下方；加载失败仍可重试，设置对话框仍让原生视图让位。`BrowserSurface` 的 `showChrome` 默认开启，CPA 单独关闭以复用原生布局和生命周期。

界面回归：`npx playwright test tests/e2e/desktop-cpa.spec.ts --project=desktop --workers=1` 的四项用例通过，覆盖图标与悬停提示、原生视图位置和弹窗遮挡、主题下拉键盘操作、模式切换、密钥校验与管理页登录、重启保留账号及窄窗口底栏。已人工检查深浅主题、已有实例及窄窗口截图；底栏边距修正后重跑设置与真实托管两项通过，并断言底栏下沿与滚动视口对齐，避免露出被遮挡的运行控件。严格类型检查、局部 ESLint、应用构建及 Notes 检查通过；日志与截图位于 `artifacts/cpa-settings*`，未重新打包 EXE。浏览器及服务层的前轮 67 项单测证据仍位于 `artifacts/cpa-compact-unit.log`。

中部通过原生 `WebContentsView` 加载既有网页，不使用 iframe 或删除嵌入限制响应头。CPA 按地址 origin 的 SHA-256 前 24 位选择 `persist:janusx-cpa-*` 独立持久分区，与普通浏览器及其他 CPA origin 隔离。同一 origin 的路径共用登录；关闭页面释放视图，保留该分区的网页登录数据。跨项目、重新打开与应用重启可复用页面自己记住的登录。

网页没有 preload、Node 或 JanusX 完整桥，启用 sandbox、contextIsolation 与 webSecurity；固定 CPA IPC 仅允许主窗口主框架调用。CPA 没有浏览器标签栏，HTTP／HTTPS 弹窗交给系统浏览器，避免帮助页覆盖管理界面后无法返回；含内嵌凭据的地址、自定义协议和本地文件被拒绝。托管模式将核对过的 OpenAI、Claude 和 Google HTTPS OAuth 授权端点交给系统浏览器，授权弹窗和页面跳转不创建 guest 标签；打开失败显示复制链接提示。已有实例模式不改写其 OAuth 请求，同样将 HTTP／HTTPS 弹窗外开，顶栏保留“在浏览器打开”。打开对话框时原生视图让位，关闭和停用释放界面资源。此承载规则不构成第三方插件的权限桥。

原版前端“记住密码”控制其浏览器分区中的登录保存，该前端的存储不获得宿主安全存储承诺。托管管理密钥另由主进程使用 Electron safeStorage 加密持久化，无系统加密能力时拒绝启动；不注入网页，需显式“复制管理密钥”后粘贴登录。宿主模型凭据不使用这份管理登录。

### Managed local CPA

用户已选择首次启用下载、自定义端口和自动更新，认可托管 CPA 依赖 JanusX 运行。`src/main/cpa/installer.ts`、`runtime.ts` 和 `service.ts` 实现组件下载、进程托管与页面连接；固定 IPC 仅允许主窗口主框架使用。已有实例模式不接管或终止用户自行运行的进程。

2026-10-16 核对并运行[官方 v8.0.31](https://github.com/router-for-me/CLIProxyAPI/releases/tag/v8.0.31) Windows x64 二进制：ZIP 为 23,699,580 字节，`cli-proxy-api.exe` 为 72,586,240 字节。ZIP 摘要为 `28bde34eb33a1b03884bac1e8c1a402a25ae4eadd3c60df7ae0df53f8b281318`，管理页另行下载。安装器按平台／架构选择官方资源，限制后端 v8 与前端 v1 稳定版、固定仓库和资源地址，必须有 GitHub SHA-256 digest 并校验下载。仅提取根级主程序与 LICENSE，拒绝不完整归档，保留管理前端许可证；不执行归档提供的安装脚本或示例配置。CPA [MIT 许可证](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.31/LICENSE)允许再分发并要求保留声明。其他平台下载选择已实现，真实启动仅验证 Windows x64；未测量内存或完整打包增量。

组件位于 `app.getPath('userData')/janusx/components/cpa`，包含 `versions/`、`accounts/`、`config.yaml`、`management-key.enc` 与日志，数据根沿用应用现有安装版／便携版规则。二进制与管理页不进入 exe 或 asar；升级分离账号和配置。当前、前一与待应用版本之外的合规版本目录会尝试清理，清理失败不阻止运行。离线组件导入尚未实现。

本地端口默认 8317，允许 1024–65535 整数，管理页由回环主机与端口生成。修改运行中端口显示“保存并重启 CPA”并提示连接中断。启动前探测本地绑定，端口占用则失败并保留配置，不结束其他进程、不暗中换端口；随后真实绑定仍可能遇到竞争，按启动失败处理。已有实例模式独立配置管理页地址。

主进程串行管理操作，幂等启动，等待管理 API 认证及管理页就绪后再创建网页；下载／启动可停止，退出时直接中止下载并终止自有进程，防止排队中的打开请求晚到后重新创建页面。启动失败和崩溃显示失败状态，由用户重试，不自动无限重启。Windows 隐藏控制台，附带父进程退出监视辅助进程作为异常退出的尽力清理；未验证强杀所有相关进程的场景。

托管强制回环监听、关闭远程管理和自动管理页更新；首次生成独立 API 调用密钥，已有 API 配置保留。管理密钥由 safeStorage 加密并通过 `MANAGEMENT_PASSWORD` 子进程环境交接，不进入命令行、普通全局配置或明文 CPA YAML。子进程只继承必要环境，日志过滤凭据相关输出并轮转。账号令牌仍由 CPA 自己保存，不承诺全部账号文件由宿主加密。当前 Windows 发布版请求管理员权限，CPA 和监视器继承父进程权限，本轮未实现降权，也未以已签名安装包验证；这仍是已知边界。

托管 CPA 复用 JanusX 代理，不新增独立网络设置。`src/main/cpa/proxy.ts` 用 `proxy-chain` 提供随机端口、仅监听 127.0.0.1、带每次启动随机认证的转发入口，随 CPA 停止、启动失败、异常退出和应用退出释放连接及监听。CPA 的 `requests.proxy-url` 与大小写 HTTP／HTTPS 环境变量均指向该入口，并删除旧版全局 `proxy-url`。原因是 CPA 8.0.31 的管理 `requests/api-call` 在没有显式代理时主动清除环境代理，原先仅继承环境的方案能登录却不能查询额度。此通道也用于订阅信息、重置次数查询和消费操作；不单独改写各供应商请求。

每个新连接读取共享 `ProxyManager` 的当前有效地址；尚未配置时调用同一 `getSystemProxy` 检测逻辑，环境优先、Windows 系统代理次之。HTTP、HTTPS、SOCKS 上游和认证由转发库处理；无宿主代理时直连。合并大小写 NO_PROXY，支持域名、后缀、端口、通配符和 IP 网段，回环始终直连。宿主代理发生有效变更后，新连接跟随，已建立的隧道保持到结束。上游代理密码只在内存中使用，不写入 JanusX settings、状态、命令行或 CPA YAML；YAML 仅含本次本地入口的临时认证，旧入口停止后失效。CPA 显式请求／账号代理仍按上游优先级覆盖全局，不批量改写既有账号；原管理页手动改全局配置后重启 CPA 会恢复宿主管理值。已有实例模式不修改外部进程。

主进程就绪探测和 OAuth 状态读取使用独立本地 HTTP 请求，绕过全局 fetch／HTTP 代理；托管管理 guest 分区固定 direct，系统浏览器仍负责供应商网页授权。共享 HTTP 钩子保留调用者显式指定的 agent（包括 false），避免转发器再代理一次自己的上游连接。管理密钥只用于本地接口，授权 state 仅用于对应会话状态检查，不读取页面认证头、回调码或账号令牌。兼容核对包括 CPA 的 `api_tools.go`、`proxy_helpers.go`、`codex_websockets_connection.go` 和 `sdk/proxyutil/proxy.go`：HTTP 执行及 WebSocket 均读取全局显式代理，但自定义插件网络实现未全部运行验收。

首次启用下载和自动更新同样经临时转发入口，不依赖 LLM 服务是否已安装全局钩子；每个资源下载结束或失败都销毁 dispatcher 与入口，保留原取消、超时和体积限制。宿主与 llm-core 使用 Undici 7：Undici 8 的 dispatcher 与当前内置 fetch 的 handler 接口不兼容，真实代理请求会报 `invalid onRequestStart method`，仅用模拟 fetch 不能覆盖该问题。共享代理与 CPA 下载均以真实内置 fetch、本地代理和隔离目标服务验证传输，不连接真实供应商。

浏览器授权与 CPA 换取令牌是两个独立网络步骤。手动回调时 localhost 拒绝连接不代表远端授权失败；提交后出现 `unsupported_country_region_territory` 表示供应商拒绝令牌请求，不能用修改本地端口解决。统一代理修复宿主与 CPA 的出口差异，不保证供应商接受实际出口或账号。CPA 8.0.31 的 Codex 令牌交换与刷新使用 `internal/auth/codex/openai_auth.go`，读取全局代理，令牌端点为 `https://auth.openai.com/oauth/token`。用户已反馈成功生成认证文件；自动验证使用隔离测试凭据，不读取真实账号。

本地设置提供只写的新管理密钥输入框、显示／隐藏和随机生成，保存时单独传递给可信主进程，不进入 settings、状态或响应。允许 8–128 位可打印 ASCII 字符且不含空格，避免 HTTP 请求头不支持的内容；前端与主进程均校验，非法输入在停止进程或持久化前被拒绝。留空保留现有密钥，首次未设置仍自动生成；随机按钮仅修改待保存值。保存后清空输入，原密钥不回填。运行中先停止自有实例，加密原子保存成功后更新内存并启动，关闭旧页面；账号和 API Key 保留。加密或文件写入失败保留原密钥，此时服务可能已停止，可再次启动。修改后原版前端记住的旧密钥失效，用户需使用新密钥重新登录；不会注入或改写原页面的登录存储。

Windows OAuth 回调端口独立于管理端口。2026-10-16 本机 Codex 请求因绑定 `0.0.0.0:1455` 返回 500 `failed to start callback server`；IPv4／IPv6 排除范围均含 `1426–1525`，在回环、全 IPv4 和 IPv6 回环地址实测绑定 1455 全部为 `EACCES`，当时无该端口监听。上游 v8.0.31 固定 Codex 1455、Claude 54545、Antigravity 51121；管理页登录不读取 CLI 的 `--oauth-callback-port`，修改 8317 无效。来源为同版本 `auth_files_oauth_callback.go`、`auth_files_provider_oauth.go`、`oauth_callback.go` 及供应商常量，未改系统排除范围或虚拟化服务。

`src/main/cpa/oauth.ts` 在托管 CPA 的独立分区中，仅对同 origin、精确 `/v8/management/oauth/auth-url` 路径的 GET WebUI 请求预检上述固定端口，按上游相同的全 IPv4 地址绑定后立即释放。可用时保留自动回调；被系统限制、被占用或探测失败时，将同源请求重定向为 `is_webui=false`，由 CPA 生成不启动固定端口转发器的授权会话。宿主显示供应商、端口、原因和操作说明；用户在系统浏览器授权后，即使 localhost 无法访问，也复制最终完整地址至原页面“回调 URL”提交。PKCE、state、五分钟有效期、取消、回调校验与令牌交换仍由原前后端负责；宿主不读取请求密钥、授权码或令牌，不注入页面。设备码和其他供应商流程不套用这些端口。

兜底提示绑定当前授权请求及 state：观察原页状态轮询并通过宿主本地管理通道核对，只有对应会话返回 ok／error、确认取消或五分钟提示到期才清除；接受回调 POST 不视为登录完成。新会话替换旧提示，旧状态轮询及迟到结果不清除新提示。授权链接生成失败、关闭页面、停止服务或退出时清空提示并移除全部请求监听，未完成的探测和状态请求不再更新已关闭页面。探测释放至 CPA 实际绑定间仍有竞争窗口；已有实例和独立系统浏览器打开的管理页不经过此分区拦截。兼容边界为 CPA 8.0.31／CPAMC 1.26.5，上游改变路由或固定端口需重新核对；完整验证证据归阶段计划。

自动更新默认开启，运行时至多每日检查一次并暂存官方稳定前后端，下一次 CPA 启动应用。“更新并重启 CPA”立即检查、下载和重启。更新下载失败保留运行版本；新版本未就绪时恢复启动前配置并尝试当前版本，就绪后才切换 current 指针，账号目录始终保留。前后端主版本过滤及启动探测不是对未来全部小版本的兼容承诺；若供应商查询或 OAuth 后续才出现问题，仍需单独诊断。

启用保存或打开已启用的 CPA 页面时启动；JanusX 冷启动不主动运行 CPA，按需打开或点击启动即可。关闭中部 Tab 只关闭 UI；停用本地 CPA 或禁用可信 CPA 扩展时停止，真正退出 JanusX 时停止自有实例并保留数据。最小化和驻托盘不视为退出。不安装系统服务或开机独立常驻。该实现不开放第三方插件的本机执行权限，也不替代后续权限桥。

## Figma direction

Figma 候选方案分为服务连接、项目关联和 Agent 工具三部分：设置管理授权及连接状态，项目保存设计文件关联，中部打开设计内容，右侧按需展示关联文件或选中内容。Agent 通过所选 API/MCP 获取设计上下文或执行受支持的操作，并适配各 CLI 的工具配置。打开网页、通过 MCP 访问设计、运行 Figma 插件是不同能力；Figma 插件依赖 Figma 自身宿主，不能当作 JanusX 插件直接导入。网页嵌入、OAuth、读写能力和文件访问范围均未验证，不能由“已连接”推导出完整编辑能力。

## Plugin format and import direction

跨软件不存在可直接通用的完整插件包格式。VS Code、Figma 等生态各自定义宿主 API 和运行环境；MCP 可作为工具接入协议，但不自动提供 JanusX 界面、安装生命周期或工作区入口。插件市场负责发现、分发和更新，插件清单与宿主契约决定包的兼容性，应先验证包格式和加载闭环，再建设市场。

沿用现有提案的起步方向：JanusX 自有插件通过本地文件夹导入，包内包含 `manifest.json` 及构建后的界面资源，清单声明身份、版本、宿主兼容范围、权限和贡献入口。先实现导入、校验、授权、启用、使用、禁用及卸载，再评估 ZIP、远程源和市场分发。该格式及导入能力目前仍是提案，不代表已经实现，也不承诺直接兼容其他软件的插件。

现有导入草案限制首批第三方插件的网络、凭据及写入能力。CPA、Figma 优先通过官方内部集成验证连接、授权和真实工作流，再提炼第三方宿主能力；若需扩大插件权限，应明确修订原提案并补充验证，不通过单个集成绕过边界。
