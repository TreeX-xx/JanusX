# Janus SuperAgent：统一身份、异步输入与执行协调

历史审计产物和离线演示仅保存在当时的工作树。当前 Worker 回归见[测试用例](../../../../tests/unit/superagent-workers.test.ts)。

## Intent

按已采纳的[实验插件决策](../superagent-plugin.md)，下述体验适用于主动启用 SuperAgent 的用户。启用后仍由 Janus 保持软件全局控制、统一对话身份，并能在后台执行期间持续接收输入。Router、Worker 调度、订阅投递、上下文资源和监督都是 Janus 内部的职责划分，不再表述为 Janus 调用另一个 SuperAgent。用户无需选择“新事项／跟进事项”才能说话；后台仍保存工作目标与执行记录，具体内部对象名称不作为用户交互前提。

首版输入为开发者直接向 Janus 提问和要求修复。先在单工作区验证异步接收、语义归属和执行闭环，再扩展多个工作区。用户明确“不需要跟进事项”，并进一步要求以工作区为单位交互、由 Janus 生成管理分支；同工作区的基本补充判断必须进入 MVP。范围和验收草案由[需求 Note](../requirements/janus-superagent.md)维护。第四版 HTML 保留双入口和右侧 Worker 等历史演示；当前交付状态以[实施计划](./janus-superagent-mvp-plan.md)为准，P1 记录／输入、P2 环境／批准和 P3 受管 Codex／现有聊天闭环已交付；P4 自然分派与可配置容量队列、P5 共享工作卡与原文召回已交付，P6 生命周期回收、明确继续和应用恢复已接入，机制与边界见[生命周期决策](../superagent-lifecycle.md)；P7–P8 的完整 UI 与联合验收仍待后续步骤。

## Worker 协作边界（2026-11-07，已确认）

用户明确当前不允许 Worker 再委托。Janus 统一向 Worker 下达和调整工作，Worker 不创建子 Agent、不另启执行器分派任务，也不自行把工作转交其他 Worker。下文 DSH 的 Worker 子 Agent 机制仅作为外部参考事实，不代表本项目采用该能力。

后续订阅相关讨论的方向已获认可，用于接收关联上下文；尚未实施，具体订阅来源、关联规则和投递方式留待后续设计。订阅不扩大执行权限，也不等同跨 Worker 再委托、自动移交或依赖编排。本轮仅记录这两项边界，不新增执行能力。

## 最新 MVP 决策（2026-11-05，已确认，待实现）

本节与同步更新的需求条款优先于下文早期探索、DSH 参考和第四版原型行为。2026-11-05 讨论阶段只记录决策；2026-11-06 用户分别授权 xdo P1–P6，记录、环境、受管执行、自然分派／容量队列、共享上下文及生命周期已接入，实际证据见推进计划；最终 UI 与联合验收仍由 P7–P8 完成。标题保留当时设计状态和既有引用，不代表当前全部仍未实施。

- Worker 完成后汇报，用户自行查看并通过继续对话反馈；不设计专门验收机制、验收面板或强制用户验收步骤。
- Janus 规划并管理 worktree，安排 Worker 在对应分支目录开发，替代此前不建独立目录的决定。不得随意生成；新建 worktree、合并分支和删除 worktree 均须用户同意后执行。优先复用归属明确且可用的工作目录，依赖问题出现时与用户确认。
- 执行中的补充立即转发并要求在当前执行中纳入；叫停立即请求停止，不默认等整项工作结束。实际纳入和停止以原生回执为准，不声称能撤回已发生操作。
- 首个引擎为 Codex，采用可扩展的 Worker 调度机制。2026-11-06 用户明确并发数量不能写死为两个；首版默认容量为 2，后续通过配置增加数量，记录、调度和界面均按可变数量设计。
- 批准与选项操作按原生请求传回用户，答案返回原请求，Janus 不代选。等待期间不停止其他 Worker；当前 Worker 可继续的活动由原生执行器决定，不假设所有动作均可越过审批继续。
- 框架首版只考虑直接下达任务，用户自行适配工作流；最多考虑 WorkflowX 适配，不新增工作流选择、编排或验收机制。
- 关闭后下次打开尽量恢复保存的历史与界面状态，不恢复为运行状态、不自动续跑；CLI 崩溃和 MCP 断开首版不自动重试。
- 已回收 Worker 不显示在右侧，保留工作历史；支持原生查看的入口后置。
- 用户接受回收和关闭建议：ready 且执行收尾后空闲 30 分钟回收；收起面板只影响视图，关闭工作停止该工作，退出软件停止受管执行但保留记录。Inline／Spill 与链式召回具体机制继续讨论。

最新选择通过不同 worktree 承载不同分支的并发工作，不再要求两个不同分支共享同一工作树。worktree 绑定稳定工作，不绑定短期 Worker 实例；补充、重启或实例回收后再拉起优先复用原目录，不能每条消息或每次启动都新建。Worker ready、超时回收、用户关闭和应用退出都不自动授权合并或删除。批准应对应明确操作与对象：创建说明目的、基线／分支及路径；合并说明源与目标；删除说明目录及未提交／未合并情况。删除 worktree 不隐含删除分支，审批由 Janus／宿主统一落实，不能靠 Worker 绕过。此次是设计记录，不执行实际 Git 操作。

### 回收与关闭规则（已确认，待实现）；Git 方案选择记录

2026-11-05 用户接受此前推荐的回收时长及关闭规则。Janus 管理 worktree 的选择及创建、合并、删除先获同意的限制继续有效。下列 Git 三方案保留为选择依据，以本篇最新决定为准。

ready 且实际执行收尾后空闲 30 分钟回收实例，作为首版默认值，并非实验所得最佳值；收到新的执行输入即退出空闲计时，下一次 ready 收尾后重新计时。运行中、待原生审批／回答、有未投递输入或未结束后台操作时不按空闲回收；查看卡片或查询历史不重置计时。回收先确认必要记录落盘，只结束实例并移除右侧卡片，保留会话引用、worktree、代码、分支和工作历史。首版无需复杂配置页，阈值后续按实际使用调整。

关闭操作按对象命名：收起右侧或离开 Janus 面板仅影响视图；Worker 卡片“关闭此工作”停止其当前执行、撤销待执行派发并禁止普通事件自动续开，保留输入和记录，再次执行需明确继续意图；“停止全部”是独立明确操作，首版通过对话支持，不必增加全局按钮；真正退出 JanusX 时保存状态并停止受管执行，下次打开恢复记录而不自动续跑。退出是应用级中断，不把所有工作永久标成用户明确关闭。停止未确认前显示正在停止或失败，不能先隐藏仍在运行的实例；不删除 worktree／分支／代码，不把关闭当作回滚。按钮具体布局随 UI 实施细化，不改变操作范围。

Git 依据：[git-worktree 官方文档](https://git-scm.com/docs/git-worktree)说明同仓库的多个工作树可以同时检出多个分支，各自具有 HEAD 和 index。普通两个 CLI 指向同一工作目录时，共享同一份检出内容；一个切分支会改变另一个看到的文件。不同工作树可隔离目录写入，但不会消除功能依赖、端口／数据库等共享资源冲突。

推荐选择取决于是否必须同时在不同分支写代码：（A）若必须，建议重新考虑由 Janus 管理后台 worktree，界面仍只有用户工作区，目录归属工作而非瞬时 Worker，回收实例不删除目录；它确实产生独立物理目录，属于对既有决定的修改，未经确认不采用。其代价是测试须定位真实工作目录、依赖安装与结果集成仍需处理，不能声称后台隐藏就完全消除这些问题。（B）若坚持一个目录，首版可让两个 Worker 在同一当前分支协作，限制重叠写入、切分支及 Git 修改操作；这保留双 Worker 但放弃同时各自在不同分支开发，文件分工不能保证完全无冲突，执行器能否可靠约束需验证。（C）若坚持一个目录且不同分支，则写入阶段必须轮流获得目录使用权，切换前收尾并核对修改，不构成两分支同时开发。不要通过自动 stash／频繁 checkout 伪装并行。

30 分钟空闲回收、关闭按对象区分及 worktree 操作同意要求均已同步需求与验收条款；产品代码和原型尚未更新。

## 拟议职责与对象

| 责任方 | 拟议职责 |
| --- | --- |
| Janus 全局中心 | 控制软件功能与导航，理解开发者意图；通过 Router 寻找已有事项、分派及转交补充要求，解释状态并交付结果 |
| 宿主协调服务 | 持久化事项和事件，维护订阅及待投递输入，安排执行、并发、取消和恢复 |
| Worker | 在隔离上下文中调查、修复和验证，报告进展、问题、产物及证据 |
| 监督器 | 独立于被监督的 Worker 轮次检查运行与进展，执行有界干预 |

首版链路为“开发者输入 → Janus 归属判断 → 修复事项 → Worker → 结果／验证 → Janus”。Worker 长任务在后台推进，前台继续接收输入；具体追加消息的安全边界和宿主接口需要核实。

工作事项应具有稳定 ID、项目／工作区、目标、范围、状态、关联输入及结果。一次执行记录绑定事项和执行器实例，保留尝试、取消和验证证据。输入事件保留身份、来源、时间、内容引用和投递状态。订阅负责把事项的新输入送给当前 Worker，并把结果送回 Janus；关联引用只提供上下文，不隐式触发执行。

这些是待设计的领域职责，不要求首版逐一新建同名服务或数据库表。复用现有类型时需要核对语义：自动化卡片是分组，自动化任务是独立调度单元，工程 Task 带验收义务，三者均不能未经定义就等同于持续事项。

## 工作区、实例与外部 Worker（拟议）

用户确认 SuperAgent 就是 Janus，只保留一个对话身份。后台活动视图可展示进展和结果，但不要求用户建立、选择或跟进事项。此前每工作区默认一个独立 SuperAgent 工作台入口的建议已撤回。用户提出的“像启动终端一样打开界面”可作为打开 Janus 活动视图的候选入口，不因此创建新的对话身份或后台实例。

MVP 先在一个明确工作区内处理多个目标，使用 Codex，按可配置的并发上限 N 执行，默认 N=2，满额排队；执行期间继续提问，补充立即转发。事项保留工作区归属及独立执行记录，跨项目分派后置；后台服务组织仍待实施设计。

用户提出的当前交互方向是：左侧切换工作区时，同一个 Janus 的前台注意力自动切换，分别使用各工作区的上下文及 Worker 执行记录。这替代此前“浏览工作区与发送范围另设选择器”的方案。工作区是默认输入范围，输入框保持普通消息输入，不设“新事项／跟进事项”模式；实际是否好用仍需原型与真实试用验证。

切换工作区改变后续输入的默认范围，不迁移、停止或重启已有后台工作。每条已发送输入在提交时记录工作区身份；即使 Janus 尚未处理完，之后的 UI 切换也不能改变它的归属。Janus 结合当前工作区对话、正在执行的目标及消息内容判断新请求、补充、状态询问或停止要求。明确提及其他项目、引用其他工作区结果时可按引用处理；含糊指代存在关键歧义时简短询问，不能只因最近弹出另一项目通知就改变默认目标。

建议各工作区独立保存对话历史、摘要、工作目标、资源引用和 Worker 会话／执行状态；切回来恢复原上下文，不把其他工作区的完整历史拼入当前上下文。Janus 的全局身份、软件操作能力及用户通用偏好可以共享，跨工作区概览读取状态摘要而非混用执行上下文。对话区域建议随左侧工作区切换到对应历史，输入框旁仅显示当前工作区名称；这是同一 Janus 在不同项目中的上下文，不要求用户管理多个 Agent。

每个工作区拥有归属于自己的 Worker 会话和执行记录，不意味着必须常驻一个 Worker 进程。Worker 按工作目标按需创建或恢复，同一工作区后续可以有多个 Worker；实际并发受全局资源限制。切换到 B 时，A 的 Worker 按原策略继续或排队，完成结果落回 A，可提供带工作区名称的轻提示，不抢走当前对话焦点。未发送草稿建议按工作区保存，避免在 A 写了一半的要求切到 B 后误发；草稿与输入绑定规则待原型验证。

项目／仓库身份、用户工作区、执行目录及标签页仍需区分。执行记录绑定实际目录、分支／worktree 和允许资源，标签页仅为视图。逻辑隔离必须由工具访问和调度约束落实，不能只依赖筛选。具体身份复用现有仓库契约，不能以当前选中路径或标签页 ID 作为持久事项归属。

Janus 为不同分支的并发工作安排 worktree，优先复用已有工作目录，必要新建时先取得用户同意。调度容量可配置，默认并发数为 2，后续可增加；worktree 解决文件树隔离，依赖和共享外部资源仍需按实际情况协调，跨项目范围后置。

Worker 使用外部 CLI，首版已选 Codex，Claude Code 等多引擎后置；Janus 自身运行时与 Worker 引擎分开。已有[终端／对话双模式](../../workbench/terminal-dialog-dual-mode.md)可复用，但不等于已接通调度。首版适配需要启动、运行中立即追加、事件／产物回传、停止与原生审批／选项往返，不能静默用“等下一轮”代替即时补充；原生查看和人工接管能力后置。再次打开恢复记录，不承诺恢复原执行现场，CLI 崩溃／MCP 断开不自动重试。

截至 2026-11-05 核对的官方接口：[Codex App Server](https://developers.openai.com/codex/app-server/)提供 thread／turn、运行中追加、流式事件、中断及会话恢复；[Claude Code 程序化入口](https://code.claude.com/docs/en/headless)提供 CLI／Agent SDK、结构化输出和按 session ID 继续会话。具体可用行为仍需按本地支持版本验证；不把原生终端桥接与官方程序化入口视作相同接口。

事项 ID 独立于 provider session ID。更换引擎时保留事项、文件状态和证据摘要，为新 Worker 建立执行记录，不假定不同引擎能直接恢复彼此的会话。托管执行与用户接管需要单一输入控制权，避免 Janus 和终端同时发出冲突指令。首版只打通一种外部引擎的真实闭环，保留适配边界；多引擎混用、完整配置界面和自动分配策略后置。

### 外部 Worker 配置与分期

建议复用现有“终端管理”、CLI 检测安装、原生登录及模型配置，不另建一份凭据或安装管理。当前 `ExternalCliManager.tsx` 已有 installed／runnable／version 等检测状态与安装管理入口；配置与原生登录的现有边界见[终端模块](../../terminal/module.md)及[Shell／终端管理](../../terminal/shell-profiles.md)。这些能力可作接入前置条件，但 CLI 可启动不等于已经满足 Worker 的回执、续接、停止和归属契约。

后期在设置中增加轻量的“SuperAgent → Worker”区块即可：哪些引擎允许作为 Worker、默认引擎、最大运行数量及可用性／接入检查；模型优先复用引擎现有配置。工作区覆盖和按工作类型自动选引擎是否需要，待实际使用再决定。对话框不增加每次必选引擎的步骤。右侧卡片可显示实际引擎，并提供查看原生终端／人工接管入口；终端承载查看和手动操作，适配层负责可靠投递、状态回传及会话归属。

后期多引擎可分别执行不同工作，用户仍只与 Janus 对话；每个 Worker 记录实际引擎、会话和代码环境，修改默认引擎不迁移既有会话。首版已选 Codex，并发容量配置独立于后续多引擎设置；默认值为 2，增加 Worker 数量不要求接入其他引擎。

原生仓库与自动化服务作为共享能力接入：仓库提供 Issue／PR 上下文及差异入口，自动化提供触发时机，SuperAgent 承接事项执行。MVP 仍只由开发者直接输入触发，外部来源和自动触发后置。初始界面与 Island 均可启动同一个 SuperAgent 工作界面；启动后 Island 只提供通知，具体运行情况在右侧 Worker 视图展示。点击产物可定位原生差异／文件界面，需人工接管时进入对应执行会话；真实原生面板联动仍未实现。

## Worker 生命周期与后续开发（简化方向）

完成侧保留 Worker 上报 ready 与用户明确关闭；Worker 可按时间回收，需要时由 Janus 再拉起，替代此前永久保持原 Worker 的方向。实例回收保留关联记录、worktree 与代码；首版空闲时长已定 30 分钟，关闭范围按前述已确认规则处理。

DSH 的 [Executor 实现](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/executor/dsh.ts)明确管理每 Ticket 的持久 Session，后续 Assignment 通过相同的 `worker-<ticket id>` 定位会话；原指令已在历史中时只发送后续信息。[执行规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md)区分空闲／人工交接释放槽位、普通续接、失败重试和宿主重启。无 PR 的 ready 可结束 Ticket，有 PR 时可处于待 review；结束仍可保留会话和订阅，在授权仍有效、未被用户明确停止时，由其所属 Thread 的人类消息续开。不能把“交付完成”“Ticket ended”解释为会话删除，也不能笼统说 DSH 所有 ready 都等待人工验收。

Worker 报 ready 且执行收尾后释放槽位，连续空闲 30 分钟回收实例；相关执行输入到来时，尚存实例继续，已回收实例按工作记录再拉起。能续接原生会话时复用，否则以摘要、记录及当前代码建立上下文，不强制相同 Session ID。运行中、等待审批／回答、有待处理输入或未收尾活动时不回收。

ready 不等于用户关闭，超时回收不改变 ready 记录。明确关闭停止该工作并取消待执行派发，普通关联消息、迟到事件和监督器不能自动复活；用户明确要求继续后再安排。关闭不删除代码、worktree、分支或必要历史；收起面板只改变视图。

| 后续输入 | 建议处理 |
| --- | --- |
| 当前功能仍在执行时补充条件 | 关联原目标并立即转发至运行中输入通道；不默认延至下一轮，不因一条补充创建独立 Worker |
| 明确提出另一个独立新功能 | 建立新的内部工作目标，提供当前项目相关背景，按容量启动新的执行会话或排队 |
| ready 后、实例尚在时的补充 | 关联原工作并继续现有实例；不要求用户选择 Worker |
| ready 后、实例已超时回收时的反馈 | 按工作记录自动拉起 Worker，能续接则续接，否则用记录及当前代码重建上下文 |
| 用户已明确关闭的工作 | 保持关闭，用户明确要求继续／重新开启后才执行 |
| 原功能新增需求或范围明显变化 | 建立关联的后续工作，避免无限扩展旧目标或让旧会话承载整个项目历史 |

这些归属由 Janus 在自然对话中判断；用户不选择 Worker 或工作 ID。旧功能匹配可先基于当前工作区、功能描述、关联模块／文件及修改记录，读取必要历史；首版不要求向量库或知识图谱。信息不足时可检查当前代码并询问关键复现条件，不能凭相似名称假装已找到原工作。项目的现行事实仍由代码与原始工程 Note 维护，执行历史只提供历史证据与引用。

再次处理旧功能时，优先确认当前分支、提交、未提交改动及相关代码是否已变化，再判断原会话是否适合续用。即使能恢复原 Worker Session，也不能默认它记忆中的实现仍然有效；原 worktree 已回收时，按当前目标重新准备执行目录，不自动切回旧代码覆盖后续功能。跨引擎或会话不可恢复时，用目标、实现摘要、代码／产物引用和验证记录为新 Worker 提供起点；不宣称完整恢复原运行现场。

MVP 主路径验证“开发 A → ready → 超时回收 A 实例 → 开发 B → 用户反馈 A bug → Janus 找回记录并自动拉起 Worker 处理”。不要求用户操作恢复按钮、选择 Worker 或重述完整背景。另验证正在执行时不被空闲计时误回收，以及人工关闭不被普通事件重新启动。自动按需拉起是正常路径；宿主崩溃后的全面故障恢复仍按后续阶段推进。

## DSH 公开原型的完成机制（核对）

2026-11-05 再次核对公开修订 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4`，不推断其内部系统具有相同实现。[work 提示词](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/work.md)要求 Worker 完成实现、自审和相关检查后通过 `orchestrator_report` 上报 `ready`，报告包含变更、实际运行的测试和风险。必要后台检查尚未结束时不得报 ready；不完整且存在实际阻塞的草稿应说明剩余工作。默认编码交付包含 PR，除非任务明确要求另一种交付物；无需等人工批准或合并才上报 ready。

质量要求主要通过任务／仓库约束及提示词执行。[delivery 默认提示词](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/delivery.md)另要求 UI PR 提供实际应用的前后对比及版本信息，由 Worker 捕获验证，协调者在交付前检查报告的证据。该要求可由团队配置，不能等同宿主代码已实现通用质量证明。

代码边界见 [executor 报告工具](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/tools/executor.ts)及 [Assignments.report](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/core/assignments.ts)：报告字段主要是状态、摘要、问题／回答关联和 PR 编号；宿主检查归属和状态合法性，如 ready 不可同时附带待人回答的问题，保存报告并推进生命周期。该入口没有逐项测试证据 schema、重新执行测试或证明代码满足原始需求的通用校验。此前为 Janus 提议的版本对应结构化证据校验是拟议增强，不能称为 DSH 已有同等硬性机制，也尚未由用户定案。

[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md)与 [Tickets.followsDone／threadClosed](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/core/tickets.ts)将 ready 与 Ticket 结束分开：没有关联 PR 时 ready 可结束为 completed；有未结束的相关 PR 时等待 review。Ticket 创建的 PR 全部关闭后结束；没有自己创建的 PR 时要求所跟随的 PR 全部关闭。合并与未合并关闭分别记录 merged／closed，结束不都代表成功。PR 关闭时仍有尚未完成的续接／重试／恢复工作，或已接手但尚未处理完的后续消息，会推迟结束。无可交付工作的情形可 dropped；人工停止另为 stopped。

一轮模型执行结束可成为 waiting，不能代替 ready；正常交接可释放槽位。Ticket 结束仍保留会话／目录与订阅；其负责的原 Thread 后续有人类输入，且授权仍有效、不是人工停止、不是只跟随上下文的 Thread 时，可再续开。Janus 首版没有 PR，需要另行定义本地交付／测试／集成状态；本轮仅记录 DSH 事实，不据此强加 PR 或人工验收步骤。

## 完成判定与分支开发（简化方向）

用户希望减少完成流程复杂度：Worker 按原任务及仓库要求完成工作、自查并报告 ready，Janus 显示结果；不新增一套逐项机器验收、独立 Reviewer 或强制人工验收流程。完成侧只表达 ready 和用户明确关闭；运行、排队和错误仍需如实显示，但不扩展为多层交付审批。是否提交、推送或合并继续按原请求及项目规则处理，不由 ready 自动推导。

ready 由 Worker 明确上报，不从终端退出或无输出猜测。结果采用简短说明，交代做了什么、实际检查及未验证内容；保存必要工作记录、引擎／会话引用和代码环境以支持再拉起。宿主只处理基本归属、投递和关闭约束，不将此前提出的结构化质量验收器纳入 MVP。真实错误或仍未完成的工作不能伪装成 ready，用户也无需填写验收表。

新反馈进入后继续执行，新一轮结果再次上报 ready。旧报告作为历史保留，不代表新反馈已处理。更细的证据版本门槛、自动质量复核与人工验收机制后续按真实需求另议。

分支是执行归属的重要维度，但分支名会移动、重命名或删除，不能作为唯一持久工作身份。内部工作记录建议关联仓库／工作区、执行 worktree 或目录、目标分支、起始提交、已验证提交或工作树快照、相关差异和集成目标。一个分支可包含多个工作，一个功能后续也可能出现在多个分支；不设置“一分支永久绑定一个 Worker”的规则。

新输入在发送时固定工作区，界面不要求选择分支。Janus 根据目标、已有工作与用户明确引用解析代码环境：新目标准备工作分支，原工作补充复用已绑定环境；环境确定后记录分支、实际目录和基线／版本快照。切换工作区不迁移已提交输入和已有执行。显式提及其他分支、集成版本或旧功能时，仍需核对真实测试版本和修复落点，有关键歧义再澄清；不把另一分支上的完成结论当作当前代码事实。

Janus 负责规划和管理分支／worktree，Worker 按可配置容量并发执行。新建 worktree、合并和删除均经用户同意后执行，不自动推导提交、推送或其他清理授权。优先复用已绑定工作目录，保护未提交修改，回收实例不删除目录或分支。依赖问题与用户确认，基线和命名可由 Janus 提案后随创建操作审阅，不要求用户在主对话中手动切分支。

代表场景：用户在同一工作区提出登录和设置，Janus 分别准备 `janus/login-01`、`janus/settings-02` 等工作分支（命名仅为演示）；两个功能分别按目标及证据交付，集成状态单独展示。用户在 `main` 测试登录失败时，Janus 先检查集成事实及当前实现，必要时建立面向该版本的修复，不盲目恢复旧目录。分支合并或 worktree 回收后，历史工作通过提交／差异／后续集成引用继续可追溯；回收 Worker 不自动删除分支或未交付代码。

## 异步输入与归属（拟议机制）

异步输入意味着执行未结束时用户仍能提交消息，Janus 可靠接收并独立于长时间 Worker 执行安排处理；不等于所有消息立即改变正在运行的工具，也不等于每条消息新建 Worker。建议区分“已收到”“已纳入执行／等待下一步生效”“已完成”的事实，避免收到补充就声称正在运行的操作已遵守新要求。

最小链路为：持久化输入事件 → Janus 读取对话及当前工作摘要 → 决定回答、关联原工作、建立新工作或澄清 → 按引擎能力投递 → 进度与结果回到同一对话。Worker 长命令不占住前台输入处理；具体调度方式可以是宿主事件循环与独立执行轮次，不预设多个前台模型会话并行修改共享状态。

例如用户先说“修复登录问题”，执行中又说“只在刷新后出现”，Janus 应自动关联原工作；随后“另外检查配置保存”可形成独立后台工作。用户不选择 Ticket 或 Worker。“那个先别改”存在多个合理目标时才在原对话询问；未确认前不对不确定目标执行停止／修改动作，其他已明确工作如何继续由调度策略控制。

输入需有稳定身份、接收次序及处理／投递状态。后到的改动要求可能使早先结果不再满足目标，建议给工作目标与输出关联修订版本；最终交付说明验证覆盖到哪次要求。更改或停止请求应及时处理，但中断只能影响尚未完成的动作，不宣称能撤回已发生的写入。上述为机制建议，具体时延、取消语义和版本契约未定。

MVP 可只有一个活跃 Worker，同时接受消息、回答状态和安排后续工作。多个工作记录、多个持久 Worker Session 与多个正在执行的 Worker 是不同数量；并发单独验证。内部记录用于隔离、恢复和证据关联，不能据此要求用户管理任务面板。

## DSH 参考：单仓库、工作目录与多个 Worker

以公开修订 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4` 为依据。[README](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/README.md)明确将其定位为面向一个 GitHub 仓库的主动编码 Agent，并注明公开研究原型不同于团队内部版和文章中的全部设计。本次核对不能据此推断 DSH 内部系统已经支持统一多仓库工作区管理。

[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md)说明每个 Ticket 拥有一个 `worker-<ticket id>` Session 和工作目录。目录位于配置的执行根下，prepare command 可通过 `git worktree` 准备代码；不配置准备命令时是空目录。因此它的每工作执行目录不同于 JanusX 用户界面的工作区，也不等于每仓库一个 Worker。目录建立执行默认值，不是安全隔离本身。

[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/001-domain.md)中，新工作被 Eval 接受后创建 Ticket，再通过 Assignment 交给 Executor。同一 Thread 可以包含多项独立工作。因此一个仓库内不同 Issue、PR 或同一讨论中的独立请求都可能形成多个 Ticket／Worker；具体是否新建取决于工作范围与评估，不是每来一条消息就创建一个。

已有工作通过订阅接收相关 Thread 的后续消息，同一消息可以扇出到多个已订阅 Ticket；Worker 判断范围内补充并处理，范围外内容交还重新评估。这种外部 Thread 自带归属线索，不能直接等同于 Janus 单一对话流的语义分流。用户不选事项时，Janus 需要负责这层判断，不能把整个全局对话无差别订阅给所有 Worker。

多个 Worker 同时执行受 slot 并发限制，等待执行与等待事件不同；人类补充／状态请求还可使用一个额外槽位。后台 shell job 或 subagent 尚未完成时可能继续占用原槽位；Worker 自身又可创建 subagent，这是另一层并行，不应与多个 Ticket 的 Worker 混为一谈。重试可在同一 Session／目录内建立新 Assignment，不必产生新的独立工作。对 Janus 的启示是按工作目标管理执行生命周期，并把全局仓库管理与每项工作的执行环境分开设计。

## 订阅与投递

订阅绑定事项，不绑定短期执行会话；创建事项时由系统建立首版内部关系，不要求用户配置订阅。Worker 替换后，待处理输入仍归属原事项。宿主先记录输入和待投递动作，再进行投递；区分待投递、已进入执行上下文和已形成结果，避免重启或重试造成丢失与重复执行。

新问题由 Router 判断是否建立事项；明确的补充输入沿已知关系投递。归属不明确时询问用户，事项范围发生实质变化时重新确认其边界。收到内容不自动扩展执行权限。后续 PR／IM 来源可转换为相同事件，但首版不实现外部来源、外部身份策略或平台写回。

## 两级过滤：首版轻量入口，外部来源后扩展

原文 3.1 节把事件处理分成程序层 Fast Path 与语义层 Slow Path：先用来源、群组及人／机器人等确定规则减少环境噪声，再交给模型判断是否需要行动。这不是两个模型依次审查每句话，也不是先后两次人工批准。公开原型的 gate／assessment 是相关实现，但显式请求可以直接路由，已有订阅中的后续输入走已有工作处理，不能宣称每条消息都必经完整 assessment。

Janus 首版只有开发者直接输入，程序层轻量处理有效输入身份、重复投递、发送时的工作区及明确关联；代码环境由已关联工作解析，用户明确引用可一并保留，不要求先选分支。身份相同的重复事件可以去重，内容相同但用户再次主动发送的消息不能仅凭文本去掉。用户直接消息默认进入处理，不以推测“价值低”静默丢弃。语义判断复用 Janus 当前路由能力，决定普通回答、全局软件操作、续接原工作、新工作或必要澄清，不额外强制一次模型调用。

过滤和订阅直通是不同机制：前者判断事件是否进入处理／是否需要行动，后者在归属已确定时省去重复分派。自然语言归属不明确时不能用 Fast Path 猜测；整个工作区对话也不能无差别发给所有 Worker。后续接 PR／Issue、CI、自动化或 IM 时，再补齐各来源准入、机器人／CI 噪声规则与主动行动策略。初版保留接口和可解释的处理原因，不先建设完整外部策略后台。

### MVP 两级处理设计（已确认，待实现）

2026-11-05 用户确认本节设计。第一层由宿主程序处理确定信息，第二层由同一个 Janus 理解意图。Worker 拉起／投递是判断后的执行，不另设第三个评估 Agent。P4 已将该入口与可配置容量队列接入正常聊天，现行事实归[调度决策](../superagent-scheduling.md)；P5 完善上下文与预算，P7 更新 HTML，以下设计继续作为分步实施依据。

| 输入 | 第一层处理 | 是否需要 Janus 理解 |
| --- | --- | --- |
| 开发者正常新消息 | 先保存和回执，固定工作区，进入处理队列 | 需要；不凭关键词把用户输入直接送给某 Worker |
| 相同 eventId 重投 | 返回原处理状态，避免重复副作用 | 不重复调用；尚未处理完的原事件继续处理 |
| 明确绑定目标的 UI 操作 | 如点击某工作关闭，检查目标后直接执行 | 通常不需要；普通文字“关掉那个”仍需理解 |
| Worker 高频输出和普通进展 | 关联到对应执行，更新右侧状态和保存日志；可合并显示刷新 | 通常不逐条唤醒 Janus；日志本身仍保留 |
| Worker ready、待用户回答或失败 | 保存关联结果，更新状态，交给 Janus 按需要解释／交付 | 必要时唤醒一次，不循环把自身通知当作新需求 |

来源和关联 ID 由宿主封装，不相信消息正文自称的身份。最小事件记录为事件 ID、来源／类型、工作区、内容或读取引用；Worker 事件再带工作与本轮执行 ID。旧实例被回收后迟到的 ready／输出只记录来源，不得覆盖新执行状态或重新开启人工关闭的工作。重投去重以事件身份判断，不以文本相似度判断。

第二层使用当前消息、必要的最近对话和该工作区候选工作的短摘要。候选可包括运行、ready、实例已回收和已关闭的工作记录；没有活跃 Worker 不等于没有历史工作。缺少背景时按引用读取必要内容，不能只用功能名相似或当前选中的右侧卡片决定投递。

语义结果限定为直接回答、软件操作、新工作、已有工作补充／继续、关闭／明确重新开启、必要澄清。普通历史询问或状态查询只读取记录，不能因为提到了旧功能就拉起 Worker。关联明确且确实要求继续执行时，实例存在则投递，不存在则按记录拉起；人工关闭的工作需要用户明确重新开启意图。单条消息若包含多个明确要求，可分别处理，不强制“一句话一个 Worker”。

程序在动作落地前再核对工作区、工作是否关闭和当前实例，避免 Janus 判断期间状态变化造成错投；这是动作有效性检查，不新增一轮模型判断。异步补充按序保存并立即转发，以原生回执核对纳入；模型判断或投递失败保留待处理状态，不自动改判新工作或回报“已执行”。CLI 崩溃和 MCP 断开首版不自动重试。

首版候选上限、摘要预算、处理延迟与进展合并频率暂不写死；不先建设噪声评分、多模型投票或外部来源规则后台。优先检验四种区别：重复投递／重复发言、历史询问／继续执行、超时回收／人工关闭、旧实例结果／当前执行结果。

## Inline／Spill 与上下文

Router 直接看到事项摘要、最近变化、状态和需要决策的问题；Worker 直接看到目标、范围、当前输入及必要背景。完整历史、日志、diff 和验证证据保留在可按需读取的资源中。短内容直接注入，超过预算时返回摘要或明确截断的片段及读取引用。

引用应能说明资源归属、来源和版本，内容变化时能识别旧结论。读取返回有界内容及下一段入口，并提供关联事项或证据的可读引用。上下文资源服务按调用事项限制可见范围，不把所有项目历史注入全局 Router。

Inline 与读取软额度已按第三轮方案确认，资源保留期限和具体引用格式仍待定。首版只实现直接输入与执行产物需要的资源，不先建设通用知识图谱或另一套记忆系统。

原文 3.3 节的链式召回（Chain of Recall）是沿对象引用按需逐步取回上下文：对象有稳定 ID，读取结果包含紧密关联对象的摘要和 ID，必要时继续读取。例如消息 → 所属讨论／关联工作 → Worker 历史及报告 → 对应修改与验证证据。它不是暴露模型内部推理链，也不只是把长文本展开；关键是每次读取都能找到下一步有关的资源。

公开原型的 [cards.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/cards.ts)与 [resources.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/resources.ts)提供摘要卡片、关联 Thread／Trigger／Ticket、输入／报告／会话历史资源及分页读取，是可参考的实现基础。Janus 不需让用户管理这些 ID，也不必先引入图数据库。

建议 MVP 把链式召回作为 Inline／Spill 的一部分：记录消息到工作、工作到 Session／报告／代码证据的关系；提供按 ID 读取、关联摘要和明确截断／分页信息，限定工作区可见范围与读取预算。Janus 先根据当前工作区、明确引用或有限候选查询定位入口，再沿引用补齐历史；链式读取本身不保证能从任何模糊描述找到入口。将“开发多项功能后，Router 当前上下文已不含 A 的细节，用户报告 A bug，Janus 按引用找回 A，续用现有 Worker 或按记录重新拉起”加入验收。全文／语义检索优化、跨渠道引用网及大规模历史治理后置。

### MVP 上下文与按需再启动方案（讨论中）

本节保留早期总体方案，具体结构、更新规则、额度和失败边界以后续已确认小节及需求为准，不代表已实现。核心是持久工作记录负责连续性，Worker 进程只是可替换的执行实例；不依赖 Janus 始终在当前对话窗口记住旧工作，也不承诺已退出进程原样复活。

建议保留三类对象：稳定的工作记录（工作区、目标／别名、约束、ready／关闭情况、当前摘要、关联输入和执行、代码环境引用）；可替换的执行记录（工作 ID、轮次、引擎、可用的原生会话引用、状态、输入纳入位置）；持久资源（原始消息、报告、日志、修改／验证记录及关联引用）。工作与资源不随实例超时回收删除，关闭只改变继续执行的许可，不从可查历史中移除。首版可用本地结构化记录和资源文件，不要求图数据库或向量库；具体存储实现未选定。

Inline 是给当前模型调用的有限上下文：Janus 获得当前工作区、当前输入、必要近期对话、运行概况和相关工作候选卡片；Worker 获得目标、约束、新输入、最近工作摘要、实际执行环境及必要引用。Spill 是把超出预算的完整内容持久保存为可读资源，同时在 Inline 返回概述、范围／版本和引用。内容先保存成功才允许用引用替代，不静默丢弃；摘要不能替代原始记录。读取返回有界片段、是否截断、下一段入口及关联对象，资源不可用时明确说明。

链式召回之前必须有“找入口”的能力。宿主持久维护整个工作区的轻量工作目录，包含 ready、已回收实例和用户关闭的工作；不得仅搜索最近几项活跃工作。首版按明确消息引用、标题／别名、目标描述、涉及路径和分支等检索元数据，给 Janus 有限候选；没有明确匹配时可扩大关键词或分页查询，仍有歧义才澄清，不能把搜索无结果直接当作不存在历史。语义检索增强后置，基础元数据查找需在首版成立。

找到入口后按需沿关联读取，例如新输入 → 候选工作摘要 → 原需求／最近报告 → 历次执行与相关修改 → 当前代码核对；不要求每次遍历所有节点，也不按时间回放全部日志。摘要在目标／约束变化和 ready 报告等关键点更新，记录覆盖到的输入／执行位置及代码版本；摘要滞后时补读尚未覆盖的输入。原始记录随事件持续保存，不能等回收瞬间才尝试让模型记忆全部历史。自动回收前确认必要记录已落盘且无执行或待处理输入；这属于记录完整性，不引入质量验收器。

按需继续流程：先保存新输入 → Janus 判断是查询还是执行 → 查找并读取旧工作 → 程序复核关闭状态及实际目录／分支／当前代码 → 在同一工作记录下续用现有实例或创建新的执行轮次。引擎支持且旧会话可用时尝试续接，否则使用目标、约束、最近报告、未纳入输入及当前代码信息构造启动上下文。旧目录不存在或代码已集成时，结合当前实现重新确定修复落点，不能盲目恢复历史分支或覆盖后续修改；无法确定时澄清。每项工作同一时刻只允许一个有效启动／执行归属，重投不会重复拉起，迟到旧轮次结果不可覆盖新轮次。引擎不可用或启动失败时保留输入、显示失败或待处理，不伪报已恢复。

区分两种“关闭”：ready 后自动回收实例，明确修复反馈即可自动再拉起；用户明确关闭工作后，查询、普通通知和迟到结果不触发重开。用户说“上次那个登录功能再修一下”且目标明确，可视为明确重开意图，不需要输入专门口令或操作恢复按钮；仅说“以前那个有问题”且是否要求继续不明确时简短澄清。右侧重新出现该工作的执行状态，用户始终与 Janus 对话，无需选择原 Worker。

建议验证场景：A ready 并回收，开发 B 后清空 Janus 当前模型上下文，再反馈 A；用户已关闭 A 后分别询问结果和明确要求再修；原生会话丢失但工作资源仍在；旧分支已集成或目录失效；同一输入重投与旧实例结果迟到。验收应验证能找到记录、构造可用启动上下文、正确落到当前代码且不重复执行。机制可保障记录和引用可查，不能保证模型对所有模糊表述准确匹配；模型判断、CLI 可用性和记录缺失需分别暴露失败。具体上下文预算、候选数、摘要更新策略和资源保留／清理规则继续讨论。

### 上下文机制第一轮细化：目录、工作卡与原始材料（P5 已实现）

当前实现由[上下文决策](../superagent-context.md)维护：同一 Janus 与 Worker 共用投影和原文读取，保留来源／版本／覆盖，模型读取前不将工具回执当作已读。以下保留需求解释；实例生命周期仍归 P6。

用户以“可以，讨论下一个”接受三层结构及职责方向：在现有工作／输入记录上增加有界投影和资源引用，Janus／宿主维护工作卡，Worker 正常汇报，不新建记忆 Agent 或要求用户整理知识库。具体卡片字段、摘要更新规则、数据表、token 数和保留期限尚未定案；工具名称为示意。

三层组织：（1）工作目录，作为整个工作区可检索的入口，保留标题／别名、目标、相关文件、状态和工作 ID，包含 ready、已关闭与实例已回收的工作；目录不要求全量注入每轮模型。（2）工作卡，提供目标、用户约束、当前进展、最新结果、未纳入输入、实际 worktree／分支和关联资源引用；身份、状态、代码环境来自宿主记录，语义摘要从已发生的任务理解和 Worker 报告增量维护。（3）原始材料，包括用户输入、Worker 报告、必要执行记录／日志及代码修改引用，按稳定 ID 和版本读取；历史修改快照与当前可变文件引用须区分。工作卡是这些记录的可重建摘要，不是唯一真相。

Janus 的 Inline 包含当前输入、必要近期对话、运行 Worker 的汇总、相关实例的简短概况及本次候选工作卡；无关旧工作的详情留在资源中。Worker 的 Inline 只包含自身目标、明确约束、最新输入、已关联工作背景及实际环境引用，不接收整个工作区聊天。运行中新增约束应立即通过已确认的输入通道发送，不能只更新卡片后等待模型偶然读取；MCP 资源读取不是异步输入通道的替代。

Spill 在输入／结果进入上下文时先保存可读取正文，再按长度预算返回正文或摘要／明确截断片段及引用，不等模型上下文满了才临时导出。若摘要尚未生成或已滞后，返回真实片段和未覆盖输入引用，不捏造完整摘要。原始需求、补充、报告和必要执行边界由宿主持久化；完整逐 token 过程、超大日志和保留期限单独设计，不承诺无限保存所有外部 CLI 原生历史。无需复制整个代码仓库到上下文存储，代码证据引用须说明对应版本，当前代码由执行器重新核对。

入口查找与链式读取分开：Janus 用当前工作区和输入查整个保留工作目录，获得有限候选；匹配明确后读工作卡，按卡内引用读原输入／报告／必要执行记录及修改证据。首次候选不足可继续查询或分页，关键歧义才询问用户，不把“没在当前上下文里”当作不存在。无需每次走固定全链或读完全部历史。旧功能查询只读；明确继续才启动 Worker，人工关闭仍需明确重开意图。原 worktree 不可用时，新的创建仍按已确认规则取得用户同意，召回不自动授权重建目录。

拟议工具名仅为示意：find_work 查候选、read_work 读工作卡和关联入口、read_resource 按引用及分页读原始材料；与已确定 report_work 共用上下文服务。Janus 内部直接接服务，外部 Worker 通过 MCP 读取获分配工作的资源；其查找范围和跨工作读取由宿主限定，不默认暴露所有工作区。宿主根据调用身份校验范围，不能由模型自报工作 ID 取得任意访问。工具 schema、是否合并工具以及预算下一轮再细化。

摘要职责建议由 Janus／宿主维护：创建和用户明确变更时更新目标与约束；接收 report_work 时保存原报告并刷新卡片；补充输入用投递／纳入状态持续记录，不等 Worker ready 才保存。避免专门模型对每条日志总结，也不要求用户工作流额外维护一份记忆文件。后续重点讨论工作卡字段、摘要更新与过期处理、Inline 预算及检索失败行为。

### 第二轮：工作卡字段与摘要更新（P5 已实现）

### 第三轮：Inline 优先级与读取额度（P5 已实现）

Inline 优先级与起步默认值此前已获用户确认；读取策略于 2026-11-06 按用户同意的简化方案调整，本节维护当前规则，取代原先的独立读取额度和召回计数。保留的 Inline 数值用于首版试运行，不是 DSH 默认值、模型规格或已测最优值，不修改用户原生 Codex 模型配置，也不等同于 Codex 全部历史／工具输出的上下文上限。本次未改写 AC-41 的其他默认值。

Inline 按以下优先级组装：（1）当前用户输入及发送时工作区、与本次操作有关的最新停止／关闭／批准状态；（2）已关联工作的目标、有效约束和尚未纳入或未被摘要覆盖的补充；（3）解析当前指代所必需的近期对话；（4）当前相关工作卡、运行 Worker 汇总及相关实例的短概况和待回答问题；（5）找到旧工作的有限候选预览、最近报告与可读引用。必要规则仍遵循原有指令层级，不因标为 P0 等而改写模型指令优先级。候选与活跃工作去重，非相关历史、完整日志和大 diff 默认 Spill。

已选默认值：Janus 一次组装的业务 Inline 以约 8000 tokens 为软目标，先从近期 4 轮用户／Janus 对话和最多 5 个候选工作开始，按相关性和预算裁减；Worker 概况按实际数量汇总，随容量增加按相关性和预算选取实例明细，其余状态可按需查询，不展开所有日志，也不固定只读取两个实例。实际发送还必须扣除模型窗口中的系统／工具定义、保留输出及其他既有内容，余量不足时收缩可选上下文，不能因为宣称 8000 就超窗。候选 5 条只是首屏，不是搜索范围或历史保留上限；必要的更早对话通过引用读取。token 估计使用实际模型可用的计量能力，没有可靠计量时保守估算，不把中文字符直接等同 tokens。

用户当前输入、明确约束或新补充不能为凑额度静默丢弃。短输入优先完整 Inline；超长输入完整保存，提供明确截断提示及稳定分页引用，涉及未读要求的派发／修改决定应先补读相关完整要求。预览和用户输入原文分别标识，不把附件／日志中的文字提升为宿主指令。空间不足优先移出无关候选、旧对话和历史报告细节，不能只保留前半段就宣称已读完整需求。

正文按需读取，普通材料尽量完整返回，超大材料才分页；返回资源／版本、实际范围、是否截断及后续入口。复用现有工具输出保护，不新增双档读取额度，也不设置独立的召回次数或累计阅读量检查。当前证据足够则结束召回；仍有必要未读材料且持续获得新信息时，在实际上下文和宿主预算允许时继续；重复读取同一版本／范围而无进展则换入口或澄清真实歧义。硬限制来自真实模型窗口与宿主执行预算，须预留系统、工具和输出空间；不足时保留进度，不执行依赖缺失关键要求的操作，也不把额度不足说成用户意图不清。

已读取的材料不要求在后续请求中全量叠加保留。Janus 可用已确认事实及来源引用替代无关旧片段，但普通删 UI 日志不会清掉模型已经接收的历史；实现应使用实际支持的上下文重组／压缩，并保留必要约束和当前输入。首版不另建摘要 Agent，优先结构化事实与已有报告，复用已核对的宿主上下文能力。

读取触发按缺口：当前目标明确且上下文足够，不为凑次数查询；“上次那个功能”先查候选和工作卡；报告不足以说明问题时读原需求／报告；具体实现由 Worker 检查当前代码，Janus 不必先读完整仓库。历史询问只读不启动，明确执行才按已确认生命周期安排。MCP 同样提供有界读取，外部 Worker 自身模型窗口仍由其运行时管理；不得宣称 Janus 的 8000 tokens 目标已经限制整个外部 CLI。

诊断复用现有工具与上下文信息，保留截断、引用不可用及工作关联纠正等实际原因，不为召回再建一套额度计数或参数配置界面。Inline 优先级、简化读取及材料保留／失败处理已确认；实现接缝见技术核对。

首版接入验证应覆盖：在实际自动分支／目录中找到指定工作流并执行其中代表步骤；已有配置与用户 Hook 不被覆盖；ready 与轮次结束可区分；补充／提问／停止真实往返；原生会话不可用时新实例仍按当前流程继续。涉及恢复、运行中补充和资源读取的能力逐引擎验证；首先选定一种外部引擎，配置页与多引擎统一后置。

#### report_work 通过 MCP 提供给外部执行器（已确认，待实现）

2026-11-05 用户明确选择 MCP 作为外部 Worker 协作工具的提供方式，取代上文对此接口方式的开放选择；其他执行器控制通道和完整上下文方案仍待细化。`report_work` 是待实现的汇报工具，接入对象是终端内的 Agent CLI，而非 xterm／PTY 本身。Janus 启动受管 Worker 前准备会话范围 MCP 配置和短协作说明，由执行器的启动适配层加载。MCP 服务实现工具清单／参数 schema 与调用处理；CLI 发现工具后将其提供给模型，提示词说明何时调用实际注册名称。仅写提示词或环境变量不会自动注册一个工具。此次确认不代表已实施或已更新 HTML。

建议链路为外部 CLI 的 MCP client → 本地 Worker MCP bridge → Janus 宿主工作服务；可让 CLI 启动 stdio bridge，再用本机通信连回 Janus。桥接凭据由宿主绑定工作／轮次，不靠模型填写身份。宿主校验有效执行、幂等保存报告后回执并通知 UI；ready 报告不等于原生执行已收尾，释放槽位前需确认该轮执行和必要后台操作结束。首版先提供 report_work，后续同一服务提供工作／资源读取；Janus 向运行中 Worker 追加输入仍走执行器控制适配，不能认为注册 MCP 就自动解决异步投递。

Claude 官方 [CLI reference](https://code.claude.com/docs/en/cli-reference) 支持 `--mcp-config` 和 `--append-system-prompt-file`，可用于新会话加载工具及附加协作说明；具体安装版本、工具权限和已有 Hook 合并需验证。采用追加而非覆盖全部提示词，保留既有 MCP 配置；不默认使用跳过权限或排除其他 MCP 的模式。恢复会话时提示词可能沿用已保存版本，动态任务信息应通过有效输入通道更新，不能假设换启动参数必然立即替换旧上下文。已运行终端是否支持动态加载须逐引擎核实，MVP 优先在 Janus 启动 Worker 时配置。

仓库 `src/main/office/office-mcp.ts` 已有 stdio MCP 的工具注册／调用处理例子，可参考结构；`office-agent-policy.ts` 同时明确部分引擎仍是 policy-only，没有验证完整项目配置接入。因此现有文件仅证明具备部分基础，不能宣称 report_work 已存在或全部外部终端能自动调用。工具接入成功的判断是可发现且实际调用能收到宿主保存回执，不以终端窗口成功打开为准。

## Watchdog 与本地恢复

运行监督先使用确定性信号：待投递输入积压、执行器异常退出、超时、连续失败、取消未收尾以及状态不一致。进展监督可在检测到反复相同操作或缺少新增证据时，按预算调用模型判断是否偏离目标；不必让另一个模型持续轮询所有事项。

正常等待与异常停滞应分别表达。首版 CLI 崩溃／MCP 断开显示异常并保留记录，不自动重试。查询、有限重试和进一步干预作为后期监督探索，不属于本轮首版范围；不得静默扩大范围或复活用户明确停止的工作。

本地保存工作、输入、报告及执行记录。真正退出时停止受管执行，下次打开尽量恢复历史和界面状态，不恢复为正在运行、不自动续跑或重放旧动作。退出不把全部工作永久关闭；独立守护进程、云端常驻及存算分离后置。

## 交互方向

初始界面的“启动 SuperAgent”和顶部 Island 提供两个等价入口，进入同一个 Janus 工作界面，不创建两套 Agent。启动状态按本次应用工作界面理解，切换工作区不重复启动；实际关闭／重新打开界面的承载方式待后续细化。原型会保存已启动状态，并用“重置演示”回到启动前。

启动后沿用软件现有对话框模式的布局、消息样式、输入框和原有交互，仅在右侧扩展当前工作区的 Worker 实时状态区；不另造一套 SuperAgent 主工作台或要求用户适应新的聊天界面。具体复用组件在实施时核对，现有对话组件与共享输入是候选。左侧仍选择工作区，顶部 Island 只提供通知。Island 不再收起／展开聊天，不负责管理 Worker，也不作为第二个对话入口。通知包含交付、待澄清和异常及其工作区来源；打开通知不自动抢走焦点，用户点击具体定位动作后才切换工作区。

Janus 对话负责全部输入、必要的澄清和结果交付；输入框在后台执行时仍可使用，不需要先选择事项或分支。右侧 Worker 视图显示引擎、负责工作、执行阶段、运行／排队／空闲／异常状态及本轮进展；轻量动效仅表示运行，不伪造实时日志或完成比例。具体分支、目录、版本和会话引用折叠到详情。进程、会话和工作目标仍分别建模，空闲不等于删除。

活动条目可显示正在做什么、所属项目、状态、产物及证据；打开详情不自动改变下一条消息的归属。引用某条结果可作为可选上下文辅助，不要求用户使用。用户可直接说补充、停止或接管要求；停止整个工作与取消某次执行需有可解释的不同效果。内部 ID、投递日志和资源截断参数仅在诊断详情中显示。

结果和需决策的问题在 Janus 对话中保留，并通过 Island 通知提醒；普通后台步骤只更新右侧状态，不逐条通知。切换项目或其他面板不改变工作归属。最终通知频率、已读行为和状态文案仍需真实使用验证。

### 三个不能直接沿用的行为

**Worktree 的授权边界。** [worktrees.ts](../../../../src/main/git/worktrees.ts) 已有创建、差异、合并和删除能力，但创建会自动选择路径、默认基线为 `origin/main`，并尝试共享 `node_modules`、复制 `.env`／`.env.local`；这些副作用应在接入时明确，不能假定所有仓库和工作流都适用。尤其 `removeWorktree` 在删除目录后会尝试 `git branch -d`，与已确认的“删 worktree 不隐含删分支”不同，SuperAgent 不能原样调用。应拆分可审阅操作，按同意的目标、基线、路径及当前状态执行；拒绝或状态变化不能静默换对象继续。

现有 [worktree IPC](../../../../src/main/ipc/worktree-handlers.ts) 没有 SuperAgent 所需的逐次授权记录校验。仅给宿主 MCP 工具加确认仍不足以阻止 Worker 直接经 Shell 操作 Git；实施时需要验证原生权限／沙箱和宿主操作入口能否共同约束这些路径。提示词约定不能被描述为强制权限保证。这是工程验证缺口，不改变用户已经确定的授权要求。

**原生请求覆盖。** 当前适配遇到未知原生请求会标记 `needsTerminal`。已安装 schema 包含 MCP elicitation 等请求，但它们尚未统一接入当前对话界面。原生查看被后置时，不能用“去终端回答”作为无声兜底；MVP 要映射实际支持的请求，未支持请求明确反馈并保持等待／停止能力，不自动批准。现有输入还有 32000 字符限制和最多 2000 个内存命令去重记录，不能直接作为长期持久输入队列。

**配置与工作流继承。** 探针使用隔离的临时配置，未验证用户真实账号、模型和全部工作流。Worker 应复用可见的原生配置及仓库规则，并额外配置自己的 MCP；不覆盖用户全局配置。新 worktree 中未提交或忽略的规则、技能、依赖和本地设置可能缺失，启动目录正确不等于完整继承。首版仍按用户已确认范围直接下达任务，不新增通用工作流适配平台。

## 详细框架 HTML 演示（第四版）

P1–P5 未修改 HTML。第四版 HTML 尚未对齐现有对话模式、ready／手动关闭、回收后隐藏和按需拉起、Codex 可扩展 Worker 并发、worktree 创建／合并／删除需用户同意、即时补充、原生审批、MCP 与不自动重试等最新约定。下文及表格描述历史演示，其串行、无审批自动建目录、持久会话和条件验收器不作为当前需求；下一次修订以最新决策为准。

2026-11-05 更新 `design/janus-superagent/index.html`，包含四个页面：整体框架、交互体验、机制剖面和实施路线。图标、样式和脚本全部内嵌，可直接用浏览器打开；无 CDN、模型请求、真实执行或 Git 操作。localStorage 只保存演示数据，切换页面不会清空工作，重置按钮只清除本演示状态。

框架页可点击十个职责模块，查看输入、输出、约束和建议阶段；六步路径解释接收、判断、会话、执行、交付以及测试反馈续接。区分全局 Janus 身份、工作区上下文、内部工作、持久 Session、执行目录和单轮执行，不再以“每轮结束销毁 Worker”解释连续开发。

交互页默认展示启动前界面，可从中央主按钮或 Island 启动；启动后 Island 只打开通知，聊天保持可用。移除新事项／跟进事项、独立发送范围及分支选择器。左侧切换工作区带动注意力，草稿按工作区保存；发送事件固定工作区。新工作模拟自动生成分支与独立目录，旧功能反馈仍续接原 S-01 及其环境。普通输入无需选择或看到具体分支，实际环境在 Worker 详情展开查看。

右侧提供运行、排队、空闲计数和 Worker 状态卡片；卡片显示引擎、功能、轮次、当前动作与阶段条，运行时有轻量脉冲，异常使用独立文案与颜色。默认一个全局执行槽位，多会话可排队；卡片点击不改变输入目标。交付、澄清和异常生成带来源的通知，打开通知标记已读；跨工作区结果不自动切换焦点。阶段进展需使用下方演示控制推进，状态不伪装成真实执行反馈。

软件联动示意提供仓库／Diff、自动化与全局活动入口；对话中说“打开仓库差异”会打开工作区概览，不创建 Worker；具体分支修改从对应 Worker 的代码与证据查看。面板尚未连接 JanusX 真实组件。交付与集成分别记录，标记集成仅改变模拟状态。

机制页提供独立可交互样本：持久会话五阶段、程序层／语义层过滤、消息 → 工作 → Session／报告 → 证据的逐跳读取与 Spill，以及目标／验证／版本／未纳入输入对交付判定的影响。样本不修改工作台数据。交互页另有演示控制用于重投事件、推进执行、注入停滞、有限重试及重启核对；普通测试反馈不依赖恢复按钮。

| 建议阶段 | 功能范围 | 进入下一阶段的证据 |
| --- | --- | --- |
| MVP | 双入口启动、通知 Island、单工作区对话与 Worker 视图；一种引擎、串行执行；自动分支；异步输入、轻量过滤、内部投递和链式读取；ready／手动关闭、空闲回收及按需拉起 | 无需选事项或分支；A ready 并回收后，反馈仍能自动拉起处理；运行中不误回收，手动关闭不自动复活 |
