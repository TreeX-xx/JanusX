# Janus SuperAgent 一期 MVP 实施计划

## Intent

把已确认的 SuperAgent 设计实现到 JanusX 产品中：用户仍只和 Janus 对话，由 Janus 理解工作、按可配置容量安排 Codex Worker（首版默认并发数为 2），支持运行中补充、停止、汇报、长期工作记录与后续继续。主界面沿用现有聊天，右侧展示真实 Worker 状态，初始界面和 Island 提供同一启动入口。

本计划承接[需求与固定 AC](../requirements/janus-superagent.md)和[设计及技术核对](./janus-superagent.md)。基础技术核对已经完成，P1–P8 均属于一期 MVP 的产品开发与交付步骤。2026-11-06 按用户授权以 xdo 实现 P1–P7，并开展 P8 联合验证；实际接口与证据见下方记录及[验收证据](../superagent-verification.md)。Main Agent 直接实施，未创建正式 Task、启动并行 Agent 或发布代码。

## 一期交付边界

一期在一个明确工作区内完成多项工作的协作闭环。所有工作、输入、执行和结果从第一步就携带固定工作区身份；浏览位置变化不能迁移既有工作或改写已发送消息。保留 Janus 现有软件全局操作能力，不把全部对话强制转为开发工作；跨工作区自动分派和完整多工作区体验留到后续。

| 一期必须交付 | 约束 |
| --- | --- |
| 唯一 Janus 对话入口与异步输入 | 无需选择事项／Worker／分支；运行中的开发不占住聊天入口 |
| 两级过滤和工作归属 | 宿主处理身份、持久化与确定性事件；同一个 Janus 理解意图，不新增分类 Agent |
| Codex 外部执行与 MCP | 使用受管 Codex App Server；MCP 提供汇报和必要工作／材料读取，保留可用的原生配置 |
| 可扩展 Worker 调度 | 并发上限 N 可配置，首版默认 2，后续可增加数量；满额排队，同一工作一次只允许一个有效执行，不让不同分支共享活跃检出目录 |
| 即时补充、停止与原生决策 | 按真实原生能力投递、显示和回答；收到、送达、纳入及完成分开，不自动代批 |
| Janus 管理分支／worktree | 优先复用；创建、合并、删除需针对具体操作取得同意，删 worktree 不隐含删分支 |
| Inline／Spill、工作卡、链式召回 | 一期全部实现；工作历史可查，关键原文可按引用读回，候选首屏不等于全部历史 |
| ready、回收与再次继续 | ready 且执行收尾后空闲 30 分钟回收实例；相关明确执行输入可续用或再拉起，已关闭工作须明确重开 |
| 保存、退出与异常反馈 | 核心记录不自动过期；退出保存并停止受管执行，重开只恢复记录，CLI／MCP 故障不自动重试 |
| 现有聊天加右侧状态 | 双启动入口、启动后仅通知 Island、原生批准／问题回传、真实状态与结果 |

一期不纳入 Claude Code 等多引擎设置、原生终端查看／接管、PR／Issue／IM 来源、主动定时开发、自动 PR 或自动合并、云端常驻、存算分离和模型式进展监督。不新增工作流选择平台、专门验收流程或独立质量评审 Agent。现有仓库／Diff 能力继续复用；自动化和未来外部来源预留事件接缝，不在一期提前建设接入平台。

## 实现组织与基本契约

建议以宿主侧的一个 SuperAgent 协调模块为中心，内部拆分记录、输入／调度、上下文与执行器职责，不引入微服务或第二套 Agent 运行时。Janus 继续使用既有模型、工具和压缩端口；执行器负责开发，宿主负责事实与授权，界面只提交操作和订阅状态。

```mermaid
flowchart LR
  UI[现有 Janus 对话] --> IN[保存输入与确定性处理]
  IN --> J[Janus 理解与工作归属]
  J --> HOST[宿主复核与调度]
  HOST --> W[外部 Codex Worker]
  W --> MCP[MCP 汇报与读取]
  MCP --> DATA[工作记录与原文资源]
  DATA --> J
  HOST --> DATA
  DATA --> VIEW[对话结果／右侧状态／通知]
```

以下为首版最小逻辑对象，不要求分别建成服务或一张表：

| 对象 | 需要保存的信息 |
| --- | --- |
| 工作 | 稳定 workId、workspaceId、目标／有效约束及来源、版本、关闭标记、环境引用、最新报告与执行引用 |
| 输入与派发 | eventId／inputId、来源、原文引用、发送时工作区、关联结果、顺序、待投递／已送达／已确认纳入或未知、取消原因 |
| 执行与实例 | executionId、实例代次、providerSessionId、原生 turnId、cwd、执行状态、待原生请求、已知后台活动与进程归属 |
| 报告与材料 | reportId、来源执行、报告类别与摘要、输入覆盖信息／未知标记、资源身份与版本、内容及关联 |
| 环境与批准 | 仓库／worktree／分支／基线身份、占用工作、具体操作及目标、批准结果和有效范围 |

工作记录、原生会话和活进程分别管理。用户看到简单状态；内部必须区分执行中、等待决策、正在停止、ready 空闲和异常，才能兑现停止／回收规则。ready 是 Worker 的明确报告，不能由无输出、原生轮次结束或进程退出推断。后到的补充会使旧 ready 不再覆盖当前要求，报告保存不引入测试质量门槛。

所有副作用在落地前再次核对工作区、工作版本、关闭状态和有效执行。旧模型决定、旧实例消息、重复批准以及迟到 ready 不得重开工作或覆盖新执行。输入去重按事件身份，同样文本的新输入仍接收；投递结果不明时保留未知，首版不通过自动重发来猜测结果。

## 开发步骤与完成标准

下列完成标准是开发者验证产品机制的依据，不是在产品中增加用户验收环节。各步骤均提交实际代码、对应的必要测试与 Note 更新；不会只交脚本或演示即认定完成。

### P1：工作记录与输入主干

**开发内容。** 定义共享类型和 IPC 契约，建立独立的工作／输入／执行／报告存储与原文资源目录，复用现有原子写入和损坏保护思路。接入宿主输入入口：先保存并固定工作区、返回收到回执，再处理事件；按 eventId 去重，保存关联结果和待派发动作。搭建对外快照／事件接口，为聊天和右侧状态提供同一事实来源。

开工时先在当前工作副本建立与锁文件及仓库脚本一致的开发／测试环境，记录依赖基线，保留用户配置和其他未提交改动。上轮临时借用依赖完成的技术核对不替代产品实现环境；不为准备阶段修改用户的 Codex 全局配置或擅自新增 worktree。

把核心记录和大体积原生日志分开，核心记录不自动过期。P1 只保存输入与正式报告正文，不接收 CLI 原始日志；P3 接入真实执行流时落实独立日志上限、截断提示及可读范围，不能让日志轮转删除原始用户要求或报告。存储版本升级需有版本标识，写入失败不能回复保存成功；损坏时保留原文件并明确反馈。不要沿用外部会话索引的 200／50 裁剪策略作为工作记忆。

**交付与检查。** 输入重投不重复建立工作／副作用，原待处理事件仍可追踪；工作区切换不改写输入归属。重开应用能读回原文和结果，但不会消费旧队列自动执行。断电／写入失败夹具不会把部分写入伪装成成功。完成此步后，后续开发都使用真实持久记录。

**前置：** 已有技术核对。**主要 AC：** 4、8 的记录部分、22、30、32、43。

已实现宿主持久记录与输入 API。聊天循环接入归 P4，Worker／MCP 归 P3，右侧界面与双启动入口归 P7；当前提交输入只落盘并回执，不产生模型、进程或 Git 操作。

| 已实现模块 | 职责 |
| --- | --- |
| [共享记录](../../../../src/shared/superagent.ts)、[IPC 契约](../../../../src/shared/ipc/superagent.ts) | 工作、输入、逐工作投递、执行身份、报告、原文引用及变更事件 |
| [schema](../../../../src/main/janus/superagent/schema.ts) | 格式版本、身份唯一性、跨记录引用和工作区归属校验 |
| [persistence](../../../../src/main/janus/superagent/persistence.ts) | 原子文件写入、原文资源、哈希完整性检查及损坏保护 |
| [store](../../../../src/main/janus/superagent/store.ts) | 单宿主串行提交、幂等接收／关联／汇报、历史查询与提交后事件 |
| [service](../../../../src/main/janus/superagent/service.ts)、[IPC handlers](../../../../src/main/ipc/superagent-handlers.ts) | 从已登记工作区解析路径；向允许的主窗口暴露输入／查询，通过 preload 订阅状态 |

运行数据位于 Electron `userData/janusx/superagent/`：`records.json` 为 version 1 元数据索引，`resources/<UUID>.txt` 保存完整输入或报告。正文先写入并同步文件，再原子替换索引，最后返回回执／发布事件。固定 eventId、会话、工作区和正文后重投会返回原输入；同文本的新 eventId 仍接收。一条输入可关联多个工作，每个关联独立保存 pending／delivered／incorporated／unknown／cancelled；这些是宿主证据，不由 UI 或模型自行宣称。

创建工作及输入关联在同一次提交完成；执行身份变更校验工作 revision，旧执行报告保留为历史，不替代新执行的当前报告；报告本身不证明全部补充已纳入。运行实例与执行身份记录分离，读取历史不拉起进程或消费队列。退出接入现有 AppShutdown，拒绝新写入并排空已入队提交，仍遵循应用既有退出超时。renderer 只能提交输入和按工作区查询，不能直接伪造执行／报告／投递结果。

存储取舍：首版用一个宿主写入队列和一个完整元数据索引，避免增加数据库、独立锁服务或读取额度配置；正文分离，核心记录无自动过期或条数裁剪。代价是元数据内存和重写成本随历史增长；若实测出现明显延迟，再迁移索引实现，保留外部契约。失败可能留下未被索引引用的正文，当前保留而不自动删除；损坏／未来版本索引拒绝读写并保留原文件，正文缺失或哈希不符明确报错，不生成虚构内容。

本地环境采用 Node 24.15.0、npm 11.12.1，按现有锁文件运行 `npm ci --ignore-scripts --no-audit --no-fund`。未修改依赖声明、锁文件或全局 Codex 配置。机器验证：P1 三组测试及 AppShutdown、既有 Janus IPC／聊天存储共 50 项通过；覆盖长原文、并发去重、205 条以上历史保留、工作区隔离、错误身份、迟到报告、资源／索引写入失败、提交结果不明后的显式重投、损坏及退出排空。命令为 `npm run test:unit -- tests/unit/superagent-store.test.ts tests/unit/superagent-persistence.test.ts tests/unit/superagent-ipc.test.ts tests/unit/app-shutdown.test.ts tests/unit/janus-ipc-contract.test.ts tests/unit/janus-chat-store.test.ts`。另执行 `npm run typecheck`、改动源码定向 ESLint、`npm run build:check` 与 `npm run check:notes`。

上述测试、类型检查、定向 ESLint、应用构建及 Note 校验均通过。Note 校验为 329 篇、0 errors，另有 17 项既有跨仓库链接诊断；测试与构建日志保存在忽略目录 `artifacts/superagent-p1-*.log`，本节保存长期验证结论。

验证边界：故障由文件夹具和注入写入错误模拟，未做真实断电或桌面 E2E；P1 不启动真实 Codex。当前资源 API 返回完整正文，超大材料分页与模型窗口保护在 P5 接入；CLI 原始日志尚无写入入口，不能将其表述为已有日志归档／轮转能力。上述证据只完成 P1，不据此勾选依赖后续执行、UI 或恢复行为的完整 AC。

### P2：受控工作环境与 Git 操作

**开发内容。** 建立工作到环境的绑定，复用前核对仓库、路径、分支、占用及未提交修改；不同分支的并发工作使用不同 worktree。Janus 根据明确目标规划基线与分支，用户不必手动切分支，但创建前展示实际操作和目标。合并与删除使用同一宿主批准入口，执行时核对批准对象及关键状态；目标实质变化则重新确认，不暗中换路径／分支。

为现有 worktree API 增加可明确选择的操作边界，SuperAgent 删除 worktree 时保留分支，删除分支须另有授权。既有手动入口的兼容性单独检查，不通过改一个共享默认值无意改变全部路径。创建的默认基线、依赖共享和配置复制也要显式决定；不盲用 origin/main，不自动复制所有未跟踪文件。依赖或规则缺失按已确认方式交用户处理。

落实 Worker Git 管理操作的权限约束，并用真实命令检查 Shell 路径是否能绕过。方案优先让管理操作由宿主在批准后执行，Worker 的可写范围与该工作环境一致；仅有 MCP 确认、提示词或命令包装器不能宣称满足强制约束。该边界是一期关键交付条件，如果本机原生策略不足，需报告具体限制及可选实现，不能默认为已满足；其他独立开发可继续。

**交付与检查。** 在临时测试仓库中，批准、拒绝、过期／目标变化均产生正确结果；未授权不建／合并／删 worktree，删目录不顺带删分支，复用不覆盖已有修改。检查重复批准和并发环境分配，不让不同活跃工作误用同一目录。用户仓库的实际操作仍逐次征得同意。

**前置：** P1。**主要 AC：** 9、19、20 的环境部分、25。

### P3：单个 Codex Worker 的产品闭环

## 依赖顺序与阶段交付

主顺序为 **P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8**。这表示交付依赖，不要求所有 UI 骨架都等后端完成；P3 即使用现有对话查看真实结果，P4 即提供基本运行反馈，P7 收齐完整交互。默认由 Main Agent 顺序实施，未授权并行子 Agent。

| P5 完成 | 从目录和带来源的工作卡召回历史，长原文按版本续读，未覆盖补充保持可见 | 30 分钟回收、完整恢复与最终 UI 仍待后续交付 |
