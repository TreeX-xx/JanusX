# Janus SuperAgent：开发者直接输入与多事项修复

## Expected behavior

[官方实验插件决策](../superagent-plugin.md)确定 SuperAgent 可选安装、默认关闭。以下编排行为适用于用户启用插件后。

用户希望 Janus 保持控制软件全局的中心，参考 Super-agent 的机制建立持续协调与执行能力，并设计相应交互；Router 是 Janus 的一项职责。首版输入来自开发者直接向 Janus 提出问题，由 Router 关联项目、分发修复并汇总结果。用户无需在多个 Agent 会话之间手动搬运上下文。

用户明确 SuperAgent 就是 Janus，支持异步输入，不需要用户选择或跟进事项。后台执行期间，用户仍直接向同一个 Janus 发送新问题、补充、状态询问和停止要求；Janus 负责理解归属，关键歧义在对话中澄清。进展视图是可选观察入口，打开详情不应隐式改变消息发送目标。应与原生仓库、自动化等能力联动，后期可读取 Issue／PR 推进工作。首个外部 Worker 引擎确定为 Codex；并发容量可配置，首版默认值为 2，后续可增加 Worker 数量。

MVP 先在一个明确工作区内处理多个工作目标，由可扩展调度机制按配置的并发上限 N 安排 Codex Worker，超出容量排队。2026-11-06 用户明确容量不能写死为两个；2 仅保留为首版默认值，记录、调度、上下文及界面从一期起支持可变数量，后续增加容量无需重写核心机制。支持异步输入、自然语言补充归属和必要澄清；多工作区与跨项目归属增强另行分期，PR／IM 仍非首版依赖。第四版 HTML 尚未对齐最新并发、目录、回收和即时补充决策，原型仅模拟设计，不代表真实能力验收。

2026-11-05 已明确的范围修正：“输入信息”指开发者直接输入，不是 PR 信息流。文中的 IM 指即时通讯渠道；Janus 对话窗口承担首版输入入口，无需先接飞书等 IM 或 GitHub PR。此前“PR 优先接入”的讨论已被此范围替代。

2026-11-06 已按 xdo 实现 P1 持久记录、原文资源、宿主输入与查询／事件接口；模块划分、测试和边界见[一期 MVP 实施计划的 P1 交付记录](../ideas/janus-superagent-mvp-plan.md#p1-交付记录2026-11-06)。它覆盖 AC-4、8、22、30、32、43 的记录层部分；执行及 UI 的后续进度见下文，完整条款按全链路验收。Main Agent 直接实施，未新建正式 Task；设计依据仍归[设计思路](../ideas/janus-superagent.md)。

同日按后续 xdo 授权实现 P2 的工作环境绑定、持久 Git 操作批准及原生权限策略，覆盖 AC-9、19、20、25 的后端部分。真实临时 Git 和本机 Codex MXC 权限检查通过，详细限制与 117 项回归证据见[环境决策](../superagent-environments.md)。P3 已在此基础上接入真实受管 Worker、实时停止、宿主提交和必要批准界面，完整交互归 P7。

P3 的现有聊天闭环已交付，涵盖 AC-1 的执行链路及 AC-6、13、18、33–36 的相关机制，见[Worker 决策](../superagent-workers.md)。P4 已接入正常 Janus 对话、确定性宿主接收、工作目录／简单卡片、自然分派工具、默认 2 的可配置容量、有序队列和独立控制，实际验证归[调度决策](../superagent-scheduling.md)。P5 已实现共享工作卡、来源覆盖、Inline／Spill 和原文续读保护，覆盖 AC-5、16 背景、20、23、39–44 的相关机制，实际边界与验证见[上下文决策](../superagent-context.md)。P6 已实现 30 分钟实例回收、原线程继续／明确缺失时重建、停止全部及应用恢复，覆盖 AC-7、8、16、21、35、37、38、43 的相关机制，实际边界见[生命周期决策](../superagent-lifecycle.md)。P7 已交付[可折叠 Worker、终端分屏及通知联动](../superagent-interface.md)，P8 的完整回归、真实模型检查与各条款证据归[验收记录](../superagent-verification.md)。

2026-11-09 用户要求 Agent 循环控制由代码内置，不再提供用户轮数设置，并参考 Codex CLI 的生命周期、上下文和故障处理。该要求针对当前 agentMaxSteps／40 轮机制，不取消 Worker 引擎、模型、推理强度和并发容量的既有配置需求；具体内置策略待设计。真实分派故障、共享运行时边界及未决项归[可靠性讨论](../ideas/superagent-harness-reliability.md)，本段记录需求而非实施完成，不改写既有固定 AC。

## 连续输入与临时并行

2026-11-11 用户明确要求连续输入具备 Codex CLI 式的本轮纠偏效果，并在分析后授权实施。只有一个活动回答时，补充直接参与当前思考和后续输出，不等整轮完成；显式独立提问才临时分叉，替代早期每次成卡、相关输入串行排队的要求。原文和接收状态可见，停止独立控制，结果不明不自动重放。SuperAgent 仍负责分析和协调，编辑由 Worker 执行；右侧 Worker 卡片保留终端／引擎类型、当前工作、展开／关闭及折叠时异常提示。现行机制见[界面决策](../superagent-interface.md)，早期探索见[多输入对话卡片](../ideas/superagent-conversation-cards.md)。

## 机制范围与分期

- 2026-11-09 用户提出后续停止维护独立 janus-cli，专心开发服务 JanusX 的 janus-superAgent。Agent 引擎继续由 janus-agentX 独立仓库管理，JanusX 中尚未抽离的协调与执行能力逐项迁入，JanusX 负责桌面壳体和宿主交互；具体迁移范围待细化，当前代码尚未迁移或删除。
- Janus 是统一协作入口，承担问题理解、事项归属、分派及结果交付。简单问答无需强制分派。
- Worker 在隔离执行上下文中调查、修复和验证。工作记录保持稳定身份；ready 后的空闲实例可按时间回收，相关输入到来时自动再拉起，必要时用保留记录重建上下文。
- 2026-11-07 用户明确当前不允许 Worker 再委托：不得创建子 Agent、另启执行器分派工作，或自行将工作转交其他 Worker；执行分派仍由 Janus 统一管理。
- 后续允许增加相关讨论的订阅，作为 Worker 获取关联上下文的能力；这是已认可但尚未实施的方向，不等同于允许再委托、自动移交工作或自动编排跨工作依赖。
- 执行期间，开发者可提出其他问题、补充已有事项、询问状态或停止工作；Router 继续响应。
- 参考订阅机制建立事项输入与执行结果的持续投递关系；首版只需内部消息，不要求外部事件源。
- 引入 Inline／Spill：必要上下文直接提供，完整日志、历史和证据按稳定引用读取。
- MVP 提供明确失败反馈；三期增强 Watchdog，监督异常和执行进展。运行监督与模型判断的具体边界待设计。
- MVP 保存工作、输入和结果记录；下次打开尽量恢复可用历史与界面状态，不恢复为仍在运行，不自动重放旧执行。CLI 崩溃和 MCP 断开首版不自动重试。

PR／IM 接入、Webhook、外部平台自动回复、自动创建或合并 PR、定时主动发现问题、云端常驻、跨设备执行及存算分离均不作为首版验收依赖。后续来源应能复用内部事件与事项契约。

## 代表交互与约束

2026-11-06 用户在 P7、P8 实施授权中补充：界面不参考离线 HTML；右侧 Worker 面板支持展开收起，并遵守既有分屏规则，用户仍可唤出和操作普通终端。本要求细化 AC-26、AC-28，不改变其固定编号或其余验收义务；界面决定见[分屏与通知](../superagent-interface.md)。

用户明确要求两个启动入口：初始界面与 Island 均可启动 SuperAgent，进入同一个 Janus 工作界面。启动后顶部 Island 只承担通知功能，不再用来切换聊天显示或建立另一个会话。交付、必要澄清与异常通知保留工作区来源，普通进度放在右侧；打开通知不自动切走当前工作区，明确点击定位后才导航。

工作区是用户日常交互单位，用户不必在主界面手动切分支。Janus 规划和管理 worktree，安排 Worker 在对应目录／分支开发；优先复用已有环境，新建 worktree、合并分支和删除 worktree 必须经用户同意。右侧展示尚存 Worker 的真实状态，回收后不显示但保留历史和代码环境；卡片选择不改变输入目标，原生查看入口后置。

用户进一步明确主面板沿用目前对话框模式的样式与交互，只增加右侧实时 Worker 展示，不重新设计一套主工作台。启动入口与通知 Island 的约定继续保留。第四版 HTML 尚未按此新增约束对齐具体对话样式，本轮仅维护讨论记录。

2026-11-12 用户进一步要求支持 Claude Code 和 Codex，并明确选择 Windows 原生 Claude Code、沿用原生权限与用户审批。实现边界和验证记录见 [受管 Worker](../superagent-workers.md)，保留已有工作引擎，不因默认设置变化迁移会话。以下首版范围作为历史保留。

Worker 使用外部 CLI／终端执行器，首版确定 Codex，并发上限由统一配置提供，默认 2；后续 Claude Code 等多引擎及其配置界面后置，不要求每次选择执行器。复用原生配置。框架首版只负责直接下达任务，用户自行适配工作流，不建设工作流选择与编排机制；最多考虑 WorkflowX 适配，具体适配不作为本次新增必需范围。

MVP 中开发者提出登录修复要求，执行期间补充“只在刷新后出现”，Janus 自动关联并立即转发给对应 Worker；再提出独立目标时，有容量则启动第二个 Worker，满额才排队。用户叫停即发起停止，不等当前任务完成。依赖问题出现时向用户确认，不自动推导跨工作依赖或集成方案；目标有关键歧义时简短澄清。

Janus 对话承担输入、澄清与结果交付，不新增待验收流程。审批与选项请求按执行器原生内容传回用户，保留请求身份并将用户决定返回原请求，不由 Janus 代选。等待回答时各 Worker 的可继续行为遵循原生执行器，不全局暂停其他 Worker，也不绕过原生审批阻塞。

用户提出左侧工作区切换自动改变同一个 Janus 的前台注意力：新消息默认使用当前工作区，分别维护工作区上下文和 Worker 执行记录，无需另选发送范围或跟进事项。这是当前交互方向，待原型验证；替代此前将浏览与发送范围分开选择的方案。

切换工作区不迁移既有工作，也不改写已经提交但尚未处理的消息归属；输入在发送时绑定工作区。补充由 Janus 依据该工作区对话、工作摘要及消息内容关联，明确跨项目表达或引用可提供其他归属线索，关键歧义才澄清。后台结果保留原工作区归属，不因完成通知而抢走前台焦点。用户停止后，迟到事件与 Watchdog 不得重新启动该工作。

各工作区独立管理上下文和执行记录，Worker 按需启动，不要求一工作区固定常驻一个进程。全局软件控制和状态概览仍由同一 Janus 提供。首版调度按可配置容量执行，默认并发数为 2；跨工作区调度仍后置。

运行中补充要求立即转发并通过原生运行中输入能力纳入，不把“等当前任务完成再发”作为默认方案；叫停立即请求中断，界面按原生回执显示实际状态。已收到、已转发／纳入与已完成仍需区分，不能声称能撤销已经发生的写入。具体原生安全点和停止边界在接入时验证，能力不足须明确暴露，不能静默改成下一轮执行。

用户已将“不建独立目录”修正为由 Janus 管理 worktree，以承载多个 Worker 的不同分支并发。目录归属工作而非短期实例，补充或再拉起不默认新建；不同活跃工作不得被错误绑定到同一共享检出环境。框架不强制创建 Task 或增加验收工作流，依赖问题仍交用户确认。

2026-11-09 用户明确已有合适工作树或指定目录时不应默认新建，并要求解决 Worker 权限和信任目录阻塞。路由保存目录／分支及已有改动承接意图，查找并复用已有工作树；目录信任在工作卡中完成原生确认，权限请求允许确认本轮范围，标签／推送经宿主能力执行。具体行为和验证归[环境决策](../superagent-environments.md)与[Worker 决策](../superagent-workers.md)，本补充不重写已有验收项。

## 长期开发连续性

用户最新要求简化为 ready 与明确关闭，并允许 Worker 按时间消散、涉及相关工作时再拉起。这替代此前普通反馈必须续接原 Worker、MVP 不设 TTL 的方向。ready 后释放槽位，空闲达到阈值可回收实例；后续相关输入由 Janus 自动拉起，能继续原生会话则继续，否则利用工作记录、摘要和当前代码建立上下文。用户不操作恢复流程，也不要求始终保持原 Session ID。

用户已接受首版 ready 且执行收尾后空闲 30 分钟回收。运行中、等待原生审批／回答、有待处理输入或未结束后台操作时不回收；新执行输入退出计时，下一次 ready 收尾重新计时，查看卡片与历史查询不重置。回收前确保必要记录保存，只结束实例并移除卡片，保留 worktree、分支、代码、会话引用和历史。

收起侧栏或离开 Janus 面板仅影响显示，Worker 继续。卡片“关闭此工作”停止该工作、取消待执行派发并禁止普通事件自动续开，保留记录；明确继续意图可重新开启。“停止全部”作为明确的全局对话操作，首版不必另设按钮。真正退出 JanusX 时保存状态并停止受管执行，重开只恢复记录、不自动续跑；退出不把全部工作标为用户永久关闭。停止未确认时显示正在停止或失败，不先隐藏仍运行的实例，关闭不回滚修改或删除 worktree／分支。

两级过滤的 MVP 设计已于 2026-11-05 获用户确认：宿主程序处理确定信息，同一个 Janus 理解意图，不新增专门分类模型或第三个评估 Agent。开发者新消息先保存、回执并固定发送时工作区；同一事件重投返回原状态，未完成的原事件继续处理，相同文本的新消息仍接收。明确绑定目标的 UI 操作可校验后直接执行；普通自然语言即使提及已有工作，也需区分询问和执行意图。

宿主提供可信来源与关联 ID；Worker 事件关联工作和本轮执行。普通输出保存并更新右侧状态，不逐条唤醒 Janus；ready、问题和失败按需要交付解释，不把自身通知循环当作新需求。旧实例迟到事件不得覆盖当前执行或复活用户关闭的工作。

Janus 使用当前输入、必要近况及有限候选摘要，必要时按引用补读；语义结果包括回答、软件操作、新工作、已有工作补充／继续、关闭／明确重开和澄清。候选包含 ready、实例已回收与已关闭的历史工作；询问不自动拉起 Worker，执行意图明确后才续用或重新拉起，用户关闭需明确重开。多意图可分别处理，右侧卡片选择不决定投递目标。动作落地前由程序复核工作区、关闭状态及当前实例；异步补充按序保存并立即转发。判断或投递失败保留待处理状态，不改判新工作或声称已执行；CLI 崩溃／MCP 断开不自动重试。

## 完成标准与分支工作
