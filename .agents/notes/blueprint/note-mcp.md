# 独立 Note MCP：在现有工作流中维护和读取工程文档

## Intent

用户提出：其他人的工作流可能没有 WorkflowX，或已经很重、难以接入另一套流程；能否通过一个内置 Note 维护方法的 MCP，让 Agent 生成 Janus 能识别的结构，并按明确规则准确、高效读取。此想法承接[当前产品方向](product-direction.md)。当前已实现独立 Note MCP、共享反馈工具和支持客户端的配置导入；实际兼容性见文末，[交付计划](evolution-roadmap.md)与[实施基线](implementation-baseline.md)保留尚未完成的验收和发布边界。

## 已确认的设计要求

用户明确要求采用模块化设计：按职责组织代码、目录与文件，明确接口和依赖边界，复用已有共享能力。具体模块划分与实现方式留待后续设计，不将实现集中在单一服务文件中。

用户已明确“一键导入”指将 Note MCP 的服务配置导入对应 Agent 终端，使该终端能够调用工具。设置已提供支持客户端的导入、更新、移除和服务检测；支持差异见实际矩阵。

设置页 MCP 标题旁提供悬浮详情，鼠标悬停或键盘聚焦可查看文档定位、原文维护、审核提醒处理以及已有 WorkflowX 时的用法。详情明确说明：导入不改写工作流规则、不启动审核，基础操作不调用模型，桌面关闭仍可使用；提供完整工具不等于要求已有 WorkflowX 用户重复经 MCP 读写正文。

终端接入优先级已确认：首批完成 Claude Code、Codex、OpenCode，随后逐个验证并补齐 Janus、Pi、DSH。优先复用前三种已有的配置适配基础，但新 Note MCP 必须在每个目标终端验证实际工具调用，不能仅凭配置写入或旧知识库 MCP 测试通过宣称交付。后三种的接入能力与方式先验证，再纳入支持范围；未验证时显示真实状态。该顺序针对外部终端导入，不推迟 B2 已确认的 Janus 右侧原生反馈读取与处理闭环。

## 全局导入与项目定位

已确认采用终端全局导入：在对应终端的用户级配置中注册 Note MCP，同一种终端配置一次，供多个项目复用；切换项目不要求重新导入，不默认向各项目写入 MCP 配置文件。不同终端仍按各自配置格式接入；全局注册不要求所有终端共享同一个服务进程。

全局连接与单次调用的项目目标分开。Note 读写和反馈处理继续校验项目、工作区及当前输入版本；服务不能把 Janus 界面当前打开的项目或分支当作所有终端的目标，也不能把全局配置固定到导入时的项目。

已确认项目定位使用客户端或调用 Agent 提供的当前项目路径，MCP 核对仓库身份、工作区与实际分支后读取 Note 或建议；信息缺失或有歧义时才要求补充，不跟随 Janus 界面当前项目。不能假定 MCP 协议一定会传递终端当前目录。定位结果随调用或会话明确绑定，切换项目/工作树时重新校验；具体参数和会话绑定实现仍待细化。

## 首版能力边界（已确认）

首版包含标准读写和按固定规则读取必要上下文。Agent 负责业务理解、主体内容和修改取舍；MCP 的定位、检索与读取不额外调用 LLM，基础读写不要求配置审核模型。

| 能力 | 首版范围 |
| --- | --- |
| 定位 Note | 按身份、模块、类型或关键词查找，返回明确来源。 |
| 读取上下文 | 读取目标 Note 和所属模块入口，列出直接关联的需求、决策等，由 Agent 按需继续展开；不默认读取整个项目。 |
| 维护 Note | Agent 提供正文，共享工具校验标准结构、身份、归属、引用及写入版本。 |
| 读取与处理审核建议 | 返回已有建议摘要及是否过时，完整依据按需读取；沿用已确认的独立处理回写能力，不触发生成。 |

较长内容明确返回已读范围、未读部分与继续读取方式，不把关联列表或检索摘要当作已经读取的完整依据。已有 WorkflowX 或同等 Note 维护能力的 Agent 可继续本地读写，只经 MCP 补充建议读取与处理；没有这些能力的 Agent 可使用完整工具。两种接入复用同一套身份、版本和反馈语义，具体字段、单次返回长度与继续读取方式由实施确定，不设累计用量上限。

## 工作区工具定位（已确认）

用户明确 Note MCP 是工作区能力工具：Agent 通过 MCP 维护 Note，就是按已有权限操作自己的工作区文件。MCP 提供标准读写、上下文定位和反馈处理，不建立额外的 Janus 项目白名单、逐次审批或产品授权流程，也不要求先在桌面中登记或打开项目。用户保留已有的任务规划、开发、测试与审核流程；不要求安装 WorkflowX skills、采用 xdo/xflow、接入任务调度器或额外部署提取模型。Janus 消费同一份原始文件，MCP 不维护另一份正文。

工具遵循宿主和操作系统的既有权限，通过调用项目路径确定目标；项目定位用于找到正确文件，不是另建接入审批。格式、身份、引用与版本检查用于防止写坏 Note、覆盖并发修改或串用建议，不把语义审核通过设为写入前提。Agent 仍需按任务需要调用工具，MCP 不自行观察全部开发活动；必要的调用约定可简短说明，不扩展为另一套工作流。

普通模块、专题、想法、需求与决策应可独立读写，不为一次文档维护强制生成可执行 Task、派发或回执。任务执行与验收状态继续遵循其明确契约，不能为了接入轻量而伪造完成。

## 独立运行（已确认）

Janus 桌面关闭后，终端仍可按需启动和使用 Note MCP，继续读写自身工作区的 Note，并读取已有审核建议、回写处理结果。服务不依赖桌面组件内存、桌面在线状态或蓝图开关；基础维护与读取不以 LLM/JEV 可用为前提。

已有反馈仍读取 Janus 持久化记录，按实际文件版本标明是否过时；没有建议存储或报告时返回暂无反馈，Note 读写继续可用。处理结果持久化，桌面再次打开后读取同一份记录。多进程一致性与具体存储布局在实施时解决，不转化为用户反复批准的步骤。

自动审核继续遵循“Janus 完全退出时暂停、重新打开后按既定 Git 规则恢复”的已确认策略。外部 MCP 读取、写入或关闭提醒不启动新审核；终端启动的 MCP 服务不承担后台审核守护进程职责。M1.2 先以两个独立进程验证存储一致性，F1 再验证桌面与实际 MCP 客户端并存、退出/重开、无建议存储、报告过时及回写持久化；配置导入、更新、冲突与撤销随首批终端一并验收，不推迟到 F3。

## 与已有 WorkflowX 的关系（基本边界已确认）

用户提出：已有 WorkflowX 的 Agent 已知道如何维护和读取 Note，再通过 MCP 读取是否重复。这个顾虑成立；如果现有工作流已经提供相同的读取、校验与维护能力，增加 MCP 通道只有配置、进程和调用成本，不能仅凭使用 MCP 就声称更高效。

建议按已有能力选择接入方式。WorkflowX 提供维护方法与读取约定；共享 Note 能力负责解析、索引、写入校验等确定性行为；MCP 是其中一种工具接入方式。安装了 WorkflowX 不必然具备全部运行时工具，没有 WorkflowX 也可以通过别的工作流维护标准 Note。需要检查宿主实际提供什么，而不只按是否安装 WorkflowX 分流。

当前实现允许只调用 `note.suggestions` 与 `note.suggestions.close`，但未检测 WorkflowX 安装情况或按已有能力缩减工具。服务始终公开七个工具；初始化说明要求模块维护前、任务收尾查看建议并读取维护指南，指南还包含一般 Note 维护约定。工具描述和指南是否进入模型上下文由客户端决定，不能声称零额外提示或调用成本。建议读取支持 `noteId` 和 `moduleId` 筛选；后者包含模块自身及直属归属 Note，不递归读取子模块。不指定 `noteId` 时默认返回摘要，按需用 `noteId` 或 `summary:false` 读取完整依据。列表默认每页 20 个目标，`limit` 范围为 1–50；用 `nextOffset` 和 `expectedRevision` 续页，版本变化必须从首页重读。已有工作流按目标模块或 Note 获取反馈，减少重复正文读取与全量输出。审核提醒存于共享 SQLite，不是额外的提醒文件；显式清理提醒不改动 Note 正文。

| 已有能力 | 推荐用法 |
| --- | --- |
| 已能按约定通过共享读取器或本地文件维护 Note | 沿用现有读取与维护路径；不要求改走 MCP，也不重复读取同一正文 |
| 已会维护 Note，只缺 Janus 审核反馈 | 使用已有宿主工具或同一 MCP 的反馈查询与处理工具，不另建产品模式 |
| 缺少标准 Note 工具，或希望统一跨宿主接入 | 提供包含维护指南和读写校验的 Note MCP，配合最少调用约定 |

已确认采用“共享能力，多种接入”的边界，复用 agentX 已有核心与宿主工具，MCP 作为适配层。相同输入应采用同一身份、来源版本、诊断与反馈语义，不各自实现一套规则。明确读取和上下文装配的收益来自共享能力本身，已有本地读取器也可以消费这些能力，不限定为 MCP 独占。

首版沿用可用宿主入口和同一 MCP，不新建 SDK、CLI、反馈文件投影或导出流程，不提供“复制给 Agent”。普通本地 Note 读取继续可用，反馈通过独立查询工具读取；模块处理前与收尾按版本查询，避免重复读正文。

## 内置反馈工具与服务数量（已确认）

用户提出是否自动内置另一个专门读取建议的 MCP，并担心冗余。建议把反馈作为独立工具模块，复用同一套 MCP 服务实现、项目绑定与结果存储。MCP 是调用协议，传递已有报告不需要启动生成模型；JEV 和建议生成发生在审核服务中，不按每个提供方新增 MCP 服务。

同一服务提供 Note 读写与反馈读取/处理工具；已有 WorkflowX 用户可以只使用反馈工具，不必重复经 MCP 读写正文。工具按职责分开不意味着首版要新增多套权限模式或单独授权界面；宿主既有只读约束仍应遵循。Agent 按已有工作区任务权限回写已处理/不采纳并清理指定当前建议，不保留历史，不再要求一次 Janus 专属审批。首版新审核和建议生成仍由左侧手动及 Git 自动审核发起，MCP 不提供生成或复核工具；读取不清理，处理也不生成审核。工具名称与版本字段仍待细化。

用户已确认右侧对话使用 Janus 原生 MCP 接入读取已有建议，并沿用授权继续调整，不设计右侧审核或建议生成触发。报告来自共用审核服务，读取不需要另启一个审核模型；无报告时返回暂无建议，不能自动补生成。原生 MCP 的反馈读取需在 B2 与左侧审核展示一起接通；已确认用该 MCP 清理建议，处理回写与关闭提醒计划同在 B2 形成闭环，不等待 B5 的独立分发与一键导入。复用同一服务实现，不另建建议 MCP 产品。

内置服务能力、给外部客户端注册连接、让 Agent 按时调用是不同环节。外部连接按宿主需要启动；桌面关闭后的 Note 读写与反馈读写已确认可用，具体自动发现、配置导入和版本更新继续细化。原生工具与独立 MCP 均已提供建议读取和显式清理；用户全局配置仅由明确的导入操作修改。

暂不建议单独开发和维护“建议 MCP”产品。它会新增配置、版本与生命周期协调，而反馈本身只需要少量查询能力；工具按职责组织，宿主按需使用，避免重复说明和工具选择负担。如果未来反馈需要不同部署位置、权限隔离或完全独立分发，再评估独立服务的实际收益。一个实现可被不同客户端启动或连接，不承诺所有宿主共享单一进程。

已有宿主反馈工具时可直接使用；否则接入同一 MCP 的反馈工具。原生闭环在 M2、外部接入在 F1 交付，不另设待讨论的“仅反馈模式”或单独建议服务。

## 接入与读取的触发方式

用户在确认 JEV 核验与生成式 LLM 维护分工后，询问有无 WorkflowX 是否都需设计 MCP 接入，以及是否必须由用户触发读取。产品设计应覆盖两类工作流：已有 Note 维护能力者可只接入反馈，缺少能力者可使用完整工具；覆盖两类不表示强制所有用户安装 MCP 或迁移已有 Note 读写。

已确认日常读取时机为处理相关模块前和任务收尾，用户也可随时要求读取。MCP 在工具说明与指南中提供简短约定，沿用已有工作流，不默认改写规则文件；服务可用不保证所有 Agent 自动调用，不主动通知或唤醒会话。

读取结果携带当前建议摘要及版本，按需展开；同一模块/版本避免重复读取正文。读取不会生成新审核，Agent 维护后显式回写处理结果，已处理或不采纳的条目清理，暂缓项继续保留。具体调用字段和去重由实施完成。

## 维护方法如何成为工具能力

指南解释应维护什么、何时更新所属文档、何时才新建主题，以及如何区分已确认内容与建议。结构化调用承接 Agent 提供的主体内容、类型和归属。共享服务负责身份、标准元数据、目录约束、引用校验、写入基线、冲突处理和可恢复提交，保存失败返回明确原因。

规则不能只藏在一篇很长的服务提示词里。必要约束要在工具参数与服务校验中落实；工具描述提供操作入口，资源/指南供按需读取，其展示和自动注入能力需按实际 MCP 客户端验证。宿主已有权限与用户授权继续有效，不另造强制审批工作流。

Agent 仍需判断哪些事实值得记录、属于哪个主题、结论是否被用户确认。服务可按显式身份和模块声明校验归属，并返回可能相关的文档；不能从自然语言自动推断所有主题关系后声称准确。把原始聊天全部交给服务再由后台模型生成 Note，会重新引入本轮希望减少的提取流水线。

## 读取的增量价值

相对直接遍历文件，增量价值来自明确的查询语义和共享索引：按选定项目与 checkout 定位稳定 URI，按模块、类型、状态、代码引用或正文检索，保留关系方向和反链，并返回真实来源与读取覆盖范围。读取按模块入口、必要父级上下文和显式关联逐步展开；相关性排序不能被视为已读取全部约束。

正文和来源 hash 必须来自同一版本；分页或按章节读取说明已返回范围、未读内容及继续读取方式。来源变化时不拼接不同版本正文；找不到、来源不可用、身份歧义、旧格式和过时快照分别报告。检索摘要用于定位，重要决定与验收依据仍需读取相应原文。

这些能力可以减少 Agent 对路径、格式、归属、关系和版本的猜测。业务含义、是否遗漏隐含条件和决策取舍仍需理解。更准确、更省 token 或更快是待验证目标：小文件直接读取可能更便宜，MCP 冷启动和索引维护也有成本；应在相同问题、相同原文下比较定位正确率、必要内容覆盖、调用次数、token 与耗时。

## 现有基础与实现边界

[共享能力归属](agentx-harness-inheritance.md)已将 Note 创建/编辑、索引、缓存、事务与撤销放在 agentX，Janus 负责产品投影。只读检查确认相邻 checkout 的 harness-node 存在 NoteService、NoteChatEditor、分页读取和版本校验；node-hosts 注册 note.list、note.read、note.write 与 note.init。独立 note-mcp 已复用这些共享工具，并扩展固定上下文和建议消费。

现有最小初始化生成项目身份与根 module Note，不写入整套工作流配置，为轻量接入提供了基础。现有列表以正文/标题/标签包含匹配并限制结果数，读取以字符分页；本提议所需的明确章节读取、丰富检索或有覆盖说明的上下文装配，不能据此宣称已经具备。

推荐 MCP 适配复用共享 Note 服务与仓库固定的标准，避免 Janus 新建另一套解析、写入和索引。服务须能独立于桌面进程运行；入口为 out/main/note-mcp.js 与 janusx-note-mcp bin；共享分页 expectedHash 在 agentX 源码实现并正常构建安装，不改写 node_modules。本文不读取或接入其他用户项目，不修改宿主工作流配置。

[蓝图内容审核](maintenance/note-content-review.md)已确定只给建议、由外部决定内容修改。建议 MCP 将已保存反馈的读取与新审核的生成分开：相关 Note 读取附带有界摘要，完整问题与依据按需获取，获授权的外部 Agent 可通过独立处理工具回写结果，清理当前条目，不建立历史库。反馈与报告版本来自同一共享服务，不依赖桌面组件内存；读取既有报告不要求模型可用，报告不可用也不阻断基础 Note 读取。建议状态、Note 删除后的自动清理和并发处理统一由[建议管理模块](maintenance/suggestions/module.md)维护；接入只做适配，工具字段由实施确定。

右侧原生 MCP 使用“读取当前建议 → 维护工作区 → 显式回写 → 清理指定条目”的流程。目标 Note 删除时由建议管理模块自动清理，无需再回写；独立进程核对来源时也执行同一规则。身份、分支、输入版本、失效、恢复和迟到结果均按模块契约处理，UI 与 MCP 不各自维护一套状态。MCP 不生成新审核，桌面关闭仍可读写当前数据。

## 当前实现与实际兼容性

服务提供 note.list/read/write/init、note.context、note.suggestions 和 note.suggestions.close，以及 janusx-note://maintenance 指南。建议查询的模块归属、摘要裁剪和分页修订保护由 tests/unit/blueprint-suggestion-query.test.ts 验证；独立 stdio 读写与清理由 tests/unit/note-mcp.test.ts 验证。摘要不替代处理前的原文依据读取。note.context 返回目标及显式模块/父模块的有界原文、关系、hash、缺失说明和续读方式；它与 note.read/write 共用一个 NoteChatEditor，成功返回的目标页可作为写前读取基线。分页续读可带 expectedHash，变化时拒绝续页并要求重读。上下文不宣称读过全部关系正文。

更新操作要求 operations 中的 uri 与成功读取返回的 expectedHash；sections 是现有二级标题到替换正文的对象，不能传整篇 markdown 或数组。同一事务为 1–16 个操作，省略未改动的章节。note.list 的 sourceHash 仅用于定位，未读取不能直接更新；服务重连后须重新读取。版本冲突不覆盖外部修改，混合新建与更新的批次失败时不部分落盘。错误返回具体参数路径，便于 Agent 修正后重试。基础规则由 agentX 共享实现，MCP 不额外放宽身份或版本检查。

已复现并修复独立上下文读者与写入读者分离造成的“已读但未授权更新”，以及维护指南要求 expectedHash 但共享 note.read 参数未暴露该字段的问题。tests/unit/note-mcp.test.ts 的 8 项通过，覆盖独立上下文更新、分页版本变化、未读更新拒绝、错误字段及修正重试、事务冲突和初始化后中文专题创建／更新。本机 OpenCode 真实进程在隔离配置和确定性模型响应下完成 list → context → write → read → suggestions，写后原文核对成功；这是传输与文件维护验证，不证明真实模型总能生成正确参数，也不能确认无日志的历史失败命中了哪条路径。验证脚本现在将未完成调用或实际未写入作为失败退出。
