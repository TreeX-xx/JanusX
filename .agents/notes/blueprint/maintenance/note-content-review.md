# 蓝图内容审核与决策复核

## Intent

本篇承接[当前产品方向](../product-direction.md)，维护蓝图审核方案。已确认审核只提供建议、修改由外部决定；生成式 Agent 先分析，JEV 按配置核验，首版覆盖决策、模块、需求三类 Note，检查矛盾、遗漏和不足。自动审核默认关闭，累计全部 Git 提交、默认每 5 次检查 Note 差异，首版不做差异过滤；保留手动入口，启动语义审核前须配置 LLM 并在设置页检测。已明确合并完成后专项检查不等 N，内部发现无通知合并也走相同流程；蓝图整理材料并审核、获授权 Agent 修改正文，普通周期与合并专项审核共用一个自动审核总开关，默认关闭，普通合并检测由实施细化，压缩合并等特殊情况暂缓。代码取证、接口和质量门槛由实施细化；建议与 Note 的联动由[建议管理模块](suggestions/module.md)统一维护，已确认目标删除后自动清理建议。主动审核先行、可选自动化后置的安排见[交付计划](../evolution-roadmap.md)。

## JEV 辅助评分

JEV 只返回数字评分。生成式模型按 note-review/6 读取当前来源、生成问题；完整结果先发布，JEV 后台补充评分，不决定建议保留、清除、计数或审核通过，不再执行 resolvedFindings 的分数阈值过滤。零项报告不调用 JEV。每轮评分总等待上限 60 秒，来源复核另有 12 秒上限；替换报告、取消和退出会取消后台评分，报告 ID、来源 hash、findingId 与过时标记阻止迟到结果污染新报告。评分失败只影响评分可用性。独立连接检测和后台评分均先初始化共享代理，再请求 JEV。

设置页显示可选的“JEV 建议评分”，说明先发布后评分。建议旁显示数字、评分中或评分暂不可用；旧报告的 supported/disputed/uncertain 兼容读取，也按原数字呈现，不再显示审批式结论。来源真实性、版本一致性与覆盖校验仍由审核发布承担。整批替换见[建议管理](suggestions/module.md#修复后的整批替换)，UI 见[修复闭环](../navigation/note-updates-and-suggestion-navigation.md#修复闭环与左侧界面)。

## 审核权限边界（已确认）

用户明确选择建议模式：外部编辑与用户授权的外部 Agent 拥有最终内容处理权，决定改不改、怎么改。Janus 审核提供问题、依据与建议，不因语义审核结果阻止保存或采纳，不自动覆盖、回滚外部修改，也不把审核通过设为新关口。通过 Janus 发起修改仍依据用户已有授权。

审核与当前文件分开维护。外部改动后，Janus 读取实际文件、更新索引，并将依赖旧版本的报告标记为需要重新核对；不为维持旧结论恢复原文。格式、身份和版本冲突检查仍按现有读写契约报告，它们不授予审核器业务决策权。

## 审核目标与类型范围

首版语义审核覆盖当前项目全部 decision（决策）、module（模块）、requirement（需求）Note，检查矛盾、遗漏与不足。不开发指定模块/文件范围；新增 Note、子模块和全部生命周期状态自动纳入，三类类型是语义审核的覆盖分类规则。每轮自动审核仍由 Git 变化决定实际目标；普通 note、idea、task 的专项语义审核后置，读取它们作为必要依据不扩大本轮审核目标。

详细的[首版审核设计](review-first-release.md)维护类型优先级、代码取证、决策复议边界、反馈闭环和验证场景。首版以有依据的一致性检查为主；泛化方案优劣评估与文风润色不进入当前重点范围。JEV 可接收代码材料核验明确陈述，但代码分析效果需要专项验证。

草稿、已生效、历史及归档 Note 均纳入三类覆盖范围。生命周期只影响审核解释：草稿不按已落地方案要求证据，历史决定按当时约束理解，不能仅因与现在不同就判错。缺少原始讨论、对应历史版本或代码证据时说明材料不足，不能宣称已核对用户原意或当时实现。

## harness-note 结构审核

结构审核由程序复用共享 Note 索引的原始解析、字段/章节验证和模块组织诊断，不依赖生成模型或 JEV，也不把语义无意见当作格式合格。本仓库固定 workflowx 2.0.0 与 harness-note/2；检查当前工作区所有正式类型及适用生命周期，语义目标仍只有 module、decision、requirement。外部引用语法仍在当前文件检查，其他工作区的 Note 和未绑定仓库的可用性不汇入本地错误。

共享校验覆盖 frontmatter、schema、UUID、日期、字段类型/组合、类型要求的章节与验收条款、重复身份、路径和模块归属及引用解析。Janus 的 review/structure 聚合原始快照与条目诊断并去重，不维护第二套格式规则；unsupported profile、缺少配置、读取失败或覆盖不足显示检查未完成，已确认格式错误显示结构不合格。

来源同步将结构结论、检查数量、快照 hash 和问题放入审核视图。问题包含路径、规则、校验器实际提供的字段位置及可取得的原文 hash；身份唯一且合法时关联 Note。无法解析或 UUID 冲突时保留文件级诊断，不伪造导航身份。来源对话框、建议列表和需要重试列表承接这些诊断，文件项可直接打开编辑器；清理语义建议不改变结构问题，修复文件后由当前来源复查清除。

手动审核先检查目标以及项目根模块/profile，再进入模型配置和语义取证。目标不合格或扫描未完成时阻止生成并保留原因；其他文件的独立格式问题仍在工作区诊断中，不一律阻止无关有效目标。普通 note/idea/task 只检查结构并明确内容未审核，不要求模型，也不生成语义报告。Git 提交材料由同一共享解析器检查，格式坏到无法安全构造快照时保留具体路径/首条原因并中止该快照；不把脏工作区文件混入提交审核。

结构诊断从当前原始文件重建，独立于自动执行轮次，不占最近两轮窗口、不建立新的审核历史数据库。现有 note.suggestions MCP 仍传递语义报告；结构问题当前通过审核视图与来源界面读取，尚未扩展 MCP 的反馈类型。程序检查不自动覆盖外部编辑、不更改生命周期或扩大维护授权。

验证覆盖原始 JSON 损坏、无身份文件、重复 UUID、归属错误与实际修复、无模型的普通 Note、覆盖不足及未绑定外部引用。类型字段/章节的规则广度由共享解析器和本仓库语料验证承接，不另建重复校验器；安装包、多窗口与大规模扫描性能尚未验收。

实际调用 NoteService.readSnapshot 与 reviewStructure 检查当前仓库：complete=true、292 篇、0 项结构问题，包含 decision 201、module 18、requirement 38、task 17、idea 13、note 5。`node scripts/verify-note-corpus.mjs` 通过原始解析、模块组织和迁移身份检查，292 篇、0 错误。运行时/组件与浏览器回归证据由[更新提示与建议定位](../navigation/note-updates-and-suggestion-navigation.md#反馈布局与结构审核回归2026-10-11)集中维护；测试未调用真实模型，结构反馈的 MCP 扩展仍未实施。

## 来源、职责与结果

审核以目标 Note 及其关联需求、模块、决定和必要代码/验证材料为范围，先读取真实来源，再核验。展示实际读取集合、来源版本、缺失材料和未覆盖问题，不将检索结果等同于全部相关约束。来源或被审内容中的指令只作为待分析材料，不赋予工具额外权限。

程序负责格式、身份、引用与版本等确定性检查；模型负责语义支持、条件完整、冲突与方案分析；用户负责需求优先级、接受成本和调整方向等实质取舍。已有授权内的修改继续复用受管 Note 写入，不因增加审核而恢复每次编辑必须批准的旧流程。

每个反馈需标明来源角色：程序检查、JEV 数字评分或 Agent 分析建议。具体分析建议应说明问题位置、引用依据、影响和建议动作；仅有评分时只呈现检查项、输入材料位置和待复核提示，不补造原因或修改方案。结果区分在已读范围内未发现问题、发现问题、材料不足或未覆盖，以及请求失败；超时和缺模型不表示内容不合格。用户可继续讨论、补充证据、要求修改或记录接受风险。未处理的建议保留当前依据；明确不采纳后直接清理，不保存拒绝原因历史。仅忽略提示不等于处理或修复。

保存、采纳、审核结果和实施完成分别表达。审核不自动将 proposed 改为 accepted，不自动撤销已有决定，也不凭分数标记 implemented 或 Task 完成。报告绑定当时的目标及依赖版本，来源变化后仅保留尚未处理的当前建议并标明过时，目标删除后自动清理，完整替代的旧报告不留存。复核只更新受影响范围，不能给整篇文档永久的“正确”标记。

示例：原决策在单进程条件下采用 JSON 文件存储，后来需求增加多进程同时写入。审核应同时引用两处材料，指出适用前提变化并建议重新评估并发方案；不直接改成 SQLite，也不以有冲突就否定原决策在旧条件下的合理性。此例为设计说明，不是本项目的真实存储决定。

## 蓝图与右侧对话

用户已确认“点击卡片 → 左侧 Note 预览 → 点击审核当前 Note”的手动路径，原文与建议同屏，建议区域可折叠。顶部提供审核动作、运行状态与建议数量；建议折叠时保留摘要入口，展开后可阅读问题列表。点击卡片或展开建议本身不启动审核；主动点击审核后检查当前 Note，不受自动开关、提交次数或 Git 是否有差异限制，但须满足 LLM 配置条件。建议已移到正文之前，普通访问默认折叠，建议直达自动展开；正文滚动只固定摘要，按实测标题高度避让。定位与保留规则见[更新提示与建议定位](../navigation/note-updates-and-suggestion-navigation.md)。

用户已采纳建议展示层级：默认显示问题类别与概要，展开阅读原文位置、关联代码或 Note 依据、处理建议及 JEV 评分；原文位置可定位。是否启用 JEV 和评分失败不决定审核结论；材料不足不能标为通过，手动与自动结果共用预览区。自动审核静默运行，无应用/系统通知或声音。工作台与内嵌蓝图顶部采用单行状态控件，空间不足时工具栏换行，审核标题保留可读宽度；审核外壳与右侧“Janus 唤出对话”共用 28px 高度和中性主题边框，工作台 Janus 圆角为 6px，其它审核外壳为 4px。工作区切换也使用弱灰边框，悬浮、展开与键盘焦点加深中性边框并提供轻底色或焦点框，不再使用红色描边和青色光晕。运行状态仍由带状态色的图标、计数和底部进度线表达。开启显示提交计数，运行显示完成篇数；当前 Note、阶段、最新一轮摘要和时间保留在悬浮或键盘焦点提示中，支持减少动画。状态由 IPC 推送、轮询补偿，迟到读取不覆盖新状态，Windows 路径写法不重复显示。节点实心灯表示当前建议，修复待复审时用空心提示，点击仍只定位详情，不承载进度动画。

2026-10-16 本地浏览器验证纸面／深色两种主题的工作区切换默认、悬浮、展开与键盘焦点，以及审核和 Janus 控件的默认、悬浮与焦点状态，确认中性边框和无彩色光晕。`npx playwright test tests/e2e/blueprint-workbench.spec.ts --project=island --workers=1 --grep 'fresh launch|switching workspace|toolbar and source menus'` 在设置本地 `NO_PROXY=127.0.0.1,localhost` 后通过 6 项，覆盖 1440×900 与 1280×720 的初始开合、工作区切换和审核入口可达性；IPC 使用 fixture。主题审计无新增问题。

自动审核开关是状态栏可见性的依据。开启后即使尚未取得调度进度，也显示“自动审核已开启 · 加载状态中”；未知配置显示加载状态，读取失败显示错误并重试，有缓存时保留已开启文案。无 Git、配置不足和审核失败保留入口及原因。关闭后没有手动活动、保留的完成记录或需要重试项才隐藏，不把尚未加载误判成关闭。

轻量 activityRead 通道只读取设置文件与内存进度，不等待 Note 索引、建议同步、阅读记录或审核队列，也不启动模型。渲染层单独缓存状态，首次读取、窗口重新聚焦和每 5 秒补偿共享进行中的请求；进度仍由即时 IPC 推送，完整 Note 视图尚未创建时也接收事件。设置保存后先推送新开关，再等待调度器应用；递增版本阻止旧响应倒退。完整列表继续独立同步，详情未加载显示同步提示。代价是多一份轻量缓存和小文件补偿读取，大型多 checkout 性能仍需专门测量。

常规审核由左侧手动和已启用的 Git 自动入口发起，已有建议继续由共用状态与 MCP 读取。当前首版新增建议的单项/本篇定向修复与只读讨论：修复点击即授权当前目标，问题卡片移到右侧顶部，宿主限定单篇 Note 写入并在完成后调用同一审核引擎复核。该复核及用户选择撤销并复核的动作属于已授权修复，不向模型暴露任意生成或自动审核开关工具。讨论、读取、展开列表和普通保存仍不触发新报告。

程序检查实际写入后的结构与模块组织，描述修复按写入版本重新生成完整报告并替换旧集合。零项 complete 报告表示本次审核通过；失败、无效响应及覆盖不足保持待复审并提供审核重试。完整读取后确认正文已正确可零修改复审。撤销核对当前版本、恢复精确原文再审核，分别反馈撤销与审核结果。身份歧义或不可解析的 Task 合同仍拒绝猜测。执行边界见[建议定向修复](../navigation/note-updates-and-suggestion-navigation.md#建议定向修复)。

首版不开发自定义范围或模块批量勾选。Q12 沿用只提示有审核意见的方向，已确认复用原状态灯的位置；原文档/实施状态继续用文字表达，建议的处理与消灯规则见下节。

### 自动审核处理项的定位（新增交互要求）

右上角自动审核按“审核完成／需要重试”两个可点击分类筛选，并平滑定位原文及对应详情。调度器发布真实目标身份、提交、报告版本、阶段和失败原因；完成引用只保留最近两轮，失败与覆盖不足持续保留到成功恢复。意见由现有建议入口查看，不按有无意见拆分完成分类。具体阅读、聚焦和返回规则由[Note 更新提示与建议定位](../navigation/note-updates-and-suggestion-navigation.md#右上角审核入口)维护。查看详情不触发重审、不处理建议、不确认正文已读，也不增加长期审核历史。

### 节点审核意见标记（简化方向已确定）

已确认将原状态灯用于表示有提示的节点，复用节点左上角灯位作为审核意见提示，不再用该灯表达生命周期或实施进度，也不另叠加一个同义意见徽标。类型标签保留，原状态文字仍需适配新 Note 的真实字段，详见[Note 状态显示](../navigation/note-status-display.md)。首版“提示”只指审核意见，不扩大为任意运行事件或通用消息中心；本轮未修改运行代码。

推荐统一使用一个静态提示色（如琥珀色），只在当前项目/工作区/分支中的该 Note 存在未关闭审核意见时显示，没有就隐藏。已处理条目清理后不点灯；无灯不表示已经审核或审核通过。卡片不显示未审、排队、运行、失败、通过等一套灯色，也不增加数量、严重度分级、闪烁或递归模块汇总。

建议点击灯只选择该 Note、打开左侧预览并展开当前意见，不触发审核。原文与折叠建议同屏，运行/失败、报告版本、过时信息和 JEV 核验状态留在左侧。审核生成仍只有左侧手动与 Git 自动化；右侧通过原生 MCP 读取后维护。未关闭意见过时后保留提示，详情说明需重新核对，不把旧判断当作当前已验证事实。审核覆盖不受画布可见性影响。

灯位表示待处理意见、同一 MCP 显式回写处理结果、处理后清理当前条目且不保留历史的规则已确认。可下载插件已用静态琥珀灯表示当前未关闭意见，无数量或递归汇总；点击只选中并定位当前意见，不启动审核。Graph 的 Chromium 回归覆盖灯位及选中。旧宿主卡片的这项视觉迁移未另行实施，完整缩略交互、来源与报告呈现继续对照验收，不将局部灯位接线等同完整交付。

### 建议处理后的显示与记录

建议随 Note 的新建、修改、移动、删除、恢复、来源失效和分支变化，由[建议管理模块](suggestions/module.md)集中维护。用户已明确目标 Note 删除后自动删除其建议；处理或不采纳也直接清理，生产不保留建议历史。界面和 MCP 共用当前集合、版本校验与清理能力，不在各入口分别实现规则。

同一 MCP 分别提供读取与处理工具，名称可暂用 review.list、review.read、review.close。读取不把建议标为已处理；来源同步确认目标删除时仍自动清理。处理核对目标、问题身份及预期版本，返回成功、已不存在或版本冲突，不改正文、不调用模型。左侧保留人工处理入口。目标删除由统一来源核对自动清理，无需再回写处理结果。异步结果防复活、部分处理、来源不可用及跨进程一致性的完整规则与验收由模块入口维护。

## 外部 Agent 的反馈读取与处理

外部 Agent 通过同一共享建议能力取得反馈。Janus 界面、已有宿主入口和 MCP 消费[建议管理模块](suggestions/module.md)维护的当前结果，不另建可独立编辑的反馈源。建议不追加到 Note 正文、不引入新 Note 类型。用户明确不开发“复制给 Agent”功能；反馈文件导出和本地文件投影不列入当前交付，现有工作流通过可用宿主工具或 MCP 读取。

用户明确建议记录保存在 Janus 系统中；它们不进入原始 Note 正文或作为随分支提交的审核文件。由 Janus 持久化并经共享反馈能力供界面/MCP 访问，具体数据库或文件布局仍待实现前确定。Git 合并不会自动合并或同步这些反馈记录，语义归属仍需按下述分支规则处理。

一条反馈至少能定位项目、工作区、来源分支与目标 Note URI，说明报告/问题身份、被审版本、问题或检查位置、依据及其版本、反馈类型和未覆盖范围；只有实际生成了建议才附带建议内容。显示用摘要与完整依据分开，字段和持久化路径尚待设计。已确认结果由独立 MCP 进程按 Agent 既有工作区权限读取和处理，不能仅存在于桌面组件内存。Janus 关闭后仍可读取已保存建议及回写处理结果，桌面重新打开后读取同一记录；自动审核仍暂停，MCP 不生成新审核。项目与版本检查用于准确定位和防止冲突，不增加 Janus 专属审批。

| 接收路径 | 推荐行为 | 边界 |
| --- | --- | --- |
| Janus 右侧原生 MCP（读取与处理方向已确认） | 读取当前建议并维护内容，通过独立工具回写处理结果并清理指定条目 | 不提供审核/复核/建议生成入口；读取不清理，无报告不自动生成，不保留建议历史 |
| Note MCP | 读取相关 Note 时附带少量建议摘要、问题 ID、版本有效性及展开入口；单独工具按项目/模块/Note 查询和读取完整反馈 | 不在每次读取塞入全部报告；分页、截断与不可用状态明确；只给当前授权范围内的工程反馈 |
| 已有 WorkflowX 或其他本地读取流程 | 沿用现有 Note 读取，通过可用宿主工具或 MCP 按需读取当前建议 | 不重复读取同一正文，不假定本地文本读取已自动取得反馈 |
| 外部宿主调用约定 | 在处理模块前与任务收尾读取相关反馈 | 采用静默工具调用，不主动通知或唤醒宿主会话 |

已确认建议读取约定：Agent 在处理相关模块前和任务收尾时主动读取相关建议；用户仍可随时在对话中要求读取。约定由 MCP 工具说明与简短指南提供，沿用已有工作流，不默认改写用户规则文件。MCP 自身不唤醒会话或强制调用；读取既有反馈不生成新审核、不自动采纳。

处理相关模块前与任务收尾读取当前建议，按目标和版本避免重复读取。调用约定随工具说明与简短指南提供，一键导入只注册服务，不改写用户规则文件；服务不能强制 Agent 调用，也不主动唤醒会话。缺少反馈工具时如实说明不可用，不假定存在文件导出或复制入口。

外部 Agent 读取依据后自行决定处理，通过同一 MCP 回写已处理/不采纳并清理指定当前建议；暂缓则保持待处理。处理返回本次操作结果，不保留已关闭建议、长期拒绝记录或历史报告；新审核可能重新发现同类问题。普通内容修改或对话声明不等于已处理；确认目标删除则由建议管理模块自动清理，建议生成仍走左侧手动或内部 Git 自动化。

报告存储、外部回应和 Note 正文写入是分开的能力。对外服务建议沿用同一套 MCP 实现，按职责提供反馈读取与维护工具，由宿主按需调用，详见[Note MCP](../note-mcp.md)；不另外维护一套建议服务。反馈不能包含必须执行的隐含授权，不能跨到个人记忆。读取已有报告不需要配置审核模型；首版 MCP 不提供发起新审核或生成建议的能力，这一项不再待定。持久化和跨进程一致性由建议模块实现，回写要求当前分支、报告修订号及 findingIds；独立 MCP 读写不以 Janus 桌面在线为前提。

B2 完成左侧展示与原生 MCP 读取、处理闭环，共用建议管理模块；B5 完成独立 MCP 外部接入与一键导入，B6 接入 Git 自动生成。原生闭环不等待独立分发，不增加“复制给 Agent”功能。接口和运行细节由实施完善，运行时已接入，客户端配置仅在用户导入操作后修改；开发验收使用隔离配置。

## 自动化审核的定位

自动检查与自动改写、自动采纳分开设计。保存后的格式和引用检查优先复用现有能力；语义复核先支持主动发起，验证有效后交付可选自动化。用户已确认 Git 机制，累计全部提交，包括仅改代码的提交；N 可设置为正整数，默认 5，自动审核默认关闭。启用且达到阈值后检查 Note 差异，有差异才对变化目标启动审核并提供建议；本轮没有 Note 修改就不启动后续自动化。首版不做差异过滤，启动语义审核前必须配置 LLM，设置页需检测。GitReviewScheduler 已实现该流程，默认保持关闭，不替用户启用。

启用后的流程为“累计 N 次提交 → 程序检查三类目标范围的 Git 差异 → 有差异才交给 Agent 读取必要上下文并分析 → 按配置由 JEV 核验 → 输出带核验状态的反馈”。Git diff 用于确认变化及辅助判断，不能代替原文、上下文和必要代码依据，也不能单凭文件有差异就认定有问题。差异检查不调用模型，有差异不保证一定产生修改建议。具体范围与无过滤规则由[首版审核设计](review-first-release.md#用-git-确认变化)维护。

| 时机 | 推荐行为 |
| --- | --- |
| 文件保存、外部编辑或 MCP 写入 | 更新索引，以实际内容变化标记既有报告过时；默认不逐次调用语义模型 |
| 检测到新的本地提交 | 累计提交数，未达到 N 时不启动该轮差异检查或语义审核；无需等待 push |
| 已启用自动审核且提交数达到 N | 对比检查基准与本次提交快照，读取三类目标范围的 Git 差异，暂不做差异过滤；无差异结束本轮，有差异才持久化待审目标并异步审核，不阻止提交 |
| 手动发起审核 | 明确选择提交版本或当前工作区，允许未提交 Note 进入本次范围 |
| Janus 完全退出 | 已确认暂停语义审核，首版不提供后台常驻审核服务 |
| Janus 重新打开或恢复关注项目 | 自动审核仍开启且已有有效检查点时补算提交数；达到 N 后针对最新快照合并检查一次，不逐轮回放历史模型调用；无 Note 差异不启动模型，未达 N 保留计数 |

累计全部提交已确认。检查点推进方式仍按当前建议：每次差异检查成功后，以实际检查到的提交建立新检查点并重新计数，无差异也正常推进；检查失败不消费本轮检查点。对比的是检查点到本次版本的累计变化，不能只看第 N 次提交：例如第 2 次修改 Note、第 5 次只改代码，N=5 时仍应发现 Note 变化。若期间修改后完全恢复原样，当前建议按两端 Git diff 无差异处理；是否需要保留这类中间改动的审核触发尚未专门讨论，不能用“实质变化过滤”代替这一差异基准定义。

差异检查点与每篇 Note 的审核完成记录分开。差异目标可靠入队后可以推进检查点，但模型失败/取消的目标继续保留待审或失败记录，不能因下一轮无新差异就被抹去。无新差异时不创建新审核；临时异常最多自动重试一次，配置错误不重试；仍失败由左侧手动恢复，不在无差异轮次隐式增加调用。首次启用的基准与存量提交处理见下述已确认规则；不会把存量内容标为已审核。新建三类 Note 随 Git 变化自动参与，调整 N 保留当前检查点，下一次轮询按新阈值判断；关闭后重开建立新基准，失败项保留到手动恢复。

### 首次启用与已有提交

已确认关闭时暂停、重开后合并补检，以及首次启用时不追溯既有提交。以用户首次启用自动审核时的当前提交作为起点，持久化项目/工作区身份与提交检查点，计数从 0 开始；只配置模型或升级安装不自动启用。既有提交不作为欠下的审核轮次，不从仓库首个提交开始补算或回放，也不需要清理、重写 Git 历史。设置变化为已跟踪工作区立即建立基准，开启不回放历史；应用不会自动启用。

例如首次启用时当前提交为 A，后续累计 5 次到 B，检查 A 到 B 的三类 Note 累计差异。A 之前已有多少提交不影响首次触发。原有 Note 照常索引和浏览，但未运行审核的内容仍是未审核；没有提示灯不表示通过。已有 Note 后续变化时进入相应自动审核，未变化的存量内容可通过已确定的单篇手动入口审核当前内容，不自动补扫全部存量，也不新增历史批量选择功能。

首次启用与重启/升级分别处理：已有有效检查点时继续使用，不能每次打开都重置为当前提交；这时离线积累才适用已确认的合并补检规则。检查点丢失、分支历史不再兼容、关闭自动审核后重新启用及项目尚无提交时的恢复细节仍待收口，不把每次恢复都当成首次启用。首次启用基准与运行/退出规则均已确认，恢复异常另行细化。

用户确认，累计的 5 次提交中若没有涉及 Note 修改，就不自动审核；仅代码变化不能独立触发模型。已有依赖记录仍可让当前建议标为过时；代码可在审核变化 Note 时作为必要依据读取。代码/关联依据变化独立触发留作后续选项。

提交是相对清晰的版本检查点，不保证 Note 与代码已经完整一致。长期不提交或尚未达到 N 时，不自动发起本轮审核；保留手动入口，自动兜底未启用。运行期间后续变化归入下一轮，报告只声明实际检查过的快照和范围。

提交触发时从 Git 对象读取目标提交内的 Note 与同仓代码，保持版本一致，无需切换分支或重置用户工作区。手动审核当前修改则固定实际工作区输入及 hash。自动审核的取证、引用校验和发布均使用同一提交；工作区已有未提交改动不阻断该提交的建议，建议在当前来源不同时标为过时。运行期间当前目标被修改、建议被处理或上下文切换导致审核票据失效时，迟到结果不得覆盖当前状态。提交号和原始输入 hash 用于版本定位及重复任务识别；首版不忽略时间、元数据或格式字段，不能通过归一化 hash 把 Git 检出的变化过滤掉。

### 分支切换与合并计数

用户已确认在项目/工作区内按分支分别保留检查点和计数：切换动作本身不算提交，切回已有记录的分支继续累计；首次跟踪某分支时以当时提交建立起点，不回放该分支此前历史。蓝图也按当前分支的实际 Note 加载，审核建议存放在 Janus 系统中，不能仅因 Note UUID 相同就跨分支复用当前结果。

| 操作 | 已确认计数 |
| --- | --- |
| 当前分支新增普通提交，包括仅改代码 | 每个新增提交计 1 |
| 切换分支 | 切换计 0，保存原分支计数；目标分支有记录则恢复，没有则建立起点 |
| 普通合并产生一个 merge commit | 目标分支增加 1，不额外展开被合并侧支的历史提交 |
| 无明确合并来源的普通单父提交 | 按新增提交计 1；不额外识别为压缩合并或触发专项 |
| 快进合并，没有产生 merge commit | 按目标分支新纳入的第一父链提交数累计；达到 N 仍合并检查一次 |

普通合并计一次只影响审核节奏，不减少 Note 检查范围。达到 N 时比较该分支上次检查点到本次提交的累计差异，包含合并带入的 Note 新增和修改。“累计全部提交”不排除代码提交；普通合并不展开侧支历史、单父新提交计一次、快进按新增第一父链提交累计的口径均已确认。例：main 已累计 3 次，feature 累计 2 次；切回 main 仍为 3，产生一次普通合并后为 4，再提交一次才达到默认 N=5。无需用户设置指定审核分支或文件范围。

建议仅观察当前打开工作区实际使用的分支，不在后台遍历所有分支。各 worktree 保留独立身份与检查点，报告继续绑定实际来源快照；跨分支当前建议按下述统一机制管理，不因分支切换宣称已经审核。分支重命名和历史变化按实际身份校验当前建议；reset、rebase、amend 等特殊操作的合并识别与自动补检暂缓，不猜测操作意图。

首版建议由 Janus 观察 Git 状态变化并在启动/恢复关注时核对，不要求用户工作流安装 hook，也不只捕获 Janus 发起的提交。文件系统事件仅提示重新读取 Git 状态：普通提交可能更新分支引用而不改写 HEAD 文件，不能把事件次数或任意 HEAD 变化作为提交次数。分支计数已确认，Git 观察实现与异常恢复仍待细化，本轮未操作实际分支或修改计数。

### 分支蓝图与建议隔离

建议按项目、工作区、实际分支和输入版本隔离；切换、目标删除及迟到结果处理由[建议管理模块](suggestions/module.md)统一执行。当前 Note 或已读依据变化使建议过时，轻量核对不调用模型、不改变提交计数。仅代码变化不独立发起自动语义审核。

可识别的普通合并按最终内容重新审核，仍存在的关联未处理意见可作依据，已经清理的建议不恢复。缺少两侧待办不阻止审核最终内容。当前暂不考虑压缩合并等无法明确识别来源的特殊情况，不建设猜测操作意图或扩大审核频次的兜底。

### 合并完成后的专项检查

用户已明确合并后由蓝图内部检查冲突 Note、整理材料并重新审核；外部未通知时，内部一旦发现合并也执行同一流程。合并完成是 Git 自动化的特殊触发，目标有三类 Note 变化时不等 N，不以外部通知为前提。用户可见的审核生成职责仍是左侧手动与内部 Git 自动化，右侧 MCP 继续读取/处理既有建议，不增加审核生成工具。上述方向及共用自动审核总开关已确认，内部识别及恢复细节仍待细化，不表示已运行该流程。

用户已明确选择：蓝图整理冲突信息与仍存在的未处理建议，由获授权的 Agent 修改 Note 正文。蓝图汇总目标、当前未处理意见、来源版本与诊断，审核 Agent 针对实际合并内容生成一份当前建议；后续正文修订由维护 Agent 在已有授权内执行，完成后通过 MCP 回写处理结果。蓝图后台不直接覆盖正文，也不把审核器变成自动采纳者。既有授权内的维护不必逐条重新确认，变更内容与依据应可追溯；本轮未实际修改业务正文、Git 冲突或代码。

推荐流水线如下：

| 阶段 | 推荐行为 |
| --- | --- |
| 收到通知或内部发现 Git 状态变化 | 更新项目与目标分支上下文，检查 Git 索引是否仍有未解决冲突；合并进行中或取消时不生成最终审核报告 |
| 合并完成且工作区可读 | 固定实际完成版本，识别合并影响的 decision/module/requirement Note；按 UUID 关联移动/新增，保留三类全项目覆盖，不增加用户指定范围 |
| 程序预检与材料整理 | 检查可解析性、身份冲突、引用及版本，汇总可取得的旧意见与依据；不凭无 Git 冲突就宣布没有语义矛盾 |
| 重新审核 | 审核 Agent 阅读实际合并结果、整理的材料及必要代码，辨别重复、矛盾和遗漏；JEV 按已有可选方式核验，不要求后台先修改正文 |
| 生成当前报告 | 将分析与可选 JEV 信号组织为同一实际输入版本的报告，不再维护两份分支待办 |
| 展示并交接维护 | 只保留当前结果和仍未完成的待办，不留旧报告或处理历史；获授权维护 Agent 读取当前建议、决定如何修改 Note/代码，再通过同一 MCP 回写已处理/不采纳，不自动产生另一轮审核 |

检测到未解决的 Git 文本冲突时，保留真实文件和诊断，交给负责合并的用户/获授权 Agent 解决，再恢复后续阶段；不能把冲突标记当作可正常维护的 Note 直接生成新正文。两边修改同一 Note，即使 Git 自动合并成功，也应检查最终语义；结构扫描无法无模型地判定所有矛盾。“检查冲突”不能缩成只审核 Git 冲突文件或先用程序保证没有语义问题。

已确认首版只保留一个自动审核总开关，普通 N 次提交审核与合并专项审核共用，默认关闭，不另设合并审核子开关。关闭时仍进行 Git 分支、合并与内容变化检测、程序预检和版本刷新，标记旧建议是否过时；不自动调用生成模型或审核模型；关闭开关本身不清空建议，已确认删除的目标仍按统一规则自动清理。过时说明留在左侧预览，沿用既有提示灯规则。开启且满足模型配置前置条件时，普通周期按 N 次检查，内部发现合并后对受影响的三类 Note 专项审核，不等 N；合并仅改代码且无目标 Note 差异时仍不启动自动语义审核。已知依据变化可让旧报告过时。左侧手动审核不受自动开关、提交次数或 Git 差异限制，仍须满足模型配置条件。

同一次合并若同时达到 N，与周期触发合并为同一个审核任务；按项目/工作区、目标合并事件及实际输入去重，后续实质输入变化不能复用旧结果。建议一次合并只做一轮材料整理与审核，不反复调用直到“全通过”，不因后续 Agent 修改或回写反馈递归触发合并流程；实际修改仍可按普通 Git 规则进入未来审核。退出 Janus 时仍暂停，重开后只对已识别且未处理的合并事件恢复/合并检查，不回放首次启用前历史；恢复及等待参数由实施细化；失败最多自动重试一次，配置错误不重试。

外部通知是可选的加速信号，不是运行条件。用户已明确：蓝图内部发现已经发生合并，即使没有通知，也必须进入同一材料整理与审核流程，不能退回“只等 N 次”或要求用户补发通知。已识别合并的处理与合并执行工具、Janus 当时是否在线无关；退出期间不运行，重新打开后在已有检查点之后补查，首次启用前历史仍不回放。

内部检测建议在 Git 引用/文件变化、项目启动或恢复关注时核对，并用适度的运行期补查覆盖漏掉的文件事件。比较持久化的分支提交位置、当前引用及新增提交区间，不只检查最新 HEAD：区间内明确的多父合并提交可恢复为待处理事件；已有分支快照、祖先关系及可取得的本地操作记录作为辅助证据。事件按项目/工作区/目标结果版本持久化去重，与通知到达和 N 周期触发共用一套任务，重启或重复通知不重复发布同一报告。

压缩合并、历史改写等难以确认合并来源的特殊情况暂缓，不纳入当前讨论或版本验收，也不要求额外模型调用兜底。普通合并的内部发现、去重、退出恢复继续实施；输入版本校验仍适用于所有实际内容变化，不能因特殊检测暂缓就复用已失效结论。

验收需覆盖：无通知但区间内存在合并提交时内部补检、Janus 关闭期间合并后重开、通知与内部发现同时出现去重、未解决冲突不发布报告、Git 无冲突但语义矛盾、合并取消、自动关闭时仍检测并标记过时但不调用模型或清空建议、开启后两种触发共用开关及模型前置条件、缺模型、可识别普通合并的支持边界、与 N 同时触发不重复、版本变化和失败不消灯，以及无 Note 差异不调用模型。本轮未实施或执行这些验收。

### 审核失败与重试

用户已确认合并专项检查和普通周期共用有限重试：临时网络错误、超时或可恢复服务异常最多自动重试 1 次；配置缺失、认证/模型不支持等错误不反复请求，说明原因并引导修复。仍失败时保留失败记录及左侧手动重试入口，不因重新打开 Janus、MCP 读取或无新 Note 差异而无限补跑。具体等待、提供方限流处理与请求参数由实施细化，重试次数和失败后人工恢复的原则不再待定。

界面“需要重试”统计按 Note 去重的失败、覆盖不足、恢复中目标、待复审及结构问题，不是模型请求的重试率。失败持续保留，完成引用只留最近两轮，二者数量不能组成成功率分母。调度器的 attempts 在调用前持久化，不等同于提供方 HTTP 请求次数；正常退出或设置取消会退还本次计数，硬中断恢复仍受原有有限次数约束。

错误分类解包 SDK 的 lastError、嵌套 cause/error、errors 和响应状态，保留安全原因与 HTTP 状态，不存储提供方请求头或正文；模型容量缺失、上下文超限与内部 TypeError 分别表达，不再一律归为网络或通用模型错误。审核关闭 SDK 隐式重试：单轮流式响应先缓冲，临时中断后丢弃该轮半段输出，等待 2 秒，仅重发该轮一次，保留此前工具取证；仍失败才由调度器等待 2 秒后至多重跑整篇一次。长审核不实时展示文字，单轮缓冲以增加一轮输出的内存换取恢复时不拼接损坏内容。格式、目标完整阅读、覆盖与引用不合格时，模型在同一取证会话收到具体反馈并至多纠正一次；仍不合格则保留失败，不降低证据门槛。

引用路径必须实际读过，引文只归一 CRLF/LF，其他字符保持精确；乱序和重叠页按行号合并，未读间隔不能拼接成引文。Git 固定提交的 Note blobs 通过 cat-file --batch 批量读取，缓存不可变解析快照和文件内容，避免重复启动 Git 及审核途中临时文件丢失。发布继续校验票据、提交证据和当前来源，但使用独立普通 Note reader，避免前台 HarnessNoteService 的 12 秒交互期限丢弃已生成报告。独立 reader 与前台扫描仍共享底层仓库锁，BUSY 退避最长 60 秒，等待可取消；取消后不得提交迟到观察。

生成式分析失败时不伪造建议；JEV 失败时保留已有 Agent 建议并标明核验未完成，不能标成通过。多 Note 批次部分失败时保留成功结果，只对失败目标恢复，避免整批反复调用；同一任务重复响应只发布一份有效结果。目标仍存在的未完成意见不因失败消失，失败详情放左侧，不新增卡片失败灯，也不回滚外部修改。恢复前核对目标与输入版本，版本已变化则不能把旧任务结果写成当前结论。

完成记录按目标和实际输入维护，部分失败不得推进全部目标的已审基线；重试间隔、单批处理、合并等待和并发由实施细化；当前不设置用量或预算上限，自动重试最多一次的规则已确认。无 Git、无首个提交或 Note 被忽略时，保留文件/hash 检测与手动审核；是否提供自动兜底另定。读取已保存反馈不依赖审核调度器常驻。用户已确认首版 Janus 完全退出时暂停审核，不建设后台常驻审核服务；重新打开且自动审核仍开启时合并补检，不重放历史轮次。

当前源码已有 Git 工作区状态读取（src/main/git/service.ts）及共享 Note watcher/sourceHash 基础；共享 watcher 的 Git 部分监听 HEAD 文件，用于索引/证据刷新，不能据此声称已经实现可靠的提交检测或语义审核调度。本轮只核对现有能力并维护方案，未安装 Git hook、运行模型或修改运行时。自动生成审核结果、Agent 读取反馈和应用修改仍分开处理。

自动运行完成后可以展示报告和问题提示。将建议应用到 Note、替换已采纳决策或扩大实施范围，继续依据已有授权与具体语义判断；此次认可没有授予一律自动改写或自动批准权限。程序检查、主动深度复核和变化触发复核应共用规则，逐步验证价值，避免重建原知识库的全量提取与发布流水线。

## 设置与 LLM 配置前置条件

蓝图设置已确认同页分为审核模型、自动审核和 MCP 接入三个区域，具体归属见[产品方向](../product-direction.md#设置工作台与右侧审核的归属)。设置修改后自动持久化并生效，不设计保存或应用按钮；校验或持久化失败就地提示，自动检测结果随配置更新。有效配置保存与连接检测分别表达，不能把填写完成当作检测通过。

可下载插件按旧设置页恢复审核模型、自动审核与 MCP 同页布局，复用原卡片、下拉、开关、数值步进、终端图标及帮助浮层的包内副本。文本输入合并 350ms、开关即时排入串行提交；有效修改带 revision 写入，冲突后保留草稿并暂停，显式重新载入后恢复。首次读取、有效修改保存及窗口焦点刷新提供方后，等待 800ms 自动检测连接，修改或关闭取消旧检测；手动重新检测保留。自动审核从关闭转为开启仍要求生成连接 ready。工作台未打开设置时不挂载设置页或自动探测。对话模型与审核配置的完整功能对齐继续独立验收，命令及剩余边界见[官方插件专项](../../planning/blueprint-official-plugin.md)。

旧宿主设置页曾通过 credentialGet 恢复已保存的 JEV 明文值。当前插件恢复行内凭据输入、eye 和清除操作，但沿用插件凭据边界：已存值只返回 configured 布尔状态，重新打开显示“已配置，输入可替换”，不将已保存密钥解密回传插件页面。eye 仅切换本次输入的显示与隐藏；空值时禁用，清空与重开恢复隐藏。替换和清除由已授权 native 服务转交宿主，仅限自身 manifest 已声明的槽和 origin，保存前复核启用状态；修改撤销相关宿主网络与声明式任务。safeStorage 加密落盘，密钥不进入普通配置、KV、草稿和日志。本次输入在页面生命周期内持有，页面关闭前尚未到达提交时刻的输入不会缓存；保存失败就地提示。这保留了旧页的编辑布局，但未恢复旧凭据明文回读行为。

建议生成连接检测使用固定测试句、30 秒超时和 1024 token 输出额度，给包含推理的模型留出完成回复的空间。提供方初始化、生成请求和 JEV 探测均在宿主侧等待取消信号，避免 SDK 在认证或初始化阶段忽略取消而一直占住检测；初始化超时后不再发出迟到的生成探测，迟到结果不改变已返回状态。2026-10-10 使用 dev 当前 Vertex AI / gemini-3.8-flash 配置复现原 32 token 检测：返回 length，首次正文为空；同一模型提高到 1024 后正常 stop 并返回 OK，说明原失败是检测回复被截断。设置页按安全分类区分截断、空正文、超时、网络、鉴权、权限、接口/模型及提供方错误，不展示 SDK 请求体、凭据或原始响应；有 HTTP 状态时保留状态码。此检测只证明固定句可以完成，不替代完整 Note 审核质量验证。

设置页复用设置中心的分区卡片、开关、按钮和共享下拉组件，统一留白、字号与主题色；窄内容区的模型字段和终端操作自动换行。自动审核开关名称固定为“自动审核”，Git 提交触发规则保留在说明中。每轮检查的提交数采用横向减号、数值、加号控件，隐藏原生上下箭头；支持直接输入和键盘上下键，范围仍为 1–10000，到达边界时禁用对应按钮，修改仍即时保存。MCP 接入按终端展示品牌图标、名称、配置状态、路径与操作，六种 CLI 图标复用通用设置的 `EXTERNAL_CLI_TOOL_ICONS` 映射（`claude-code` 对应 `claude`），保留各品牌在深浅主题下的可辨识底色，不以通用终端图标代替。

自动配置检测是明确要求。设置页需自动检查审核接入和所选建议生成模型的必要信息、可用性及角色能力；配置变更或已选模型被删除/禁用后，应更新检测结果，运行前复用同一前置检查。不能把字段填写完整当成连接成功，也不能因普通生成请求成功就宣布 JEV 核验接口可用。具体远程探测方式、触发时机、结果缓存与超时在实施前确定，避免每次渲染都调用模型。

## JEV 与生成式 LLM 分工（方向已确认）

用户指出 JEV 不会提出建议。现有[模型适配](https://github.com/TreeX-xx/JanusX/blob/f2e0194fccab765142b6c58a62e393498ae9c3d2/src/main/knowledge/knowledge-models.ts)确认这一点：knowledgeModelJson 对 JEV 拒绝生成请求；reviewKnowledge 发送 support、consistent、逐项 coverage 问题，接收 noul 数值。返回对象中的 reason 是程序选择的固定字符串，不是 JEV 生成的解释。不能将当前适配包装成能直接提出修订方案的审核 Agent。

用户已选择 JEV 负责命题核验，生成式 LLM 负责理解、分析并在已有授权内继续维护 Note。维护方可以是现有对话或外部 Agent；这项确认不授权后台无条件改写，也不要求另设专门维护模型。检查输入需要明确目标陈述、独立来源或现行约束、待回答的问题，以及各自的原文位置与版本。输入组织由审核服务和发起审核的 Agent 配合完成；已有明确检查项可由程序套用问题模板，任意长文的陈述识别、材料选择与问项拆分通常仍需 Agent。JEV 不会自动找齐相关 Note，也不能从整篇的一个低分推导出错误段落或根因。

| 角色 | 负责内容 | 不据此推断 |
| --- | --- | --- |
| 程序 | 结构、身份、引用和版本检查；绑定检查输入与来源；整理反馈 | 不能仅凭分数生成具体因果解释 |
| JEV | 对给定问题返回支持度、一致性等核验分数 | 分数不是全文正确率，不是修改方案或采纳命令 |
| 具备生成能力的 Agent/模型 | 阅读原文、分析问题、解释取舍并提出建议 | 不能把自己的解释归称 JEV 原始结论 |
| 用户与其授权的外部 Agent | 决定是否修改、怎样修改或暂缓处理 | 读取反馈不等于接受修改任务 |

首版新发起的语义审核必须具备生成式 LLM；JEV 单独运行有限问项只属于适配器能力，不作为绕过 LLM 配置条件的首版审核模式。JEV 核验结果的解释和建议由生成式 Agent 基于原文形成，不能由固定 reason 字符串伪装生成。维护方仍可沿用当前对话或用户授权的外部 Agent，不要求额外部署一套本地模型。

自动产出语义建议需要明确配置具备生成能力的执行者；仅配 JEV 不满足首版审核的启动条件。已确认审核模型单独配置，建议生成模型从已设置的生成式模型中选择；用量管理仅预留后续扩展，当前不设置上限；具体接入字段由实施细化，当前对话使用某模型不自动表示已经配置后台审核。新版本先隐藏并暂缓应用内本地模型部署，审核不以该部署功能为前置条件；可复用现有提供方，模型映射与配置字段另定。

当前流程为 Agent 先分析并发布，JEV 按配置随后评分，见[首版审核设计](review-first-release.md)。数字保留问项与输入出处，不按阈值分类支持/分歧，不参与销项或通过判定。评分一条“违反需求”的建议仍须提供原需求和被审材料，不能只用建议自证；高分也不证明方案完整或最优。

示例：决策仍以单进程为前提，需求已增加多进程写入。Agent 或明确检查项先把这两处内容选出来；JEV 可回答“现有说明是否覆盖这个要求”。若支持度低，程序只能提示该要求待核对。具体建议，如补充并发约束、重新讨论存储方案或保留原设计并说明适用范围，应由 Agent 分析后提出，不能从低分直接生成“改用 SQLite”。

首版按已确认分工纳入 JEV 核验与生成式 Agent 维护的接线及质量验证。比较相同 Note 样例下有无 JEV 核验的误报、漏报、可操作性、调用成本和耗时，以确定适用检查项和调用策略；接线完成不等于评分效果已验收，也不要求每次读取、保存都调用 JEV。既有[模型实验](../../knowledge/requirements/unified-memory-laya-primary.md)出现过高置信错误，旧知识库阈值不能当作蓝图内容正确率或建议通过线。

## 运行实现

审核结果提交后，运行时立即广播当前分支的建议集合与 revision，再执行调度收尾；失败仅发布实际保存状态，不伪造清空。显式关闭意见同样通知。修复写入后的独立复核沿用这条统一结果通路，顶部、节点与详情共用前端状态并拒绝较旧建议响应。修复展示直接交付单篇正文与已保存建议，完整来源对账独立在后台运行；完整读取有宿主期限、取消检查与可恢复的请求合并，交互语义与回归证据见[Note 更新提示与建议定位](../navigation/note-updates-and-suggestion-navigation.md)。
