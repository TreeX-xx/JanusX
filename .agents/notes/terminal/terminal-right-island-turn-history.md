# Terminal right-island turn file history

## Problem

A terminal's file-change signal must describe the difference between consecutive completed conversations. Reusing a submission checkpoint ties this signal to input parsing and can combine several conversations. Multiple mounted islands subscribe to the same global event, so unguarded appends create duplicate history entries. Empty turns require an empty latest view while prior change records remain accessible.

## Decision

`TerminalTurnChangeTracker` owns one in-memory file baseline per terminal. The initial capture precedes CLI creation and uses foreground scheduling in the shared workspace I/O queue: it still yields in batches and honors cancellation and directory transactions, but does not incur the background 20ms rest at each yield. Accepted turn-end captures remain background tasks; each compares its captured state with the previous completed turn and advances the baseline, including quiet turns. Start/end gating ignores duplicate completion hooks, per-terminal queues preserve event order, and unregistering discards pending results. Snapshot failures clear the baseline and publish an unavailable result; the next successful capture re-establishes the baseline without claiming a cumulative change.

The tracker reads Git's tracked and nonignored untracked paths, with a directory walk for folders without Git. Internal checkpoint and build directories are excluded. Small regular files use content hashes; files at least 2 MiB use size and modification metadata and have no content diff. Text retention is bounded at 16 MiB per terminal snapshot. The `diff` library counts added and deleted lines in chronological order with a per-file time limit; omitted content or a diff timeout leaves counts unknown. Captures are observational filesystem reads, so concurrent writers can affect a boundary; a detected size change during a read invalidates that capture.

The renderer shares one reference-counted IPC subscription. Turn identity and sequence reject duplicates and stale results. Only nonempty successful changes append to the twenty-record history; every quiet or unavailable turn clears latest independently. Identical file lists from different turns remain separate valid records. Terminal teardown clears both views. History stores immutable summaries in memory. File clicks in latest and history use the same native editor window IPC as the file tree, retaining its tab reuse, system always-on-top control and desktop titlebar dragging. Deleted files and terminals without a working directory cannot open a preview.

File paths remain relative to the terminal cwd. The editor window identity uses the most specific containing root among the terminal's owning workspace, its active scope and its known worktrees. Windows drive and UNC paths compare without case or separator differences; POSIX paths preserve case. This groups subdirectory terminals with their file tree window, keeps nested and sibling worktrees separate, and resolves background terminal snapshots by their owning workspace rather than the visible workspace. A cwd outside all known roots remains its own editor scope. Worktree discovery is not triggered by a click; a missing worktree listing can therefore prevent reuse until that scope is known.

The right-edge file dock is 32 px wide and 64 px tall when collapsed, with 2 px horizontal padding to keep the 99+ badge readable. A separate 32 px wide, two-button scrolling capsule sits 8 px above it; the group meets the pane edge in fullscreen or without history, and moves inward 22 px only when a normal buffer has scrollback, leaving its scrollbar rail reachable. Buffer history controls the inset, so a fading thumb does not move the island. Attached controls have only left-side rounding; inset controls have a full border and rounded corners. It displays only the latest nonzero file count, caps its compact label at 99+, and keeps the exact count in the accessible label. A quiet dock hides the number and remains operable for latest and history. Single click opens latest; double click opens history; keyboard activation and explicit view buttons provide the same access. Expanded views are fixed-size and scroll inside: latest is 340 × 320 px and history is 370 × 420 px, with the total tool group capped at the pane height minus 16 px. The file panel shrinks inside that space, while the scrolling capsule keeps its size; panel width stays within the pane. Switching views changes the shell size instead of hugging content. History renders one card per batch (1 px `--shell-border-soft` hairline, 6 px radius, `color-mix` of `--shell-chrome` toward `--shell-text`, the session turn-card material), while latest stays a flat current-turn list. Cards emphasize filenames over directory paths, align line counts, use localized status and timestamps, and share dark/paper theme tokens with reduced-motion support. The morph is owned by `TurnChangeIsland.css`: width and height animate on the elastic overshoot curve when expanding or switching views and on a snappy curve when collapsing, the body fades in behind the shell, and the superseded `turn-island-*` block in `globals.css` (dead class names plus a transition the component had overridden) is removed.

The focused terminal auto-expands latest on a nonempty turn result when its pane is at least 240 px wide. Automatic and manual expansion both collapse after six seconds outside pointer hover and keyboard focus; leaving the island restarts the timer. Outside pointer-down collapses immediately, including when the terminal stops event propagation, because dismissal listens in capture phase. Escape and the collapse button remain available. The right-pointing collapse chevron follows the panel’s motion back to the right edge, has a 28 × 28 px target, and restores focus to the same terminal when clicked. Background terminals retain counts without stealing focus. Manual expansion remains available below 240 px. The file dock keeps its file-only latest/history views. The separate scrolling capsule pages on click and repeats while held, without changing PTY geometry. Its native-buffer and CLI protocol behavior, stop conditions and verification are owned by [terminal scrolling](./terminal-scrollback-navigation.md).

Verification on 2026-10-20: `npx playwright test tests/e2e/turn-changes.spec.ts --project=island --workers=1 --output=artifacts/turn-island-auto-collapse` passed 10 browser cases, including timed automatic expansion/collapse, manual expansion with hover pause, and outside dismissal through stopped event propagation. Existing history, theme, keyboard and editor-routing cases also passed. This uses production React components with simulated IPC, not packaged desktop acceptance.

## Foreground startup capture (2026-11-02)

Pre-launch capture keeps the shared workspace transaction and reads at most eight files concurrently. Each read uses bounded 64 KiB chunks with the existing 2 MiB limit and before/after file metadata checks. Results commit in sorted path order with the same 16 MiB retained-text budget. Each group settles fully before yielding or rejecting, so cancellation and failed reads cannot leave detached work using a released I/O lane. Background completed-turn captures retain their sequential, cooperative scheduling. No cross-terminal snapshot cache is introduced; every launch still captures a fresh baseline before starting the agent.

`node scripts/performance/snapshot-startup-probe.mjs --freeze` saved the working-tree baseline before edits; running the script without that flag compared three alternating samples over 2,584 files. Before: 4,411 / 4,252 / 3,991 ms; after: 1,586 / 1,449 / 1,378 ms. Median registration capture decreased 66%; all six complete snapshot digests matched. Event-loop maximum samples were 16–17 ms before and 19–22 ms after, so this is not an event-loop latency improvement. Source copies, bundles and results are in `artifacts/terminal-startup-investigation/`. OS caches were not flushed; this measures foreground capture, not full Electron/CLI readiness or peak memory.

`pty-startup-probe.mjs` separately compares bundled/system ConPTY with and without terminal capability replies. The previous ready-marker benchmark did not answer primary device attributes: bundled ConPTY waited approximately three seconds, whereas a reply removed that wait. Its earlier PTY overhead must not be treated as normal xterm startup cost. Production ConPTY selection remains unchanged. The browser startup suite verifies a live device-attributes reply and no duplicate reply on historical replay; first-mount races and real provider startup still need desktop timing.

Verification: 42 tests across `turn-snapshot-startup`, `turn-change-tracker`, `terminal-creation-rollback`, `terminal-ipc-contract`, `terminal-launch` and `terminal-officecli-path` passed. This includes the eight-read bound, cancellation/failure draining, independent terminal baselines and deterministic text retention. All four `terminal-startup.spec.ts` browser tests passed. `npm run typecheck` and scoped source ESLint passed. Ordinary Shell does not capture file baselines and receives no claimed speedup from this change.

## Dev startup follow-up (2026-11-03 Asia/Shanghai)

While no text has been rendered, the xterm host has zero opacity: its blank cursor and scrollbar are hidden, while parsing, layout, capability replies and rendering continue. The first rendered nonblank text reveals it. This is a visual milestone, not a guarantee that the native agent is ready for input. Existing startup feedback remains visible separately. Four browser startup cases passed, including opacity before/after text, live device-attributes replies, replay, repeat creation, and failure/retry; the Shell waiting screenshot was inspected.

Read-only samples from the real `JanusX-Dev/janusx/logs/terminal.log` are summarized without command arguments in `artifacts/terminal-startup-investigation/dev-startup-samples.json`. After the prior optimization, OpenCode preparation/baseline/total were 689/2249/3640 ms, Claude 9/1683/9270 ms, and Codex 841/1405/2808 ms. Two later DSH launches had baseline/total 7342/7602 and 2445/2626 ms. First PTY bytes followed creation by approximately 0.1–0.3 seconds in these samples; those bytes can be ANSI negotiation, not a prompt. These are observed dev launches with uncontrolled load, not a paired benchmark or proof of full readiness.

Next optimization priorities: (1) Claude's roughly 7.6 seconds after preparation and capture: separately measure asset creation, `--bg` dispatch, authenticated bridge arrival, `agents --json --all` identity validation and attach; replace redundant CLI work only with an equivalent identity guarantee. Model discovery is already asynchronous. (2) Split baseline lane waiting from capture work to explain DSH variance, then evaluate workspace incremental snapshots with invalidation for external edits; unchanged directory ownership and fresh launch boundaries remain required. (3) Overlap CLI/hook preparation with baseline capture after establishing cancellation/rollback ownership; the observed cold preparation budget is about 0.7–0.8 seconds for Codex/OpenCode, and warm probes are already cached. Do not start agents before their baseline: startup hooks may edit files.

The create timing now reports `runtimeMs` and `ptyMs` in addition to preparation/baseline/total; a one-time `terminal conversation ready` event records the adapter's ready milestone. Existing `terminal first output` remains a first-byte metric. No further startup speedup is claimed in this follow-up. Typecheck/scoped ESLint and 20 terminal launch/IPC/rollback unit tests are the targeted checks; the current user dev process was not restarted for measurement.

## Startup optimization verification (2026-11-03 Asia/Shanghai)

Claude control commands now close their unused stdin immediately. The native `--bg` command otherwise waits for possible piped input; dispatch itself does not require a prompt. The CLI still creates its own worker, the bridge must arrive, and `agents --json --all` still verifies the worker identity afterwards. No persistent worker pool, user configuration change or model call is introduced.

`claude-startup-probe.mjs --freeze` preserved the pre-change adapter; the comparison used real Claude 2.1.316 with an isolated profile and localhost model, alternating three samples per adapter. Full adapter start took 6771 / 5418 / 5374 ms before and 2253 / 2246 / 3815 ms after: median 5418 to 2253 ms, down 58%. Dispatch fell from 3404–4916 ms to 385–428 ms. All six starts reached ready and made zero model requests. These timings exclude repository capture, Electron rendering and real-provider latency. Sources, bundles and measurements live in `artifacts/claude-startup-performance/comparison.json` and sibling files.

Local launch now starts CLI/hook preparation and the fresh file baseline concurrently, under the existing per-terminal creation lock. No native agent or PTY starts until both finish. Failure cancels and drains capture before releasing the lock; close/shutdown gates now cover ordinary terminals too. A rejected Shell-profile preparation can be retried with the same identity. `preparationMs` and `baselineMs` overlap and must no longer be added together to estimate total startup. `launch-preparation-probe.mjs` compares a real native version query with foreground capture, serial versus parallel: median 1376 to 1320 ms over 2587 files, all six digests identical. The version query in this probe takes only about 70–80 ms, so this is a modest component result, not a full dev startup percentage.

Two trial changes were rejected: querying Claude identity before the bridge produced an incomplete native session identity in a real-CLI run; avoiding EOF reads in file capture had no stable timing benefit. Both were reverted. Existing background capture scheduling and independent terminal baselines remain unchanged.

Checks passed: 58 unique targeted unit cases (including the added close-during-preparation variant on rerun), one real Claude CLI integration case covering background completion, interrupt and follow-up dialogue, and one real Electron fixture case covering Claude/Codex/OpenCode creation, native-history restoration and follow-up turns. The CLI test used the isolated localhost fixture, not a live provider account. Typecheck, scoped ESLint and isolated Electron build passed; the desktop test used `artifacts/terminal-startup-round2/app/main/index.js` with repository icons copied into the probe's resources directory. No running user dev session was restarted by this verification.

## Alternatives considered

- Reuse submission checkpoints and filter empty renderer events. This keeps one snapshot mechanism, but its baseline depends on input recognition and represents submission time rather than the previous completed conversation.
- Persist additional end-of-turn checkpoints. This reuses blob storage, but mixes transient UI tracking with restore-point retention and session checkpoint counts.
- Keep one event subscription per island with content-based deduplication. This minimizes lifecycle plumbing, but repeats global work and can erase legitimate identical changes in different conversations.

## Consequences

Latest reflects the current conversation while history contains only actual change records. Independent baselines add filesystem reads and bounded text retention per open terminal; large-file metadata is approximate, and shared-workspace edits from other terminals are included. History is not persisted, and editor previews are current files rather than archived contents.

Startup investigation on 2026-10-18 (source revision `403a8ea`, Windows, JanusX repository cwd): three sequential calls to the production `captureTurnFiles` implementation captured 2,076 files each in 2,226 / 1,981 / 1,973 ms. Measurement used `node --input-type=module`, TypeScript `transpileModule` in memory, and `performance.now()` around each awaited capture; no CLI was launched and no filesystem cache was flushed. These are isolated baseline timings, not end-to-end terminal startup measurements. At that revision, `createTerminalLifecycle` awaited `turnChangeTracker.register` after program/hook/OfficeCLI preparation and before PTY creation on every non-shell launch. The scanner serially read eligible files, adding roughly two seconds before CLI startup in this workspace, including repeated launches. The 16 MiB limit bounds retained text, not all file reads. Ordinary shell terminals skip the baseline.

The user clarified that every terminal type opens blank on every new launch; AI-only baseline work cannot explain the whole report. Startup now displays a localized, nonblocking hint immediately, switching to waiting-for-output once the PID arrives. Only xterm rendering nonblank buffer text dismisses it; ANSI-only output does not. Failed/exited terminals hide the hint, and replay dismisses it when a pane remounts. All terminal launches and terminal warmups now use the OfficeCLI verification completed before the app window opens, without capability probes on the create path; see [OfficeCLI bundled](../desktop/officecli-bundled.md). Main-process diagnostics record preparation, baseline, spawn-total and first-output-total durations, excluding renderer mount/paint. Existing portable logs contained AI request-to-ConPTY waits of 15–193 seconds with native spawn taking 68–228 ms for those samples; they contained no shell sample and do not establish the common cause for all presets.

The 2026-10-18 implementation read batches of at most eight files concurrently and committed in sorted path order. An alternating comparison of `git show HEAD:src/main/terminal/turn-file-snapshot.ts` against that implementation (same in-memory transpilation command, 2,079 files, three samples, no cache flush, other verification running) measured 1,305 / 1,336 / 1,405 ms before and 661 / 734 / 729 ms after. These are historical component measurements. The subsequent [shared I/O queue](../planning/workspace-data-contract-baseline.md) serializes capture and bounds file reads to 64 KiB chunks, with cooperative yields and deterministic 16 MiB text retention. Large directories still require a complete scan; foreground launch capture can consume more disk time while it runs and must wait for an existing same-directory transaction. It does not promise instant CLI readiness.
