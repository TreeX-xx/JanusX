# 会话模型连接隔离

## Intent

用户希望在共享 LLM 连接目录上，由每个 Agent 独立决定是否采用 JanusX 的配置，并允许 JanusX 配置 Claude Code、Magpie 配置 Codex 等混用。进一步提出：两个 Claude Code 会话是否可以同时使用不同渠道，并认为这会是有价值的功能。

本文记录技术可行性及用户已认可的交互方向，尚未实施会话级渠道选择。用户于 2026-11-16 认可“设置默认、新建时覆盖、会话中辨认”的方案并要求记录；本文整体保留 draft，工程细节和待验证链路尚未定稿。服务接入及交互问题由 [LLM 配置产品研究](./llm-configuration-product-research.md) 维护；[共享渠道与 Agent 绑定](./terminal-provider-collections.md) 仍描述当前配置实现；[启动级 Hook 隔离](./terminal-hook-launch-isolation.md) 提供已有启动注入背景，不等同于已实现模型连接隔离。

## 当前基础与可行性

当前 providers 是共享连接集合，bindings 按 Janus、Claude、Codex、OpenCode、Pi 类型选择连接与模型。外部绑定经 ConnectionProjector 写入对应 CLI 的配置文件，因此是 CLI 配置范围内的选择，不能满足同一 CLI 的两个会话分别使用不同连接。

Claude Code 官方支持启动时的 --settings 文件或 JSON、--model，以及进程环境变量。附加 settings 的指定键对该会话覆盖普通用户/项目配置，省略键仍沿用原值，组织托管策略保持上位约束。见 [CLI 参数](https://code.claude.com/docs/en/cli-reference)、[设置优先级与会话覆盖](https://code.claude.com/docs/en/settings#change-a-setting-for-one-session)、[环境变量](https://code.claude.com/docs/en/env-vars)（2026-11-16 核对）。

建议为每次启动生成独立连接覆盖，只注入本会话的地址、认证、模型及必要模型映射。会话 A 与 B 不写同一份全局 LLM 配置；停止 A 不需要恢复可能已被 B 或外部工具更新的全局文件。这个方向不要求先自建协议转换网关，也不要求仅为 API 渠道隔离而复制整份用户 home。

当前 claude-conversation.ts 已合并启动 --settings，并在每次启动创建的私有目录生成 settings.json，再用于 --bg 调度；catalog-settings.json 保留相同 provider 环境并禁用 Hook。这是可复用的基础，尚未把用户的会话渠道选择贯穿到该链路，也未完成共享后台运行时的双会话验证。

## 本轮真实 CLI 验证

使用本机 Claude Code 2.1.325，在同一个临时 HOME、同一个 CLAUDE_CONFIG_DIR、同一个工作目录下，并发运行两个原生 print 进程。每个进程通过独立 --settings 文件指定一个不同的 localhost Anthropic 模拟服务、虚构 API Key 和模型，并用 --model 明确选择模型。

| 检查 | 实际结果 |
| --- | --- |
| 会话 A | 渠道 A 收到 probe-a，校验凭据为 A 的虚构凭据，CLI 退出码 0 |
| 会话 B | 渠道 B 收到 probe-b，校验凭据为 B 的虚构凭据，CLI 退出码 0 |
| 共享配置中的第三个渠道 | 零请求 |
| 共享 settings.json | 验证前后字节一致 |
| 运行时 | 两个真实 Claude 进程并发；使用同一临时 home 与工作目录 |

验证关闭不必要流量、自动更新、Hook 和外部 MCP，工具列表为空；请求只指向本机模拟端点，未复制用户登录凭据、未调用付费模型。临时结果位于 C:/Users/Tree/AppData/Local/Temp/janusx-session-channels-HJGh99/result.json，执行脚本位于系统临时 janusx-llm-source-research/probe-session-channels.cjs。上述路径用于本机复核，不作为永久文档依赖。

这证明该版本原生进程的地址、认证和模型可以并发隔离，不能据此宣称 JanusX 产品已支持。尚未验证真实交互 TUI、--bg 后台调度/共享 daemon、跨终端/对话模式切换、断线重连、原生子 Agent、恢复旧会话、运行中切换渠道以及 macOS/WSL/SSH 的完整链路。

## 已确认的交互方案

设置管理可用渠道和新会话默认值，每个会话决定本次使用哪个连接与模型。日常启动直接采用默认值，需要时再覆盖，不强迫用户每次填写配置或经历选择弹窗。

### 设置中的职责

“渠道管理”维护地址、凭据、协议和模型，一次配置供多个 Agent 和会话选择；列表展示连接状态和引用它的 Agent 默认值。“Agent 默认配置”明确表示新会话的初始来源，可以是 JanusX 渠道及模型，也可以是“沿用 CLI 已有配置”。修改默认值不改变已经运行的会话，不隐式改写外部 CLI 的全局默认。

沿用已有配置是完整可用的选项，可来自 Magpie、CC Switch、官方登录或手动设置，无须强制识别外部管理工具。各 Agent 独立选择配置归属。

### 新建时覆盖默认值

主“新建 Claude Code”按钮按默认值直接启动，旁边提供选择入口：使用默认配置、沿用 CLI 已有配置、选择其他渠道和模型。临时选择默认仅影响本次启动；“设为以后新会话的默认值”是独立操作，不自动选中。添加渠道不自动让所有 Agent 或运行实例采用它。

### 会话中的展示与调整

会话处持续显示 Agent、模型和渠道，例如“Claude Code · 模型 A · 工作渠道”，区分所选配置与已确认运行值。并排会话不能只显示相同模型名而隐藏连接来源。

点击该位置时区分“换模型”和“换渠道”：前者在当前渠道支持的模型中选择；后者改变服务来源和凭据。第一版切渠道优先提供“使用此渠道新建会话”，原会话继续运行。当前会话重启换渠道及保留上下文的续接方式，待恢复链路验证后另行设计。不以仅修改界面标签冒充连接已经切换。

### 何时使用不同渠道

| 场景 | 选择不同渠道的原因 |
| --- | --- |
| 工作与个人项目并行 | 分别使用公司和个人 Key，便于费用归属 |
| 对比服务商 | 同一模型通过不同服务运行，比较速度与稳定性 |
| 主力与辅助会话并行 | 分别选择主力服务和低成本服务 |
| 本地与云端配合 | 某会话连接本地模型，其他会话使用云端 |
| 临时试用新服务 | 新建试用会话，保留原有工作会话 |
| 与现有工具混用 | 部分会话由 JanusX 选择，其他会话沿用外部配置 |

渠道表示地址、凭据和连接方式，模型表示该渠道提供的选择。同一渠道内使用不同模型只需分别选模型，不要求创建重复渠道。第一轮交互集中于设置默认、新建时覆盖、会话中辨认三个入口。

## 生命周期与隔离边界

重新打开或恢复会话应保留先前选择，渠道被删除或凭据不可用时提示重新选择，不静默回退到别的付费服务。保存渠道引用与必要版本信息时，凭据仍由本机连接存储/受控启动文件处理，不写入对话文本或普通会话元数据。

编辑共享渠道时提示引用对象，区分服务目录当前值和运行实例已采用值。连接快照/版本语义需要明确，凭据撤销、共享额度和上游故障仍会影响使用相同服务的会话；这里只讨论连接配置隔离，不是独立账号、配额、文件系统或完整用户状态隔离。

沿用外部配置的会话不注入 JanusX 的连接覆盖。若外部网关在稳定地址后自行改变路由，JanusX 只能说明它连接该网关，不能保证网关上游的实际渠道被固定。

## 正式接入时的验证重点

同项目/不同项目下双 Claude 会话使用不同地址、凭据、模型并发工作；创建、关闭、重启一个会话不改另一个会话或 CLI 全局配置。TUI、对话模式与后台调度使用同一会话选择，模型目录探测也不能串用其他会话的凭据。

会话恢复、重连、复制与自动化显式携带正确连接选择；渠道编辑和默认切换不静默改变已启动实例。测试配置优先级、旧 API Key/Token、云 provider 开关、模型别名和子 Agent 映射，避免残留设置把请求送往另一渠道。组织托管约束应报告为不支持或被限制，不通过关闭策略解决。

用户在原生 CLI 内主动执行会写回共享偏好的命令仍属于另一边界；会话连接隔离不能宣传为所有用户设置完全隔离。官方订阅与第三方 API 并发混用的认证优先级需专门验证，当前探针仅覆盖两条 API 渠道。
