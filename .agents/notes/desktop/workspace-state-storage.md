# 工作区私有状态迁出项目目录

## Problem

启动配置属于本机项目配置，检查点和命令日志属于应用私有状态；默认放在项目内会污染目录，并增加监听、同步、备份和工具扫描的附加开销。P2 已将这三类数据接入 userData；已有旧数据需用户主动迁移。Hook 尚未改造，仍可能创建 `.janusX`，不能将本阶段解释为整个目录已退场。

实施由[工作区数据、读写与 Hook 生命周期总计划](../planning/workspace-data-lifecycle-plan.md)统一编排，后续由用户逐阶段调度；本篇保持存储和读写设计事实的归属。

检查点底层仍由终端提交及 Agent 文件工具使用，支持快照、差异与恢复；[会话检查点模块](../sessions/checkpoints/module.md)明确会话管理界面已移除还原点呈现及操作。保留底层能力不代表恢复旧界面。启动配置仍参与表单、运行器、项目检测与 worktree 配置继承。

## 当前读写与清理事实

检查点引擎位于 `@janus-agent/agent-core`，命令执行位于 `@janus-agent/node-hosts`，源依赖来自相邻 `janus-agentX` 仓库。终端创建调用检查点初始化；首次查询也可能初始化。初始化共享进行中的请求，只加载已有检查点元数据，不创建空目录；首次真实写入才持久化关联和数据。块回收走空闲队列。

创建检查点会枚举候选文件、查询文件状态、捕获内容，写完整快照 JSON 与索引。内存中的 mtime/size/hash 缓存避免未变化文件重复读取内容，内容块按哈希去重；超大文件不保存内容。新检查点直接为 ready，完成已有 ready 检查点不重新扫描。变更数量查询仍可能枚举文件及查询状态。同步命令流式写日志并使用背压，桌面后台命令退出时分块保存尾部 1000 行，启动配置只在保存时写入。P1 的代表性采样归最小读写方案；P2 不将路径迁移视为降低磁盘物理占用的保证。

检查点创建后异步执行保留策略：每工作目录最多 40 个，超过 30 天清理但至少保留最新 5 个；初始化和删除检查点时回收无引用内容块。没有总容量预算，长期不再创建检查点的目录也不会因时间经过自动执行保留策略。同步命令单次捕获约 10 MiB 上限不等于日志总量受控，未发现其历史日志自动清理。后台退出任务在当前进程内最多 20 个，淘汰时删除关联日志，但重启后不扫描历史文件。工作区删除入口回收终端和 Office 监听、删除注册记录，没有联动回收这些私有状态。

## Decision

由主进程在当前有效 `app.getPath('userData')` 下管理 `janusx/workspace-state/<storageId>/`，保存版本化 manifest、launch.json、checkpoints 和 logs。新工作区直接使用新存储，不创建项目根 `.janusX`；已有旧数据的工作区在用户主动迁移前继续使用旧存储，成功后单向切换。读取不存在的数据不创建目录，首次真实写入才落盘。只迁移 JanusX 私有状态；源文件、Git、工程 Notes、项目依赖和构建产物继续由项目及其工具拥有。团队共享运行配置通过显式导入／导出提供，现有配置继承语义保留。

storageId 是随机 UUID，不使用显示名称或单纯路径哈希。P2 的本地目录关联以 realpath 和 dev／ino／birthtimeNs 核实，同路径被替换得到新身份，同目录重复导入复用经验证的关联，不同 worktree 和 profile 隔离。无注册记录的工具调用也通过统一解析器持久关联。远程工作区在迁移页面明确标为不支持，不把远程路径当本地目录访问；远程私有状态迁移留待对应运行环境实现。

显示名称变化不改变存储身份。磁盘目录移动或改名后的显式重新定位、移除与重导入由 P4 实施；P2 不从名称猜测迁移，也不清理离线关联。同一路径被新项目占用不得静默继承旧恢复数据。路径暂时不可访问只标记离线，不推定删除，尤其不能因断线或移动盘未挂载执行清理。

## 生命周期与清理（P4 待实施）

从侧栏移除工作区先停止关联任务、释放读写资源，再解除关联；最后一个关联解除后标记待清理并进入恢复期，重新导入可恢复关联。显式永久清除只删除已核实身份的应用私有数据，不删除项目文件。活动任务、恢复操作和日志读取持有使用保护，多个实例需协调，避免清理与写入竞态。

配置不按日志过期；检查点属于恢复历史，应保留已有数量／时间规则并补充容量预算；日志按时间与容量回收。全局及单工作目录预算、待清理恢复期、日志天数尚未定值，不将讨论示例写成已实现默认。后台清理在启动后或空闲时低频、分批执行，有时间及扫描量上限；同一批检查点淘汰后统一回收内容块，避免每删一项重复全量扫描。设置页应展示占用、最后使用及待清理状态，提供分类清理和永久清除入口。迁移后检查点内存缓存及监听也必须随身份解除释放。

## 最小读写门控（P1 已实施）

用户要求减少设计复杂度及难维护阈值。以[最小读写方案](../planning/workspace-data-contract-baseline.md)为实施依据：一个宿主队列串行执行重型读写批次，同目录变更保持顺序；初始化和相同查询共享执行，列表只读元数据；扫描、日志和空闲清理分批处理，关闭时取消无用请求。首版采用 32 文件／批、全局最多等待 64 个任务、后台全量扫描批间休息 20ms，沿用已有大小保护，增量扫描后置。

撤下多层速率预算、令牌桶、自适应压力降速、复杂优先级及旧复杂实验阈值。先消除多终端扫描叠加、查询风暴、大日志集中写和重复 GC，再用代表场景验证；后台固定休息不延迟显式写前保护和恢复，实测不足再按证据调整。

安全约束保留：Agent 修改前完成完整保护快照；回合错过边界显示不可用；快照发布与 GC 互斥；部分扫描不能冒充完整恢复数据。P1 已接入共享队列，P2 的迁移复用同一通道和三个常量。自动化结果及限制见最小读写方案。

## 升级、降级与迁移

应用版本号与数据格式版本、清理策略版本分离。正常覆盖升级复用稳定的 userData 和 storageId，不按应用版本创建新目录、不重置最后使用时间或恢复期。沿用[应用 profile](./application-profile.md)的开发版、安装版、免安装版隔离；切换发行渠道或显式 user-data-dir 是选择其他 profile，不能自动合并或把另一个 profile 当孤儿数据删除。

P2 的 manifest 使用 schema 1，记录 storageId、当前关联路径、retentionStartedAt 及迁移回执；后续清理策略字段由 P4 引入，不预填未实施的策略。未知新格式或损坏 manifest 保留并报告。升级只执行明确的格式迁移，不自动重置时间。收紧清理策略需明确过渡规则，不能在升级首次启动时意外批量删除历史；不能承诺旧版应用或未来所有版本天然理解新格式。

旧 `.janusX` 迁移由用户主动触发，按白名单处理启动配置、检查点及日志：在旧写入已停止后复制、校验、记录回执并切换读取，然后自动删除已验证的旧源文件，仅在目录为空时移除目录。未知文件和尚未迁移的 Hook 资产保留，不递归删除整个 `.janusX`。复制或校验失败保留原数据且不覆盖目标新数据；切换后旧文件删除失败显示“迁移完成，旧文件清理未完成”，后续只重试清理，不重复导入或退回旧存储。批量选择按工作区逐个排队，单项失败不阻断其他项。

用户确认主动迁移时，迁入数据的时间保留期从首次成功切换时间重新起算一次；原 createdAt 保留用于历史展示和排序，单独持久化保留期起算时间。失败、重试、旧文件清理重试和普通版本升级均不刷新这个起点；既有数量限制仍生效，容量规则和日志保留天数由 P4 确定。此项是主动迁移的明确例外，替代之前“迁移也不重置保留期”的设计；迁移本身不额外触发历史淘汰。

迁移入口只列出当前 profile 已登记目录，不扫描整盘。复制保留原件，因此临时需要容纳一份迁入数据；磁盘不足作为可重试失败报告，未引入容量预算系统。目标同名文件内容不同即中止，不覆盖。Agent 使用 command.read-log 按当前 workspaceId 和文件名 logId 分页读取，默认 16 KiB、最多 64 KiB，拒绝路径穿越和跨工作区读取，不授予任意 userData 读取权限。宿主注入接口在 janus-agentX 源码维护；独立 CLI 未注入时保持旧路径，不直接修改 node_modules。

## 升级提示与设置入口（P2 已实施）

常驻入口放在“设置 → 通用 → 数据管理”区块，条目名为“旧工作区数据迁移”。直接展示已登记工作区的待迁移、已迁移、离线／无法检查、失败及旧文件待清理状态，不新增一级分类或中间管理按钮。可选择单个或批量工作区，再点击“迁移并清理旧文件”执行。执行前说明会迁移哪些私有数据、校验后清除对应旧文件，并重新起算迁入数据的时间保留期；未知文件可能使 `.janusX` 继续保留。

首次运行支持该能力的升级版本时，应用界面就绪后，对已登记且可访问工作区只做旧存储存在性检查，走 P1 队列，不统计完整目录大小或扫描源码。发现旧数据才显示一次可关闭提示，明确声明来源、迁移范围、实际目标位置及成功后的清理行为，不能只写“迁移数据”或“应用数据目录”。提示文案为：“可将旧工作区 `.janusX` 中的启动配置、检查点历史和命令日志迁入 JanusX 应用数据目录。保存位置：{当前 profile 的实际 workspace-state 绝对路径}。校验成功后将自动删除对应旧文件；项目源码和其他未纳入迁移的文件保持原位。”提供“前往迁移”和“稍后处理”；前者直接定位上述设置区块，不执行迁移，后者关闭提示。提示不阻断正常使用、不自动打开设置、不自动复制或删除数据。新安装且没有旧数据的用户不显示提示。

设置迁移页在执行按钮之前持续展示每个工作区的实际来源目录、实际目标目录及本次找到的迁移类别，类别映射为 `.janusX/janusX.launch.json` → `launch.json`、`.janusX/checkpoints/` → `checkpoints/`、`.janusX/logs/` → `logs/`，缺失类别标注“未发现”，不暗示会完整搬走整个 `.janusX`。目标根路径由当前有效 userData 动态解析，不写死 `%APPDATA%/JanusX`，具体工作区目标包含其 storageId。完整路径可换行并可复制，不能只保留截断文本。批量迁移逐项展示对应来源和目标；前往迁移前可先展示目标根目录，具体 storageId 路径在解析后、执行前呈现。页面同时说明迁入数据的时间保留期在首次成功切换时重新起算一次，原创建时间保留，普通升级和重试不再次重置。此处只展示路径和范围，不为展示目录而创建实际数据目录。

提示已展示状态按当前 profile 和迁移功能标识持久化，不按每个应用版本或每次启动重新提醒。关闭提示后仍可从设置进入；没有已知待迁移项时不消耗提示展示状态，后续发现旧数据时可提示一次。离线工作区不当成没有数据或已经完成，用户重新连接后在设置重新检查。所有已知项目迁完后入口仍保留，显示“暂无待迁移工作区”，并提供“重新检查”；轻量检查与迁移进度独立，打开设置不自动迁移。

## Alternatives considered

保留根目录布局实现成本最低，但不满足用户的目录边界要求；按路径哈希建目录简单，却会在移动后遗留孤儿状态。稳定身份与应用数据集中管理增加注册、重新定位、清理和跨版本迁移成本，但使改名、移除及占用治理具备统一语义。若后续需要跨电脑携带或共享状态，再设计显式导出，不恢复默认根目录存储。

## Consequences

P2 的本地实现与自动化验收见下节。磁盘目录重新定位、移除与重导入、关联释放、容量回收及跨进程长期维护仍属于 P4／P6，不能由本次迁移测试替代。

## P2 实现与验收

主进程在 profile 选择及单实例锁之后安装解析器。registry.json（schema 1）持久化目录身份和本功能的提示已展示状态；首次只读发现不落盘，首次写入或提示展示才保存。每个 storageId 的 manifest.json 记录切换和清理完成状态，迁移回执逐文件记录相对路径、大小及 SHA-256。关联表与 manifest 不按应用版本分目录或刷新保留期；检查点仍保留原 createdAt，年龄淘汰使用 max(createdAt, retentionStartedAt)。

迁移只枚举 launch 文件、checkpoints 顶层 JSON／blobs 的 40 位哈希文件和 logs 顶层 .log 文件；不遍历未知子树。复制使用 64 KiB 缓冲和队列让出，校验内容、元数据稳定性、配置格式及检查点块引用，重新核对来源清单后原子提交 manifest。提交前失败保留源；提交后失败只重试回执内的源清理，清理前再次核对两侧哈希。只删除已知空目录，未知文件、未知空目录和 Hook 保留。未知或损坏目标不覆盖。

迁移前拒绝活动终端、运行任务和日志使用者；迁移期间阻止新命令启动，同目录配置和检查点操作由队列排序。切换前释放旧检查点缓存，旧空闲 GC 恢复时发现缓存已替换即退出。此门控属于当前桌面进程；其他旧应用或独立 CLI 必须先关闭，不能把内容校验当跨进程锁。

定向自动化命令为 `npx vitest run` 加 tests/unit 下 workspace-state-storage、workspace-storage-service、workspace-storage-ipc、workspace-storage-preload、workspace-storage-ui、project-config-contract、project-chat-context、project-ipc-contract、project-service、project-runner-scope、project-runner-adhoc-recovery、project-runner-stop-all、agent/command-tools、agent/project-tools、launch-config-chat、checkpoint-io-query、checkpoint-query-store 的 .test.ts 路径。覆盖真实文件复制、冲突、中断重试、清理失败、源变化、未知 schema、链接拒绝、离线／同路径替换、profile/worktree 隔离、重启恢复、保留期一次起算、活动任务和大日志让出；Chromium 验证明确触发、完整路径、提示一次、延迟挂载定位及窄屏无溢出。该命令共 17 文件、111 项通过。agentX 全量测试为 agent-core 377 项通过／1 项原有跳过、node-hosts 64 项通过；两包构建、JanusX typecheck、定向 ESLint、build:check、i18n:check、check:package-boundary 和 check:notes 通过。

本次为主 Agent 自动化测试及浏览器截图检查，未进行真实升级安装包、慢盘物理占用、远程迁移或长时间跨进程验收；这些仍由 P6 跟进。没有以测试证明磁盘利用率永不达到 100%。

本次用户另行授权清理当前仓库 `.janusX/blueprints`、`design`、`shots` 残留，共 20 个文件、无 Git 跟踪；有界代码及文档检索未发现这些目录的完整路径引用，目录内未发现重解析点。删除调用被自动审批审查以 blocked by policy 拒绝，清理未完成；此结果不等同于已迁移或已回收空间。
