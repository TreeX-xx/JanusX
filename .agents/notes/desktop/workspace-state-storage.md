# 工作区私有状态迁出项目目录

## Problem

2026-10-29 用户确认将迁移方向及维护规则记录到文档；本决策已确认，代码迁移尚未实施。JanusX 当前仍会在工作目录生成 `.janusX`。其中启动配置属于本机项目配置，检查点和命令日志属于应用私有状态；默认放在项目内会污染目录，并增加监听、同步、备份和工具扫描的附加开销。隐藏文件树条目和 Git 忽略不能阻止创建。

实施由[工作区数据、读写与 Hook 生命周期总计划](../planning/workspace-data-lifecycle-plan.md)统一编排，后续由用户逐阶段调度；本篇保持存储和读写设计事实的归属。

检查点底层仍由终端提交及 Agent 文件工具使用，支持快照、差异与恢复；[会话检查点模块](../sessions/checkpoints/module.md)明确会话管理界面已移除还原点呈现及操作。保留底层能力不代表恢复旧界面。启动配置仍参与表单、运行器、项目检测与 worktree 配置继承。

## 当前读写与清理事实

检查点引擎位于 `@janus-agent/agent-core`，命令执行位于 `@janus-agent/node-hosts`，源依赖来自相邻 `janus-agentX` 仓库。终端创建调用检查点初始化；首次查询也可能初始化。初始化创建目录、加载检查点 JSON 并回收无引用内容块。

创建检查点会枚举候选文件、查询文件状态、捕获内容，写完整快照 JSON 与索引。内存中的 mtime/size/hash 缓存避免未变化文件重复读取内容，内容块按哈希去重；超大文件不保存内容。新检查点直接为 ready，完成已有 ready 检查点不重新扫描。变更数量查询仍可能枚举文件及查询状态。每次同步命令结束写日志，后台命令退出时保存尾部 1000 行，启动配置只在保存时写入。迁移位置不能消除快照自身的扫描成本；本次未进行性能采样，不据此认定现场卡顿原因。

检查点创建后异步执行保留策略：每工作目录最多 40 个，超过 30 天清理但至少保留最新 5 个；初始化和删除检查点时回收无引用内容块。没有总容量预算，长期不再创建检查点的目录也不会因时间经过自动执行保留策略。同步命令单次捕获约 10 MiB 上限不等于日志总量受控，未发现其历史日志自动清理。后台退出任务在当前进程内最多 20 个，淘汰时删除关联日志，但重启后不扫描历史文件。工作区删除入口回收终端和 Office 监听、删除注册记录，没有联动回收这些私有状态。

## Decision

由主进程在当前有效 `app.getPath('userData')` 下管理 `janusx/workspace-state/<storageId>/`，保存版本化 manifest、launch.json、checkpoints 和 logs。默认不再创建项目根 `.janusX`，读取不存在的数据不创建目录，首次真实写入才落盘。只迁移 JanusX 私有状态；源文件、Git、工程 Notes、项目依赖和构建产物继续由项目及其工具拥有。团队共享运行配置通过显式导入／导出提供，现有配置继承语义保留。

storageId 是稳定身份，不使用显示名称或单纯路径哈希作为持久身份。注册工作区关联存储身份，真实目录／worktree 另有独立身份，远程目录包含运行环境身份。同目录重复导入可复用经验证的关联，不同 worktree 不共享可恢复快照。无注册记录的工具调用也必须通过统一解析器得到持久关联。具体身份结构及验证算法待实施时确定，不能仅凭路径相同就将旧恢复数据绑定到新项目。

显示名称变化只更新元数据。磁盘目录移动或改名通过显式重新定位更新路径并保留身份；不能从名称猜测迁移。同一路径被新项目占用不得静默继承旧恢复数据。路径暂时不可访问只标记离线，不推定删除，尤其不能因远程断线或移动盘未挂载执行清理。

## 生命周期与清理

从侧栏移除工作区先停止关联任务、释放读写资源，再解除关联；最后一个关联解除后标记待清理并进入恢复期，重新导入可恢复关联。显式永久清除只删除已核实身份的应用私有数据，不删除项目文件。活动任务、恢复操作和日志读取持有使用保护，多个实例需协调，避免清理与写入竞态。

配置不按日志过期；检查点属于恢复历史，应保留已有数量／时间规则并补充容量预算；日志按时间与容量回收。全局及单工作目录预算、待清理恢复期、日志天数尚未定值，不将讨论示例写成已实现默认。后台清理在启动后或空闲时低频、分批执行，有时间及扫描量上限；同一批检查点淘汰后统一回收内容块，避免每删一项重复全量扫描。设置页应展示占用、最后使用及待清理状态，提供分类清理和永久清除入口。迁移后检查点内存缓存及监听也必须随身份解除释放。

## 最小读写门控（P1 已实施）

用户要求减少设计复杂度及难维护阈值。以[最小读写方案](../planning/workspace-data-contract-baseline.md)为实施依据：一个宿主队列串行执行重型读写批次，同目录变更保持顺序；初始化和相同查询共享执行，列表只读元数据；扫描、日志和空闲清理分批处理，关闭时取消无用请求。首版采用 32 文件／批、全局最多等待 64 个任务、后台全量扫描批间休息 20ms，沿用已有大小保护，增量扫描后置。

撤下多层速率预算、令牌桶、自适应压力降速、复杂优先级及旧复杂实验阈值。先消除多终端扫描叠加、查询风暴、大日志集中写和重复 GC，再用代表场景验证；后台固定休息不延迟显式写前保护和恢复，实测不足再按证据调整。

安全约束保留：Agent 修改前完成完整保护快照；回合错过边界显示不可用；快照发布与 GC 互斥；部分扫描不能冒充完整恢复数据。P1 已接入共享队列，仍沿用旧路径；P2 再迁移 userData。自动化结果及限制见最小读写方案。

## 升级、降级与迁移

应用版本号与数据格式版本、清理策略版本分离。正常覆盖升级复用稳定的 userData 和 storageId，不按应用版本创建新目录、不重置最后使用时间或恢复期。沿用[应用 profile](./application-profile.md)的开发版、安装版、免安装版隔离；切换发行渠道或显式 user-data-dir 是选择其他 profile，不能自动合并或把另一个 profile 当孤儿数据删除。

manifest 记录数据 schema、策略版本、身份关联、生命周期时间和迁移回执。升级只执行明确的版本迁移，采用可重试、幂等、写前校验及原子提交；清理与迁移互斥。未知新格式或损坏 manifest 保留并报告，旧版本降级不得按旧策略删除无法理解的数据。收紧清理策略需明确过渡规则；恢复期是否缩短必须显式处理，不能在升级首次启动时意外批量删除历史。规则调整需要升级／降级及中断恢复验证，不能承诺所有未来版本天然兼容。

旧 `.janusX` 迁移按白名单处理启动配置、检查点及日志：在旧写入已停止后复制、校验、记录回执并切换读取，再清理已核实的源文件；失败保留原数据且不覆盖目标新数据。迁移只发现已登记或显式打开的目录，不扫描整盘。需要空间预算及目标冲突处理。未知文件保留，避免整目录盲搬／盲删。Agent 当前用工作区读取工具访问日志，迁出后必须提供受限日志读取接口，不扩大为任意 userData 读取权限。依赖包应在 janus-agentX 源码中支持宿主注入路径，不直接修改 node_modules。

## Alternatives considered

保留根目录布局实现成本最低，但不满足用户的目录边界要求；按路径哈希建目录简单，却会在移动后遗留孤儿状态。稳定身份与应用数据集中管理增加注册、重新定位、清理和跨版本迁移成本，但使改名、移除及占用治理具备统一语义。若后续需要跨电脑携带或共享状态，再设计显式导出，不恢复默认根目录存储。

## Consequences

实施验收应覆盖：新项目不生成 `.janusX`、重命名及重新定位、移除与重新导入、重复关联、worktree／远程隔离、同路径换项目、离线目录、活动读写与多实例清理、容量回收、旧数据迁移中断／冲突／重试、正常升级及未知 schema 降级保护。上述迁移与长期生命周期行为仍处于方案阶段；P1 仅实现读写门控，不代表它们已交付。

本次用户另行授权清理当前仓库 `.janusX/blueprints`、`design`、`shots` 残留，共 20 个文件、无 Git 跟踪；有界代码及文档检索未发现这些目录的完整路径引用，目录内未发现重解析点。删除调用被自动审批审查以 blocked by policy 拒绝，清理未完成；此结果不等同于已迁移或已回收空间。
