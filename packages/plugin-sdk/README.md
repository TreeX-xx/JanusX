# JanusX plugin SDK

The SDK provides the version 1 local-plugin contract, strict manifest and call-policy validation, a MessagePort client, and an independently buildable four-surface scaffold. In JanusX, open Settings → Plugins, import the built directory, enable local development mode, review permissions and project scope, and enable the plugin. The scaffold shows a standalone preview outside the authorized host.

## Background tasks, network and public contracts

P5 uses **host-executed declarative tasks**, not arbitrary plugin background JS. See the independently importable [provider and consumer examples](examples/README.md). A manifest-only package can use `views: []` plus `contributes.tasks`; it needs no page, dist directory or build. Require `tasks.declarative` and request `tasks.run`. Each task declares a scope, a primitive object input schema, a deadline and bounded delay/log/request/emit/service steps. Run and stop tasks in host Settings → Plugins → Background tasks and credentials, or use `api.tasks.start({task,input})`, `list()` and `cancel({id})`. Page close leaves tasks running; project/worktree changes stop project tasks, and disabling/reloading any participating plugin stops its work. Retry by explicitly running again. Histories and in-flight work are not restored across app restarts.

`api.network.fetch({url,method?,body?,credential?})` and task request steps require `network.fetch` capability and a permission such as `{ "name": "network.fetch", "origins": ["https://api.example.com"] }`. Only exact public IPv4 HTTPS origins on port 443, GET/POST and bounded text bodies are supported. DNS answers are checked and pinned, TLS remains verified, and unapproved/private targets, cross-origin redirects and POST redirects fail. Plugin pages remain offline. Requests are mediated by the host, use independent HTTPS connections and do not inherit browser cookies or environment proxies. Each request has a 4-second deadline and a 64-KiB response limit; the broker applies per-plugin concurrency/rate limits. No arbitrary request headers, streaming, IPv6-only service or custom proxy options are exposed.

For bearer tokens, require `credentials.use`, add its permission and declare `contributes.credentials: [{ "id": "token", "title": "API token", "origin": "https://api.example.com" }]`. Users enter/replace/revoke tokens only in host Settings. Slots are separately encrypted by plugin and application or project/worktree scope, with no fallback inheritance. Unavailable secure storage fails closed; no token getter exists. Requests may name their own declared slot; credentials are injected only at its authorized origin. **Credentialed requests return status only**, with empty body/contentType, so a remote echo cannot disclose the token to plugin UI. Authenticated response payloads and OAuth refresh are not part of this contract. Disable/uninstall retains encrypted slots; Delete plugin data clears them.

Declare versioned `events` and `services` with explicit consumer plugin lists; consumers declare matching `consumes.events/services` entries with provider ID, local ID, integer version and primitive schema. Missing required providers block activation; `optional: true` allows discovery to degrade. `api.events.subscribe({plugin,event,version}, listener)` returns an unsubscribe function. `publish({event,data,cause?})` emits only the publisher's declared schema and scope; pass an actually received event ID as cause when continuing a chain. The host stamps source/trace, rejects repeated-plugin chains and forged causes, and limits root-event spam. Events do not automatically execute tasks. `api.services.discover()` lists matching accessible services; `call({plugin,service,version,input})` starts a provider-declared task and returns a consumer-owned run ID. Results use the fixed v1 `PluginTaskRun` status/log/result contract. Version/schema/scope and both sides' permission/consumer declarations are checked at use; services do not expose private storage or arbitrary RPC. Cycles/depth, steps, run histories, results, subscriptions, cancellation and activation generations are bounded by the host.

## User configuration

To add a host-generated configuration form, require `configuration.settings`, declare the `configuration.read` permission and add `contributes.settings`. These are ordinary non-secret parameters, separate from private KV and authorization:

```json
[
  { "key": "label", "title": "Reference label", "type": "string", "default": "Reference", "scope": "project", "minLength": 1, "maxLength": 40 },
  { "key": "enabled", "title": "Show details", "type": "boolean", "default": true, "scope": "project" },
  { "key": "limit", "title": "Item limit", "type": "number", "default": 10, "minimum": 1, "maximum": 100, "integer": true, "scope": "project" },
  { "key": "style", "title": "Display style", "type": "enum", "default": "compact", "options": ["compact", "full"], "scope": "application" }
]
```

Each of up to 64 unique fields has a key, title, optional description, type, valid default and scope. `scope: "project"` permits a project/worktree override of the application value; `application` fields cannot be overridden there. Strings are bounded to 4096 characters, enums to 32 options. Patterns, arbitrary schemas, HTML, executable migrations and credential fields are unsupported.

Users edit these fields in Settings → Plugins → Configuration. Saves and resets check a revision including the schema and inherited layer. Unknown or invalid old values are diagnosed and ignored when computing effective values, but kept on disk until explicitly reset or replaced. Disable and uninstall preserve configuration; Delete plugin data clears it. Corrupt stores fail rather than silently resetting.

For a renamed setting, require `configuration.migrations` and declare `contributes.settingMigrations: [{ "from": "old-label", "to": "label" }]`. Up to 64 mappings must have unique sources and destinations. Sources must be retired keys and destinations must be current settings; live-key sources, chains, merges, scripts and transforms are rejected. The host previews migration candidates in the selected settings layer without exposing incompatible raw values. The user applies compatible migrations explicitly: an old value moves only when the destination is absent, the value passes the current field constraints, and its scope is allowed. Existing destinations and incompatible old values remain untouched. One version-checked atomic save applies all ready mappings in that layer and notifies configuration watchers. Application and each project/worktree must be migrated separately; ordinary reads and reloads never migrate. The revision includes the mapping declarations. Save or reload pending form edits first. The trusted management API accepts `configurationUpdate` with `migrate: true`, an empty patch and `reset: false`; plugin pages gain no migration or write method. Type conversions, cross-layer moves, history backups and migration rollback are not provided; applying consumes only successfully moved source keys.

`context.configuration` is true for a plugin with settings. `api.configuration.get()` returns `{ values, overrides, inherited, revision, issues }`; `watch(listener, options?)` returns `{ configuration, unsubscribe }` and streams complete effective snapshots. It follows the page's bound project/root, accepts no path or plugin/project ID, and requires `configuration.read`. The generated page displays and watches configuration when present. Configuration writes belong to the trusted host form; plugins cannot call an arbitrary configuration setter. A stale form reports `CONFIGURATION_CONFLICT` and preserves its edits until the user reloads. Use the separate host credential slots described above; do not put API keys or tokens in ordinary settings.

To offer a configuration button in your own page or menu, require `configuration.open` and `configuration.read`, and declare settings or credential slots. Credential-only plugins can use the same navigation without declaring dummy settings. The host sets `context.configurationNavigation: true`. `await api.configuration.open()` accepts no plugin ID, path or scope; it opens this plugin's host configuration. `{ opened: true }` acknowledges dispatch, not a save. Project pages select the current project/root layer; application pages select application defaults. Only an active page may navigate, with one request per plugin per ten seconds. Hidden pages return `CONTEXT_UNAVAILABLE`, repeated requests return `RATE_LIMITED`, and revoked pages retain lifecycle errors. The host modal shields plugin pages until closed. Navigation grants no configuration write authority or access to raw credentials.

## Pages inside application settings

Declare an application-scoped, single-instance view with `location: "settings"`, require `views.settings`, and request `ui.views.open`. For example:

```json
{ "id": "settings", "title": "My plugin settings", "entry": "dist/settings.html", "location": "settings", "scope": "application", "instancePolicy": "single" }
```

Installation adds the view to the application's Plugin settings navigation. Disabled or blocked plugins show a host-owned message linking to the plugin manager; installation alone never runs the page. Local sources appear only in development mode. After permission review and activation, selecting the entry mounts the package's offline, isolated page inside the settings dialog. Closing the dialog, changing tabs, disabling or uninstalling the plugin releases the page. Uninstall removes the navigation entry immediately and leaves retained plugin data intact. Updates to settings page declarations require renewed consent. Older hosts reject the new required capability.

An own open-view command, `api.views.open({ view: "settings" })`, or the installed-plugin settings button selects this application settings entry. It does not open a workbench or change the selected project. The page receives application context (`project: null`), so it cannot read project files through application context. It retains the usual bridge permissions and failure/retry behavior. The host waits for the dialog's entrance animation before attaching the native page, hides it during exit, and detaches it while another host dialog or notification covers it.

This surface is independent of `contributes.configurationViews`, whose workbench editors submit proposals for declared configuration fields. A settings view does not require dummy configuration fields, gain a configuration setter, or receive permission to propose configuration changes. Use the existing granted configuration, storage or separately authorized native interfaces for its actual data needs.

## Trusted native services

`runtime.native` is restricted to verified official packages whose signing key is also pinned for that plugin in the host native allowlist. Explicit permission review and enablement are required. Local linked/copied sources cannot request this mode. A native utility process has the current user's OS rights; it is not a filesystem or network sandbox. Ordinary plugins retain the isolated page and declarative task boundaries.

Declare `native.entry` as a bundled `dist/*.cjs` file, a positive `dataVersion`, and the allowed method names. The Node entry imports `startNativePlugin` from `@janusx/plugin-sdk/native`; views import the regular SDK and call `api.native.call({ method, input }, { signal })` or subscribe using `api.native.watch`. Values are bounded JSON, packets are bound to the activation generation, and calls support cancellation. The host stamps the project and page instance; renderer-provided paths cannot choose another project. Emit `{ scope: { projectId, root }, data }` for project events, or `{ scope: null, data }` for application events. Known public error codes survive the bridge; exception text is not forwarded.

The implementation returns `call`, `stop`, and optional `releaseContext(instanceId)`. Release cancels resources owned by a closed, crashed or invalidated page without cancelling other pages. Stop must release the service's timers, watchers, tasks and processes. The host terminates an unresponsive service after the shutdown deadline. Native updates require a stopped plugin; unsupported data-version changes are rejected instead of assuming code rollback restores data.

Trusted native packages may additionally require `desktop.native` (which requires `runtime.native`). Host callbacks offer `desktop.encryption`, `desktop.encrypt/decrypt` (base64 ciphertext), `desktop.clipboard`, `desktop.openPath` (only inside the plugin's native data directory), `desktop.environment`, `desktop.proxy`, and `desktop.external` (HTTP(S) only). Proxy listeners belong to the native activation and close on revocation. The fixed `desktop.legacy` migration mapping currently exists only for `official.cpa`; it accepts no caller-selected host configuration path. Explicit data resets must honor the activation's `allowLegacyImport` flag.

`desktop.browser.open/close/bounds/status` allocate a separate online sandboxed guest for the native request's host-stamped page `instanceId`, passed as `owner`. It has no preload, SDK bridge or Node integration. The parent plugin page remains offline. The guest is clipped to the plugin's rectangle and hidden with its owner; closing the page destroys only the guest. HTTP(S) popups use the system browser, navigation stays on the management origin, and browser/device permissions and downloads are denied. Open accepts a credential-free HTTP(S) URL without query parameters, optional direct proxy mode and bounded OAuth routes/provider ports/authorization URLs. OAuth state checks call the native `browser.oauth-status` handler; credentials never enter the guest bridge. Status reports load failures and manual callback notices. This is an explicitly trusted native callback, not an online-page capability available to ordinary plugins. The optional [CPA package](../../plugins/cpa/README.md) demonstrates the application-level lifetime.

`desktop.containers` additionally requires `desktop.native` and opts into the structured local container integration. `desktop.terminal.open` accepts `{ owner, request: ContainerTerminalRequest }`: an absolute Docker executable, validated local pipe/socket endpoint, full container ID, allowlisted shell and bounded dimensions. `read/write/resize/close` require a live owner and session ID; the native service must check the container-to-session binding. `read` returns `ContainerTerminalOutput` with a cursor, truncation and exit state. `desktop.terminal.end` lets the native activation clean up without a page owner. Sessions survive page release and are destroyed on native revocation. Eight live sessions and 256 Ki characters per session bound retention; no generic command text is accepted. `desktop.service.open` routes credential-free loopback HTTP(S) URLs to the built-in browser; the native plugin validates a published container port first. `desktop.docker.open` explicitly opens an existing Docker Desktop installation. Hosts without `desktop.containers` reject the package before activation. See [Docker](../../plugins/docker/README.md).

Host callbacks provide `models.catalog`, `models.select`, `models.probe`, `models.generate`, `models.verify` and `agent.run`. Model calls require the model permission; verification also checks the declared credential slot and network origin. Provider keys remain in the host. `nativeAgentRequestSchema` defines a separate bounded Agent turn with only read tools; `agent.tool` callbacks bind to its run ID. Agent-generated edits must use a separate user-approved transaction. This interface does not expose shared host chat sessions or terminal execution.

An optional `native.mcp` contribution declares a bundled CJS entry and command ID. `mcp.launch` returns the host-owned stable launcher and configuration directories. The launcher rechecks the installed signature, consent, compatibility and package bytes before importing the entry, and holds a package lease for the external process lifetime. It never downloads on launch. Updates preserve leased generations; uninstall and data deletion reject while any generation is in use. Production catalog keys and native allowlists must be provisioned by the application publisher before release.

Custom settings pages require `configuration.customViews`, the separate `configuration.propose` permission, and `contributes.configurationViews`, for example `{ "project": "desk" }`. Each optional `application` / `project` reference must identify your own workbench view of the corresponding scope. Changing these bindings requires renewed authorization. Settings → Plugins → Configuration offers Open custom settings for the selected layer; the settings modal closes while the existing isolated workbench opens. The normal form remains available for fallback. No React component or remote settings URL is accepted.

The host sets `context.configurationEditor: true` only for these views. The scaffold then shows a JSON patch editor; replace it with your domain form as needed. Read a baseline with `api.configuration.get()` and call `api.configuration.propose({ patch: { label: "Example" }, expectedRevision: baseline.revision })`. Patches contain 1–64 declared fields; null restores inheritance, and application-only fields are rejected in a project patch. Only an active authorized editor may propose. The host validates scope, types and the baseline revision, then opens its own form for review. `{ proposed: true }` means dispatch, **not saved**; the user must save in the host form. Proposals share the ten-second navigation budget with `configuration.open`. Other plugin views cannot propose, even with the plugin-wide permission. A changed revision returns `CONFIGURATION_CONFLICT`; reload before resubmitting. Host review also checks the original revision at save time and retains pending edits on conflict. Reload discards the proposal; closing settings discards its unsaved review draft. Page-local edits and proposals have no crash/restart recovery guarantee, and cancelling after dispatch does not retract a proposal already handed to the host. This API does not grant a setter, migration, network, file or credential authority.

Call `await connectPlugin()` from a bundled page module to obtain `PluginApi`. The client accepts the port transferred by the minimal isolated carrier preload (or a parent shell), performs the ready handshake, and converts timeouts, aborts and invalidation into `PluginError`. It does not install a global `window.janusPlugin` or expose Electron IPC. Each page has its own instance and context revision; project/root changes close its port.

Build and pack the SDK from this repository:

```powershell
npm run build:plugin-sdk
npm pack --workspace=@janusx/plugin-sdk --pack-destination C:/my-plugin-artifacts
npm run plugins:create -- C:/my-plugins/reference --sdk C:/my-plugin-artifacts/janusx-plugin-sdk-0.1.0.tgz
```

The SDK is not yet published. The generator requires a packed tarball and a new destination; it never overwrites an existing directory. The resulting project uses the public package exports and contains no imports of JanusX source, React, private stores or IPC.

In the generated directory:

```powershell
npm install
npm run build
npm run check
npm run preview
```

`build` typechecks and bundles two HTML pages with local JS/CSS. `check` validates the manifest and the `dist` delivery tree, file types, budgets and declared entries without executing plugin scripts. It rejects linked resources; runtime real-path races, identity, network and navigation isolation are outside this development diagnostic and are checked separately by desktop tests. No install scripts, remote plugin source or package JS entry is executed by the checker.

Use `parsePluginManifest(text, host?)` for strict JSON/schema/compatibility checks, including duplicate keys and contribution references. Optional unknown capabilities are reported through the host's capability list and do not permit unknown fields or methods. `validatePluginCall(manifest, method, params)` rejects unknown methods, undeclared permissions/files, malformed parameters and undeclared view targets. This pure gate does not establish sender identity or user grants. The host must bind the real sender, source, instance, context revision and grants before dispatch, recheck before returning, and perform filesystem/quotas checks.

The SDK reserves `janusx.*` for built-ins. Contributions support workspace/right/workbench/settings/island/window views (single-instance by default), declarative open-view commands, toolbox/add-menu entries and local shortcuts. [Native window views](examples/window-views.md) require their own capability and permission and retain the same offline page bridge. Methods expose context, declared UTF-8 files, private KV, view opening, toast and bounded Island status. Declare `contributes.island` and `ui.island` to call `api.island.update({ id, status })`; status is host-rendered text, progress, badge and a bounded text preview. Actions reference up to three own open-view commands of the same scope. Closing the latest publisher removes its status. Direct page network access, arbitrary process execution, model calls and command callbacks are not accepted. Host-mediated document drafts and declarative tasks/network require their separate capabilities and permissions. Terminal types, CLI/session adapters and PTY backends remain host responsibilities.

`npm run plugins:check` builds the SDK, validates the contract template, verifies the external scaffold and runs the SDK/tool/runtime/command tests. `npm run plugins:verify-scaffold` runs the external scaffold verification separately: it packs this SDK and performs an actual install, typecheck, build and package check in a new system-temporary directory outside the repository; the receipt is `artifacts/plugin-p1/scaffold.json`.

The built-in Agent can consume explicitly authorized declarative public services. Declare `agent.services` as a required capability and permission and include `janusx.agent` in a public service's consumer whitelist. The host retains execution approval, workspace identity, task budgets, cancellation and result ownership. See the [public adapter guide and status provider](examples/agent-services.md) for the supported scope and external CLI availability. [Model tasks](examples/model-tasks.md) add bounded text generation using the host-selected default Janus model, with explicit `models.generate` authorization; no raw keys or provider selection cross the plugin bridge. [Skill resources](examples/agent-skills.md) add explicitly authorized, on-demand third-party guidance with exact revisions and live service references. [Sequential workflows](examples/agent-workflows.md) compose authorized services with typed task-input bindings and step tracking. [Document context providers](examples/document-context.md) expose explicitly granted saved project files on demand through the same page/Agent protocol.

Read-only document viewers are supported in the main window's embedded file editor. Add `documents.viewers` and `documents.readText` to required capabilities, add the `documents.read` permission, and declare a viewer referencing a project-scoped workspace view:

```json
"viewers": [{ "id": "text", "title": "Text preview", "view": "details", "extensions": [".txt", ".log"], "filenames": ["Makefile"] }]
```

The generated page already handles `context.document`. Use `api.workspace.getContext()` to inspect `{ document?: { viewer, path } }`, then `api.documents.readText()` to read only that bound file. The read accepts no path and returns `{ path, text, bytes, version }`; `version` is the content SHA-256, not a save token. Each document/viewer/project-root binding has its own page instance. Private KV remains scoped to the plugin and project/root, so different document pages can deliberately share it. Workspace views may opt into the separately required views.multiple capability. A matching filename is not permission for arbitrary workspace reads, writes or directory traversal.

To submit a draft, also declare the `documents.edit` permission and required `documents.applyEdit` capability, then re-enable the plugin to approve the changed permissions. The bound document context includes `editable: true`; the generated page then offers a textarea and a submit button. Call `api.documents.applyEdit({ text, expectedVersion: file.version })` with the full UTF-8 text (up to 1 MiB, no NUL). It takes no path. Success `{ applied: true }` means the host accepted an unsaved draft, **not** that a file was saved. A dirty or stale host buffer, or a changed disk baseline, returns `DOCUMENT_CONFLICT`. This is a one-draft handoff: review it in the built-in editor before saving or making further submissions.

Accepted drafts survive plugin disable, page failure, project switching and editor detach through the host's existing in-memory editor sessions and unsaved-close flow. Unsubmitted textarea edits remain page-local; neither draft kind promises recovery after an application crash or restart. Reads still observe disk, not the accepted draft. Cancellation or a lost acknowledgement does not undo a draft already accepted by the host. User-triggered saves retain policy authorization and check the baseline hash, serialize competing editor saves, and preserve the draft on conflict. External processes do not share the save queue: this is a pre-write version check, not an OS-level atomic compare-and-swap. Conflicts now offer an editable disk/draft comparison and a user-reviewed save that checks the reviewed version again.

Users choose a viewer through Open with and may persist a default for the filename extension (or full name for extensionless files). No plugin automatically replaces a built-in viewer merely by registering. Dirty buffers owned by another editor, diff/navigation, binary/Office files and floating editor windows use the built-in path. Mount failures, invalidation or a disabled/unavailable plugin fall back to the built-in viewer. Changes to viewer declarations require renewed authorization. Reads are UTF-8, at most 1 MiB, with the same sensitive-path and real-filesystem restrictions as ordinary file reads. Reads observe the current disk content; automatic document change subscriptions remain future work. Continuous host-owned drafts, bounded directory metadata and general workspace instances are described in the [document workspace guide](examples/document-workspace.md).

[Declarative palette themes](examples/palette-themes.md) contribute bounded colors without executable pages. Themes use separate authorization and preserve built-in colors for host settings and approvals.

Workbench views can declare `frame: "plugin"` with required capability `views.workbench.frame` and permission `ui.views.open`. The host then omits its header and surface padding, letting the isolated page draw its own complete workbench. Only such views receive `context.workbenchFrame: true`. `api.views.getFrame()` additionally requires `workspace.context.read` and returns up to 128 granted project identities as `{ projects: [{ id, name }], projectId }`, without roots or paths. `api.views.requestFrame({ action: "close" })` requests closure; project-scoped views may instead request `{ action: "selectProject", projectId }` for a granted project. Both return `{ requested: true }` on dispatch; this is not a guarantee that navigation completed. The host checks the currently active workbench and project/root binding before acting. Project changes retain the existing close-on-scope-change lifecycle. Other view locations cannot declare or call this contract. Declaration changes enter the permission fingerprint. This API grants no native-window controls.

A project workbench may also require `views.workbench.worktrees`. Then `getFrame()` includes `worktrees: [{ id, name, branch, isMain }]` and `worktreeId`, with at most 128 current worktrees of the bound project. IDs are opaque; no filesystem paths enter the page. Use `requestFrame({ action: "selectWorktree", worktreeId })` to select one. The host rechecks the current Git worktree list and project grant before dispatch, rejects removed or unknown IDs, and ignores requests from an obsolete workbench. Switching worktrees within the same project keeps a plugin frame open but destroys and recreates its scoped page, invalidating old requests and subscriptions. Page-local state is reloaded; use scoped storage for durable drafts. Switching to another project still closes the workbench. Older hosts reject the new required capability.

To retain the native page and its header across authorized project or worktree changes, a project workbench with `frame: "plugin"` can additionally require `views.workbench.rebind`. Subscribe through the current SDK's `api.context.subscribe` before starting scoped work. It emits `{ transitioning: true }` when old requests and subscriptions are revoked, then `{ transitioning: false, workspace: PluginContext }` after the host verifies the new root and project grant. The SDK rejects pending calls, blocks calls during transition, and updates the revision used by subsequent requests; context listeners remain subscribed while other subscriptions must be recreated. Cancel local request queues and remove old scoped UI immediately, keep the header mounted, then reload content and subscriptions using `workspace`. Native services receive a new opaque owner and `releaseContext` for the previous scope, so keeping a page does not keep old jobs or previews valid. Missing or ungranted projects, disablement and reload still close the page. This opt-in capability changes no grants and exposes no paths; older hosts reject it instead of silently recreating the page.
